# 11 · 性能、通用性与上位机优化计划

> 当前执行与并发依赖见 [15](resume-and-parallel-plan.md)。本文件保留方向与原则，
> 不以估算代替性能/功耗实测，不根据过期资源报告排除候选。

## 1. 执行顺序

```text
T0 分段计时与公平基准                  ✅ 已建立，三级独立硬件周期计数器闭环（P7）
→ P0 拆解 4.25 s 板端固定开销        ✅ 已闭环（5.284s -> 1.505s，3.5x）
→ P12 PS 固件新靶心（中断驱动/Cache）   ← 2026-09-11 新增，当前最高性能优先级
→ 多 payload 泛化（重复 ≥3 次）        ✅ 21次运行零抖动闭环（P3）
→ 错误鲁棒性矩阵                      ✅ G5 误接受率已闭环（P8）
→ 功耗实测 / 新板迁移                 🚧 待功率计 / 待新器件
```

> **2026-09-11 按 P7 硬件周期实测更新**：
> 独立硬件周期计数器实测证伪了「PL Voter/Decoder 硬件是 62.9% 瓶颈」的假设：
> 4,096 条记录下 Voter 执行仅 29.6 ms (0.93%)，Decoder 仅 0.02 ms (0.0007%)，总 PL 硬件执行不足 30 ms。
> **真正占 99% 的大头锁死在 PS 侧**：
> 1. `[waiting]` lwIP poll 轮询空等 2,776 ms（87.5%）；
> 2. `[in-state]` 全局 Cache Invalidate 维护 396 ms（12.5%）。
> 因此，**彻底关闭所有 PL 侧硬件微架构展开与并行化**，性能优化的主航道正式切换为 **PS 固件中断驱动与精细化局部 Cache 维护（P12）**。

## 3. 数据不足的处理

保持 `data/R0.83_data/` 只读。用 `tools/generate_payload_dataset.py` 生成 D1 多 payload，用 `tools/mutate_reads.py` 生成 D2 错误/覆盖度数据；每个实验保存 manifest、输入/输出哈希、随机种子和最终判据。D0 真实、D1/D2 合成、D3 外部数据必须分开报告。

## 4. 上位机

拆分 FASTQ 读取、几何检查、协议会话、结果接收、LDPC 和验证报告；用 profiler 找热点；优化缓冲复用、流式读写、C LDPC 和结果并行处理。Python 保留为参考实现，C/原生扩展必须逐位对照并通过断连、超时、错误协议测试。

## 5. 成功定义

> 按 [17](competition-strategy.md) §1：**“性能”不再定义为超过对照 CPU**。
> 在 XC7Z010 上这已被自有实测数据证明不可能（固定开销 4.25 s 本身就大于
> 多核 CPU 基线）。性能成功 = 真实浪费被消除且可复现。

- 性能：同输入同正确性下，分段和端到端耗时下降；
- 通用性：至少 5 个 payload；
- 鲁棒性：覆盖度、substitution、insertion、deletion 曲线；
- 工程性：长稳、断连恢复、资源/时序/功耗有证据。
