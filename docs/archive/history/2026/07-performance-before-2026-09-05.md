# 07 · 性能实测与加速价值分析

测试机：Intel Core i5-13500H（8 线程可用），WSL2 / Ubuntu 20.04。
数据：R0.83 SE150，参考 40,500 nt，读段 150 bp。
所有 CPU 数字为实测；FPGA 数字为按 RTL 逐周期推算（尚无上板实测）。

---

## 1. 结论先说

**同一个算法，实现方式不同，耗时相差 170 倍。** 所以「PC 快还是 FPGA 快」这个问题，
必须先说清楚拿哪一版 PC 实现来比。

### SE150（2,048 条 × 2 方向，可完整还原图片）

| 方案 | 每条读段（含正反两个方向） | 总耗时 |
| --- | ---: | ---: |
| CPU 单核，C（位平面 + popcount） | **0.226 ms** | **0.46 s** |
| CPU 8 进程，C | 0.058 ms | 0.12 s |
| CPU 单核，numpy FFT 相关 | 5.9 ms | 12.1 s |
| CPU 单核，numpy 暴力滑窗 | 6.4 ms | 13.0 s |
| **XC7Z010 @100 MHz（当前 RTL）** | **1.94 ms** | **4.0 s** |

### SE250（800 条 × 2 方向，可完整还原图片）

| 方案 | 每条读段 | 总耗时 |
| --- | ---: | ---: |
| CPU 单核，C | **0.286 ms** | **0.23 s** |
| CPU 8 进程，numpy FFT（`tools/readout.py`） | — | 1.77 s |
| CPU 单核，numpy FFT | 9.0 ms | 7.2 s |
| **用户实测：48 核 2.2 GHz，约 600 条** | — | **40+ s** |
| XC7Z010 | — | **不支持**（几何写死 150 bp） |

### 与用户实测数据的对账

用户报告：48 核 2.2 GHz 机器上处理 600 余条读段（滑窗相关 + 大数投票 + LDPC）需 40 余秒。
本文用同一数据、同一算法复现如下：

| 口径 | 耗时 |
| --- | ---: |
| numpy FFT **单线程**，800 条 SE250，本机 ~4.5 GHz | 7.2 s |
| 同上，按时钟折算到 2.2 GHz | ≈ 15 s |
| 用户实测 | 40+ s |
| **优化 C，单核，本机** | **0.23 s** |
| 优化 C，单核，折算到 2.2 GHz | ≈ 0.5 s |

**结论：用户的 40 秒是实现层面的数字，不是硬件极限。** 它落在「单线程、
numpy/MATLAB 级实现」这一档，48 个核基本没用上；同样的算法写成 C 并只用一个核，
就是 0.5 秒量级——**快约 80 倍**。

### 那 FPGA 到底快不快

取决于跟谁比：

| 比较对象 | 结论 |
| --- | --- |
| vs 当前未优化的 PC 实现（40 s） | FPGA（4 s）**快约 10 倍** |
| vs 优化后的 C，单核 | FPGA **慢约 9 倍** |
| vs 优化后的 C，8 线程 | FPGA **慢约 33 倍** |

**建议只使用第二、三行作为对外口径。** 拿未优化的软件当基准，
在论文或答辩里必然被问「CPU 基线优化过吗」，那时第一行的数字会全部作废。

整条 PC 链路（读 FASTQ → 比对 → 投票 → 差分 → 反稀疏化 → LDPC → 出图），
用优化实现在 8 线程下约 **0.35 秒**完成；LDPC 本身只占 0.16 s，其中大半还是进程启动开销。

FPGA 慢的原因不是"FPGA 不行"，而是**当前这版 RTL 只用掉了它应有算力的约 1/150**。见第 4 节。

---

## 2. 一个必须先澄清的事实：种子法在这里不适用

常规测序比对（BWA、Bowtie、minimap2）之所以快几个数量级，靠的是**精确 k-mer 种子**。
但本任务的接收端只有**水印**，而读段是 `水印 ⊕ 稀疏数据` 的含噪副本——两者只有约 50% 的碱基相同。

实测（60 条读段，取各自最佳位置）：

| 比对对象 | 最长连续精确匹配 |
| --- | ---: |
| 读段 vs **水印**（接收端真实拥有的） | 中位 **5** nt，最大 8 nt |
| 读段 vs 真实编码序列（接收端没有） | 最大 150 nt |

16-mer 精确命中的概率约 `0.5^16 ≈ 1.5e-5`。**任何基于精确种子的加速都无效**，
必须做全位置暴力相关。

> 这条结论对项目是**正面**的：它说明 `srpe_batch` 的暴力滑窗不是笨办法，而是必需的，
> 加速这件事本身是成立的命题。问题只出在并行度怎么用。

## 3. FPGA 侧耗时推算（按 RTL 逐周期）

`srpe_batch` 每批 64 条读段：

| 阶段 | 周期数 |
| --- | ---: |
| `S_CLR` 清位平面 | 150 |
| `S_LOAD`/`S_LOAD_R` 装载 64 条 | ≈ 19,264 |
| **`S_LAUNCH`+`S_RUN`+`S_UPD`+`S_NEXT` 计算** | **50 区域 × 808 位置 × 153 = 6,181,200** |
| `S_EMIT` 输出 64 条 | ≈ 19,200 |
| 合计 | ≈ 6,219,600 |

@100 MHz → **62.2 ms / 64 条 = 0.97 ms/条（单方向）**。
由于必须处理反向互补（`docs/03-status.md` D1），等效为 **1.94 ms/条**。

其余各级相比之下可以忽略：

| 环节 | 2,048 条时的耗时 |
| --- | ---: |
| Stage1 比对 | ≈ 4.0 s ← **绝对瓶颈** |
| Stage2 投票 | ≈ 12 ms |
| Stage3 反稀疏化 | < 1 ms |
| 水印预载（P2 的 PS 方案，191 KB） | 数十 ms |
| TCP 传输 80 KB 读段 | 视链路而定，约 10~50 ms |

**优化任何一级都没有意义，除非先优化 Stage1。**

## 3b. 只算前三级（LDPC 不上板）时的对比

按 RTL 逐周期推算，SE150、2,048 条 × 2 方向：

| 环节 | FPGA（XC7Z010 @100 MHz） | 占比 | CPU 单核（C） | CPU 8 线程 |
| --- | ---: | ---: | ---: | ---: |
| 水印预载（50 区域 × 957 符号） | ≈ 20 ms | 0.5% | — | — |
| **Stage1 滑窗相关** | **3,970 ms** | **98.5%** | **463 ms** | **119 ms** |
| Stage2 大数投票 | 38 ms（每 bit 3 周期 × 300 bit/条） | 0.9% | ≈ 3 ms | ≈ 3 ms |
| Stage3 反稀疏化 | < 0.5 ms | 0.01% | < 0.5 ms | < 0.5 ms |
| **前三级合计** | **≈ 4,030 ms** | | **≈ 467 ms** | **≈ 123 ms** |

**结论：把 LDPC 排除在外，不但没让 FPGA 的优势变大，反而变小了。**

原因很直白：LDPC 是一项**两边都要付**的固定开销（约 160 ms，其中大半还是进程启动）。
把它算进来时，它稀释了两边的比值；把它拿掉，比值反而更极端：

| 口径 | FPGA 路径 | 纯 CPU 路径（单核） | FPGA 慢多少 |
| --- | ---: | ---: | ---: |
| 含 LDPC | 4.19 s | 0.63 s | 6.6× |
| **仅前三级** | **4.03 s** | **0.47 s** | **8.6×** |

而且「前三级」实际上就等于「Stage1」——Stage2 + Stage3 加起来占 FPGA 侧不到 1%，
在 CPU 侧也只有几毫秒。**任何关于前三级的性能讨论，本质上都只是关于 Stage1 的讨论。**

### 要让 FPGA 在前三级上追平 CPU，需要什么

| 目标 | 需要的提升 | 可行路径 |
| --- | ---: | --- |
| 追平 1 个 CPU 核 | 8.6× | BATCH 64→256（4×）+ 时钟 100→200 MHz（2×）＝ 8×，需 XC7Z020 |
| 追平 8 线程 CPU | 25× | 必须做第 4 节的组合展开改造（理论 150×） |

### 能耗对比（前三级）

| 方案 | 耗时 | 功率（估） | 单次任务能耗 |
| --- | ---: | ---: | ---: |
| XC7Z010 当前 RTL | 4.03 s | ≈ 2.5 W | ≈ 10 J |
| CPU 单核 | 0.47 s | ≈ 20 W | ≈ 9.4 J |
| CPU 8 线程 | 0.12 s | ≈ 45 W | ≈ 5.4 J |
| **XC7Z020 + 组合展开改造** | **≈ 0.027 s** | ≈ 3.5 W | **≈ 0.09 J** |

**当前设计连能效都不占优**（10 J vs 5.4 J）；但改造之后能耗降到 1/60，
这才是 FPGA 该有的样子。功率数字为估算，未上板实测。

### 一个和速度无关、但可能更重要的优势

前三级把数据**压缩了三个数量级**：

```
SE150 完整 FASTQ  19,079,454 B  ──前三级──►  8,100 B      （2,355 : 1）
```

如果板子直接接在测序仪后面在线消化数据，主机只需要接收 8 KB 而不是 19 MB。
**这是「读出装置」这个产品形态的真正价值，和快多少倍无关。**
（注意：当前架构是主机把读段发给板子，数据缩减的收益被上行传输抵消了——
要兑现这个优势，数据源必须直连板子。）

## 4. 为什么慢：并行度用错了维度

对比同一算法的两种实现：

| | 每周期完成的碱基比对数 | 时钟 | 等效吞吐 |
| --- | ---: | ---: | ---: |
| XC7Z010 当前 RTL | 64（64 条读段 × 1 个碱基） | 100 MHz | 6.4 G/s |
| CPU 单核（popcount） | ≈ 14（1 条读段 × 64 碱基/指令，含开销） | ≈ 4 GHz | 56 G/s |

FPGA 每周期确实比 CPU 强 4.4 倍，但 CPU 的时钟高 40 倍，净胜 9 倍。

**根因**：当前设计在「读段」维度并行（BATCH=64），却在「碱基」维度**串行**——
`S_RUN` 用 150 个周期逐个碱基地累加。而这 150 个比对之间毫无依赖，完全可以并行。

### 关键观察：两种「位平面」用法，FPGA 可以同时用

`srpe_batch` **已经在用位平面了**（`plane_lo`/`plane_hi`），但用的是和 CPU **正交的方向**：

| | 一个「字」里装什么 | 每周期完成 |
| --- | --- | --- |
| 当前 FPGA | `plane[i]` 的 64 bit = **64 条读段**在第 i 个碱基上的值 | 64 条 × **1** 个碱基 |
| CPU popcount | 一个 uint64 = **64 个连续碱基**（同一条读段） | **1** 条 × 64 个碱基 |

CPU 受限于 64 位字宽，只能二选一。**FPGA 的比较器宽度是任意的，可以两个维度一起吃：**

```
每周期完成 64 条读段 × 150 个碱基 = 9,600 次碱基比对 = 一个位置一次算完
```

### 具体架构

```
                 ┌─────────────────────────────────────┐
  水印 BRAM ──►  │ 150 级移位链（2 bit/级，共 300 FF） │ 每周期左移 1 = 位置 +1
                 └──┬──────────────────────────────────┘
                    │ 300 bit 水印窗口（组合广播）
        ┌───────────┼───────────┬──────────────┐
        ▼           ▼           ▼              ▼
   ┌────────┐  ┌────────┐  ┌────────┐    ┌────────┐
   │ read 0 │  │ read 1 │  │ read 2 │ …  │ read63 │   每条 300 bit 寄存
   │ 150 个 │  │        │  │        │    │        │   match = ~(h^wh)&~(l^wl)
   │ 比较器 │  │        │  │        │    │        │
   └───┬────┘  └───┬────┘  └───┬────┘    └───┬────┘
       ▼           ▼           ▼             ▼
   150→8 加法树（流水 3~4 级）× 64
       ▼           ▼           ▼             ▼
   与 best_sc[k] 比较并更新（64 组 8-bit 比较器 + 寄存器）
```

**水印不再需要按区域展开**：整条水印顺序流过移位链一次，位置就自然从 0 走到 L−RB。

| 项 | 估算 |
| --- | --- |
| 2-bit 比较器 | 64 × 150 ≈ 9,600 LUT |
| 加法树（150→8 bit，需流水） | 64 × ≈130 ≈ 8,300 LUT |
| best 比较/更新 | 64 × ≈16 ≈ 1,000 LUT |
| 读段寄存 | 64 × 300 = 19,200 FF |
| **合计** | **≈ 19K LUT + 20K FF** |

XC7Z010 只有 17,600 LUT / 35,200 FF——**装不下**；
XC7Z020（53,200 LUT / 106,400 FF）可以，且余量足够再翻一倍 BATCH。

### 预期提速（含装载/输出开销）

| 阶段 | 当前周期数 / 64 条 | 改后 |
| --- | ---: | ---: |
| 装载 64 条（每碱基 2 周期） | 19,264 | 1,280（改成每读段 ~20 周期） |
| **比对** | **6,181,200** | **40,650**（每位置 1 周期） |
| 输出 64 条 | 19,200 | 1,280 |
| 合计 | 6,219,600 | **43,360** |

**提速约 143 倍。** 注意：如果不同时优化装载/输出，它们会变成新瓶颈
（不优化时只有约 78 倍）。

| 方案 | 每条读段（双向） | 2,048 条 | vs CPU 单核 | vs CPU 8 线程 |
| --- | ---: | ---: | --- | --- |
| 当前 XC7Z010 @100 MHz | 1.94 ms | 4.03 s | 慢 8.6× | 慢 33× |
| 改架构 XC7Z020 @100 MHz | 0.0136 ms | 27.8 ms | **快 17×** | **快 4.3×** |
| 同上 @200 MHz | 0.0068 ms | 13.9 ms | **快 33×** | **快 8.6×** |

能耗（前三级，2,048 条）：≈0.097 J，比 8 线程 CPU 的 5.4 J **低 55 倍**。

### 顺带解决三个功能问题

这个改动不只是快，它把几个麻烦事一起消掉了：

| 原问题 | 改后 |
| --- | --- |
| **B1 的 50 区域预载负担**（PS 首版已修复 `reg1` 与展开；仍需 191 KB / 50 次 DMA） | 区域概念消失，水印顺序流过一次即可；PS 直接 DMA 原始 10,125 B，不用展开成 191 KB |
| **G1 水印长度运行时适配**（`NUM_LC/STRIDE/REF_LEN` 三个综合参数互相约束） | 三个参数全部消失，只剩一个「水印符号数」计数器上限——**变成一个纯寄存器** |
| `MUL957()` 把 ×957 写死成移位加，参数化要换乘法器 | 不再需要任何乘法 |

水印 BRAM 也从 `NUM_LC × REF_LEN = 47,850` 个符号降到 `L = 40,500` 个（省 15%）。

### 风险与验证顺序

| 风险 | 应对 |
| --- | --- |
| 150 输入加法树的时序 | 流水 3~4 级；只增时延不减吞吐。先跑综合看余量再定级数 |
| 64 条读段 × 300 bit 必须并行可读，只能用 FF 不能用 BRAM | 19,200 FF，XC7Z020 占 18%，可接受 |
| 装载/输出若不同步优化会成新瓶颈 | 用更宽的 AXIS 或一次写整条读段的寄存器组 |
| 改动面大，可能引入新错误 | **先在仿真里用 P0 的黄金向量逐条比对 `pos`/`score`**，通过后再上板 |

建议把它排在 P2 之后作为独立的「Stage1 v2」，**不要和缺陷修复混在一起做**——
先让当前架构出正确图片（判据明确），再换架构（判据就是"和 v1 结果逐条一致但快 100 倍"）。

## 5. 那 FPGA 的价值到底在哪

对**这个数据集**而言坦率地说：不在速度。整个任务 PC 上 0.35 秒就做完了，
加速一个 0.35 秒的任务没有工程意义。价值只在以下几个方向成立：

| 方向 | 说明 |
| --- | --- |
| **功耗与能效** | XC7Z010 整板约 2~3 W，i5-13500H 满载约 35~45 W。当前设计能效仍落后（因为算力没用出来）；按第 4 节改造后，每焦耳处理的读段数可比 CPU 高 3~10 倍 |
| **嵌入式独立部署** | 测序仪旁边放一块板子就能直接出结果，不需要配一台 PC。这是「读出装置」这个产品形态的核心，而不是算得多快 |
| **确定性时延** | 硬件流水的时延是可算的固定值，不受操作系统调度影响 |
| **规模化** | 真实 DNA 存档按块切分，块与块之间完全独立，是天然可并行负载；能效优势会随规模线性放大 |

**建议的项目定位**：把叙事从「比 CPU 快」改成
「**在 2~3 W 的嵌入式功耗下完成 CPU 需要几十瓦才能做的事，且不依赖主机**」——
这是站得住的，而且和 DNA 存储读出装置的真实使用场景一致。

## 6. 对实施计划的影响

1. **不要为了性能去优化 Stage2/Stage3**——它们合计占不到 0.5%。
2. **`docs/06-implementation-plan.md` P1 的「k-mer 粗定向」方案作废**（第 2 节已证明种子法失效）。
   替代方案：上位机把每条读段的正反两个方向都发给板子，由 Stage1 分别打分，
   Voter 按 `score` 择优/加权（D2 的寄存器已经存在，只是没被使用）。
   读段数翻倍在这里代价很小——总共也只需要约 2,048 条。
3. **P6「LDPC 上板」的优先级应进一步下调**：LDPC 只占总时间的百万分之一量级，
   把它搬进 PL 对系统性能毫无帮助。它的价值只在于「摆脱 Windows EXE、实现全板端闭环」，
   属于产品完整性而非性能。
4. **换板选型建议**：若要让 FPGA 在性能上真正有说服力，需要 XC7Z020 或更大的器件。
   这一条应该并入方向 A 的选型决策，而不是默认沿用 XC7Z010。

## 7. SE250 的额外发现

顺带用 `tools/readout.py` 测了 SE250（64,800 条 × 250 bp）：

| 发送条数 | 参与投票 | 覆盖 | LDPC |
| ---: | ---: | ---: | --- |
| 640 | 622 | 94.9% | ❌ 失败 |
| **800** | **781** | **97.3%** | ✅ **与原图一致** |
| 1,000 | 974 | 98.4% | ✅ |
| 1,200 | 1,169 | 99.6% | ✅ |

**SE250 比 SE150 更省数据**：800 条 × 250 bp = 4.9× 覆盖即可还原，
而 SE150 需要约 2,048 条（双向发送、阈值过滤后 1,967 条参与投票）。
原因是 250 bp 的相关峰信噪比明显更好——正确方向平均 125.6/250（50.2%），
与噪声底的区分度比 150 bp 时更大。

**这对硬件选型是个正面信号**：若未来支持 250 bp 档位，所需读段数和传输量都会下降。
代价是数据通路宽度翻倍（`CODEBITS=500`），必须作为独立综合档位处理
（见 `docs/06-implementation-plan.md` P3）。
