### 2.1 上传转正前的历史整轮墙钟分解（全量档，3 次中位）

本表 3.916 s 上传、8.682 s `t_result` 和 13.272 s 整轮属于矩阵时段旧测量，不是当前绝对值。正式转正包默认 `PIPE_IDLE_FETCH_N=16`，上传实测 **0.40 s**；最新同小时参考 `t_result` 为 **9.33 s**，整轮约 **10.4 s**。派生包 `PIPE_IDLE_SLEEP_US=0` 的 0.19 s 是实验值，保留但不作为当前配置。

### 2.2 旧矩阵样本 8.682 s 的 PL / PS 分解（**推导值**）

`PL 7.77 s (87.8%) + PS 1.08 s (12.2%)`，由 P4/P16 两档实测斜率与 Stage1 模块周期比 3.272× 联立解出。
→ **PS 侧每条记录仅 0.0064 ms；把 PS 侧全部清零也只到 7.77 s。**
→ 自检：RTL 模型 `2550 块/记录 × 176 拍/块 ÷ 64 记录 = 7012 拍/记录`，与实测 7500 拍/记录差 6.5%，
   **说明 Stage1 几乎一直满负荷，没有成片可回收的空闲。**
⚠️ 这是**旧矩阵样本上的推导**（前提："P4 与 P16 只差 Stage1 周期数"），**不是直接测量**；最新同小时参考 `t_result` 为 9.33 s。按该分解比例，当前处理段中 PL 约占 87.8%，不要把 7.77 s 写成当前值。

### 2.3 函数级预算：**PS 侧可归因工作只占 2.1%，固件侧已无可捡**（2026-10-13 实测）

出厂节流 + `-DPROF_ENABLE=1` 的派生包，全量 103616 记录，`[PIPE]` 总计 9238 ms：

| 项 | 调用数 | 耗时 | 占比 |
| --- | ---: | ---: | ---: |
| `submit_bd_transfer` | 3,676 | 63.2 ms | 0.7% |
| `reclaim_some_bd` | 80,422 | 38.6 ms | 0.4% |
| `Xil_DCacheFlushRange`（含逐 BD 描述符 flush） | 105,307 | 43.4 ms | 0.5% |
| `Xil_DCacheInvalidateRange` | 29 | 14.5 ms | 0.2% |
| `TX_STREAM` 四段 helper 合计 | 40,126 次进入 | 175.0 ms | 1.9% |
| `xemacif_input` | 42,566 | 7.7 ms | 0.1% |
| `send_result` | 1 | 17.2 ms | 0.2% |
| WM 展开 + 预载 + 结果打包 | — | 9.0 ms | 0.1% |
| **PS 侧可归因合计** | | **≈194 ms** | **≈2.1%** |

`[in-state]` 694 ms（7.5%），`[waiting]` **8543 ms（92.5%）**——其中 `42,602 × 200 µs = 8520 ms` 是**主动休眠**。

**由此关闭的旧推测（不要再照它们定方向）**：
- ~~「Cache 维护 396 ms」~~ → 实测 flush + invalidate 合计 **58 ms**，不成立；
- ~~「逐 BD cache flush 是瓶颈」~~ → 含 BD flush 共 **43.4 ms**，不成立；
- ~~「BD 提交/回收开销大」~~ → 合计 **102 ms**，不值得动；
- ~~「lwIP 收包是瓶颈」~~ → **7.7 ms**，可忽略。

**⚠️ 口径陷阱（务必记住）**：**无睡眠下的 PROF 数字不能用于预算**。
同一固件 `PIPE_RUN_SLEEP_US=0` 时 `reclaim` 被调 **9,309,600 次、计 4230.8 ms**——那是主循环空转 100 倍速带来的**空转载荷**，
不是工作量。**函数级预算一律在出厂配置下测**；无睡眠只用于状态级对比。

### 2.5 已证伪 / 已归档，**不要再走**

1. **「lwIP poll 空等 2,777 ms」** —— 那是 **P12 之前**的固件（P7 评测于 2026-09-11）。当前 `sw/app/main.c` 已是 P12-B 事件驱动。
2. **「删掉 `PIPE_RUN_SLEEP_US=200` 节流」** —— 2026-10-13 已做完整 A/B：三档 200/50/0 的斜率
   `0.079086 / 0.078348 / 0.079057 ms/记录`，**差异 <1%，端到端一点没快**；时间只是从 `[waiting]` 搬进 `[in-state]`。
   `docs/03` P13「不能盲删 200us 节流」已获实测支持。
3. **TX_STREAM 压缩** —— 归档记录里**已尝试四次并放弃**：真正约束是硬件处理每帧的墙钟时间，
   原设计是**时间节拍器**而非容量节流器。**不要再从 BD 环容量下手。**
4. **Voter/Decoder 微架构流水线化** —— 板上周期实测：Stage2 644.9 ms、Stage3 0.022 ms，即使归零，端到端提速 <1%。
5. **P32/P64（加 `P_WAYS`）** —— 外推整机 58.7k / 108k LUT，**均超 XC7Z020 的 53.2k**，不是候选。
6. **精确种子索引** —— 实测最佳位置最长连续匹配仅 5~7 nt，16-mer 命中概率 ≈1.5e-05，**在本任务不可用**。
7. **流式阶段批量推进** —— 两次失败（`submitted=640 > ring free=512`，Stage1 停顿约 30 s 直接 FAIL）。

### C. PL 侧（**唯一能达标的方向**）

**子 Agent 一律走 codex-luna MCP**（`codex_run` / `codex_status`），固定 `gpt-6-luna` + `max`，**不降级**。
成功判据四项全中：`status=completed`、`ok=true`、`exit_code=0`、`turn_completed=true`。

- **⚠️ 子 Agent 在 codex 沙箱内不要运行 `tools/verify_repo_binding.sh`**（沙箱把 git 目录挂成只读，必然失败白跑）。

**Git（最高优先级门禁）**：唯一 Git 写入者是 **main**。禁止 `git add -A` / `git add .`；

## 6. 验收

一条优化只有在**全部**满足时才算成立：

1. 唯一判据 SHA **逐位不变**（`run_g3.sh` 全量档，`--strict-artifacts`）；
2. 有**同输入、同板、同天**的前后对照（≥3 次，报中位数与离散，不只报最好一次）；
3. **能失败的判据**事先写下，且改坏时确实会红（必要时做一次故障注入自证）；
4. 四档以上规模都测（小档不被固定开销淹没，大档不掩盖真实斜率）；
5. 结论与边界写进 `docs/`（03/05/09 + 对应 benchmark），并**登记到 `docs/09-evidence-ledger.md`**；
6. 已冻结的参考包与既有留证**零污染**。
