# 06 · 实施计划

面向的三个既定目标：

- **G1** 水印长度运行时自动适配，不再把任何历史常量当协议；
- **G2** 读段数由上位机决定并显式下发，板端校验后按本次任务运行；
- **G3** 移除「用已知正确结果出图」的旁路，改为 `真实 FPGA 回传 → LDPC → 图片`。

外加两个方向性目标：**A** 换 XC7Z010 板卡，**B** LDPC 上板做第 4 个 IP。

计划的组织原则：**每个阶段结束时都有一个可运行、可回归、比上一阶段更接近目标的系统**，
且每一步的判据都是「与黄金向量逐位比对」而不是「看起来对」。

## P1 · 生产链路软件闭环（3 人日）

目标：让 `clients/python/first.py` 这条**真实生产路径**具备反向互补能力，
使得「只要板子做对了，就能出正确图片」在软件侧不再有缺口。

### 关键设计决策：反向互补在哪里做

> ⚠️ **先排除一个看似聪明的错误方案。** 曾考虑让上位机用 k-mer 种子快速定向，
> 但这在本任务中**根本不成立**：接收端只有水印，而读段是 `水印 ⊕ 稀疏数据` 的含噪副本，
> 两者只有约 50% 的碱基相同。实测读段与水印的**最长连续精确匹配只有 5~7 nt**
> （`docs/07-performance.md` 第 2 节），16-mer 精确命中概率约 1.5e-5。
> **所有基于精确种子的方法都失效**，定向只能通过相关运算得到。

| 方案 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A. 上位机 k-mer 定向 | 种子命中数判方向 | —— | ❌ **不成立**，见上 |
| **B. 双向都发 + 板端按分数取舍** | 每条读段发正反两份，Stage1 各打一次分，Voter 丢弃低分条目 | 读段数 ×2；Voter 加约 10 行 | ✅ **推荐** |
| C. PL 内双向比对 | `srpe_batch` 内部算两个方向 | 省一半传输，但 RTL 改动大 | 后续优化项 |

**选 B 的理由**：定向本来就需要相关运算，那就交给本来就在做相关运算的 Stage1；
上位机零算法负担。读段数翻倍在这里几乎无代价——**总共也只需要约 2,048 条**。

### 分数阈值已实测标定

对 400 条读段分别比对正反两个方向（分数满分 150）：

| | 中位 | 5%/95% 分位 | 极值 |
| --- | ---: | ---: | ---: |
| 正确方向 | 75 | 69 | 最小 61 |
| 错误方向 | 60 | 64 | 最大 68 |

| 阈值 | 保留正确方向 | 误留错误方向 |
| ---: | ---: | ---: |
| 64 | 99.3% | 5.5% |
| **68** | **97.3%** | **0.3%** |

**取 `SCORE_MIN = 68`（≈ 0.45 × READ_BPS）**，分离得很干净，
不需要"配对同一条读段的两个方向"这种复杂逻辑，一个简单阈值就够。

### 位序统一决策（影响 P1 和 P2，越早定越好）

现状是三种位序混用（`docs/02-data-contract.md` 第 6 节）。**建议统一为：**

> 所有比特流一律按「码流顺序 + 字节内 LSB-first」打包。

这样 AXIS 上 `in_buf[k]` 正好等于码流第 k 位，**RTL 端零转换**；
PS 做水印差分时可以直接逐字节 XOR。代价只是 `first.py` 改一行打包方式。
反过来在 RTL 里做位反转要多一层组合逻辑，且极易出错。

⚠️ 改完必须同步更新 `docs/02-data-contract.md` 第 6 节，并重新生成黄金向量。

### 2.1 ~~修水印预载（B1）~~ ✅ PS 首版已实现，待 AXIS/上板验证

实现现状：`sw/app/wm_expand.h` 与 `expand_watermark_regions()` 已按本节方案展开 50 个区域；
`PIPE_WM_TX` 对每个区域写 `reg1`、置 preload 并 DMA 957 个 32-bit 符号。
`bash tools/run_sim.sh host` 已用 47,850 个黄金符号验证展开结果。尚缺 DNA 顶层 AXIS 级
验证或上板 ILA，不能据此断言 BRAM 已按预期写入。

**推荐做法（阶段一：不动 RTL）**

```
PS 侧：
  1. 把主机送来的 81,000 bit 位平面水印解成 40,500 个符号
     symbol[i] = (wm_bit[i] << 1) | wm_bit[L + i]
  2. 展开成 50 个区域（区域 lc 覆盖符号 [lc*807, lc*807+957)），
     写入新的 DDR 展开缓冲区，每符号占一个 32-bit 字（低 2 位有效）
     容量 = 50 × 957 × 4 = 191,400 B
  3. for lc in 0..49:
         写 reg1 = lc
         写 reg0 = PRELOAD
         DMA 该区域的 957 个字（3,828 B）
         等 DMA 完成
     写 reg0 = 0
```

同时修：
- `MAX_WATERMARK_SIZE` 从 10,120 改到 **10,240**（≥ 81,000 bit 的 10,125 B，且 8 对齐）；
- 去掉 `echo.c:1570` 的静默截断，改为回 `PKT_ERROR` + 错误码；
- DDR 布局增加水印展开区（见下方「DDR 重新布局」）。

**后续优化（阶段二：改 RTL）**：让预载一拍解 16 个符号、由硬件按 `MUL957` 自行展开区域，
把 191 KB 传输降到 10 KB。**但不要在首次闭环前做**——先用零 RTL 改动的方案把链路打通。

**判据**：加一个 debug 通路（或用 ILA）回读水印 BRAM 前后各若干符号，
与 `watermark_regions.bin` 逐符号相同。

### ~~2.4 修反稀疏化（B5 + B6）~~ ✅ 已完成（2026-08-07），并顺带重写了控制层解决 B7/B8/B9

**B5 取反标志位置错**（一行修复）：

```verilog
// 契约：每组 5 bit 按码流顺序 b0..b4，输出 = b1^b0, b2^b0, b3^b0, b4^b0
// grp[i] = b_i，输出 r[k] 按 LSB-first 送出
- if (grp[4]) r[k] = ~grp[3:0]; else r[k] = grp[3:0];
+ r[k] = grp[4:1] ^ {4{grp[0]}};
```

**B6 输入缓冲拍序与同周期覆盖**：

```verilog
- in_pool <= {in_pool[63:0], M00_AXI_RDATA};        // 新拍压到低位，旧残留被顶到高位
+ in_pool <= in_pool | ({64'd0, M00_AXI_RDATA} << in_bits);
```

并把「接收」与「消费」合并进**同一个组合分支**再统一寄存，消除两条非阻塞赋值互相覆盖
（现状是同周期到达的一拍被直接丢弃、`in_bits` 记账错）。
背压已有（`RREADY` 含 `in_bits <= 64`），`in_pool` 128 位不会溢出：
最坏 128 → 消费 40 → 88，此时 `RREADY` 为 0，不会再进新拍。

**判据**：喂 `stage2_expect.bin`（稀疏流），输出与 `stage3_expect.bin` /
`codeword_R083.txt` 逐位相同。

### ~~2.7 DDR 重新布局~~ ✅ 已完成（2026-08-16，`sw/app/ddr_layout.h` + 主机单测）

| 区间 | 用途 | 大小（按 N 条读段、L 个水印符号） |

## P3 · 任务配置化（8~12 人日）→ **G1 + G2 达成**

**必须排在 P2 之后**：在一条未验证的链路上做参数化只会让问题更难定位。

### 3.1 协议扩展：`PKT_CONFIG`（0x05）

在 `PKT_WM` 之前发送，板端校验通过才允许后续包。字段全部大端：

| 偏移 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | u16 | `config_version` | 从 1 开始，不兼容变更即 +1 |
| 2 | u8 | `watermark_format` | 0=打包位流，1=32-bit 值序列 |
| 3 | u8 | `bit_order` | 0=LSB-first（本计划统一值） |
| 4 | u32 | `watermark_bits` | 有效逻辑位数 L×2 |
| 8 | u32 | `read_bases` | READ_BPS |
| 12 | u32 | `read_count` | 本次实际发送条数 |
| 16 | u32 | `num_lc` / `stride` / `ref_len` | 三个 u32，滑窗几何 |
| 28 | u32 | `stage1_bytes_per_read` | 冗余校验 |
| 32 | u32 | `stage2_bits` / `stage3_bits` | 两个 u32 |
| 40 | u32 | `crc32` | 覆盖前 40 字节 |

板端校验（任一不满足即回 `PKT_ERROR` + 具体错误码，**绝不静默截断**）：

```
ref_len       == stride + read_bases
watermark_bits== 2 * (num_lc * stride + read_bases)
num_lc  <= NUM_LC_MAX  且  ref_len <= REF_LEN_MAX     （综合上限，只读寄存器可查询）
read_bases ∈ 已综合档位集合
read_count % 64 == 0  且  read_count <= MAX_READS
stage3_bits == stage2_bits * 4 / 5
DDR 布局计算后各区间不重叠、不越界
```

再加一个 `PKT_CAPS`（0x06）让上位机**查询板端能力**（最大水印长度、支持的 read_bases 档位、
最大读段数、综合时的 BRAM 上限），这样"支持范围"是可发现的而不是靠文档口口相传。

### 3.2 PL 参数寄存器化

| 参数 | 能否运行时可变 | 说明 |
| --- | --- | --- |
| `NUM_LC` / `STRIDE` / `REF_LEN` | ✅ 可以 | 改成寄存器；注意 `MUL957()` 是把 ×957 写死成移位加的，必须换成通用乘法器（XC7Z010 有 80 个 DSP48，够用）；BRAM 按 `NUM_LC_MAX × REF_LEN_MAX` 综合 |
| `TOTAL_BITS` / `LAYER_SIZE`（Voter） | ✅ 可以 | 已是 parameter，改寄存器；BRAM 按最大值综合 |
| `READ_BPS` / `CODEBITS` | ❌ 不能 | 决定数据通路宽度、位平面 BRAM 深度、结果打包宽度 |

**`READ_BPS` 的务实做法**：综合时支持一组**离散档位**（先做 150，再评估 250），
运行时由 `PKT_CONFIG` 选择档位；不支持的档位明确报错。
`PKT_CAPS` 里公开档位列表。这就是"自动适配"的诚实定义——
适配的是**主机提交且已校验的本次任务配置**，而不是任意长度。

### 3.3 上位机

- 解析水印文件时自动判定格式（文本 bit / 32-bit 值），报告有效位数、字节数；
- 由 L 和 READ_BPS **自动求解** `num_lc/stride/ref_len`：
  取 `M = L - READ_BPS`，在板端上限内挑一组 `num_lc × stride = M` 的因数分解
  （优先让 `ref_len` 不超上限、`num_lc` 尽量小以省 BRAM）；无解时明确报错并给出建议；
- 读段数：检测总条数 → 用户可指定 → 向上取整到 64 的倍数 → 不足补零并在日志中标注；
- 把最终配置打印成一份可存档的任务描述（JSON），随结果一起保存，便于复现。

### 3.4 验收判据

- 同一比特流下，用**两种不同水印长度**（如完整 81,000 bit 与截短后的合法配置）
  各跑一次，都能得到与各自黄金模型一致的结果；
- 超限任务（水印过长、read_bases 不支持、read_count 非 64 倍数）返回**可诊断的错误码**，
  且板端状态可继续接受下一个任务，不需要重启；
- `PKT_CAPS` 报告的能力与实际综合参数一致（加一个自动比对测试）。

## P7 · Stage1 架构改造（10~15 人日，需 XC7Z020 或更大器件）

把「每周期 64 条读段 × 1 个碱基」改成「每周期 64 条 × 150 个碱基」——
即在保留现有读段并行的同时，再吃下碱基维度的并行。完整设计、资源估算、
预期提速和风险见 **`docs/07-performance.md` 第 4 节**。

要点：

- 预期提速 **约 143 倍**（若不同时优化装载/输出则只有 78 倍）；
- 改后 @200 MHz 比 8 线程 CPU **快 8.6 倍**，能耗低 55 倍；
- **顺带消掉 B1 和 G1 的大半难度**：区域展开概念消失，
  `NUM_LC/STRIDE/REF_LEN` 三个互相约束的综合参数退化成一个寄存器；
- 资源约 19K LUT + 20K FF，**XC7Z010 装不下**，需 XC7Z020 起步。

**排期建议**：放在 P2 之后作为独立里程碑，不要和缺陷修复混做。
P2 的判据是"出正确图片"，P7 的判据是"与 v1 结果逐条一致但快 100 倍"，两者互不干扰。
