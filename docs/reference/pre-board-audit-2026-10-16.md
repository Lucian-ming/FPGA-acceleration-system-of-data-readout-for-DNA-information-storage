## 3. 🔴 P0 —— 不关掉就会"白跑"或"结论不成立"

### P0-1：**板上没有任何可读回的 v1.1 构建身份**（最重要）

- `tools/board/g3_caps.py` **自己写着**：*「CAPS 不含 P_WAYS/PIPE_TREE，TCP 层无法区分板上运行的是
  P4 还是 P16」*；CAPS 只回几何/容量/功能位，**没有固件版本、没有 bit 身份、没有源码标识**。
- `tools/board/g3_boot.tcl.in` 烧录后**只检查 XSDB 输出的 `BOOT> running`**，不读回任何标识。
- `run_g3.sh` 的 `--skip-boot` **硬编码可用**；`g3_soak.py` **每轮都 `--skip-boot`，从不烧录**。
- 严格制品门禁**也拦不住**：对**完整的 v1.0 包**跑同一门禁返回 **exit=0**（错传 `xc7z010` 才返回 2）。

⇒ **后果**：板子现在跑的是 SD 卡上的 **v1.0**。若某一步没真烧录（或烧错包），
**CAPS 看起来一模一样**，我们**分辨不出来**，"v1.1 通过 G3"就无从归属。

**三个可选处置**（**需要你拍板**）：

| 方案 | 成本 | 效果 |
| --- | --- | --- |
| **(a) 在固件 CAPS 里加一个构建 ID**，G3 与长稳每轮核对 | 改 `sw/app` + 主机解析 → **只需重建软件包**（bit 不用重跑 Vivado） | **根治**。但 CAPS 是协议字段，要同步改 `protocol.py`/`g3_wait_ready.py` |
| **(b) 每轮强制真烧录**（去掉 `--skip-boot`），并把烧录日志与所用文件哈希写进留证 | 无代码改动；每轮多几十秒 | 大幅缩小风险，但**仍不能证明** PL 真接受了那份 bit |
| **(c) 只用 `--skip-boot` 但人工确认** | 0 | **最弱**，靠人记性 |

### P0-2：v2 的 42 例脚本**默认指向旧包，且会覆盖 v1.0 的留证**

- `logs/g3/c2-v2-67/run_all_67.sh` 的默认制品 `...stage3poll-20261016T000308Z-board-migrate`
  **当前不存在**（`P0`）。
- 默认 `OUT=logs/g3/c2-v2-67`，而**该目录就是 v1.0 那 42 例的留证目录**；脚本会**截断 `SUMMARY.tsv`
  并用 `>` 覆盖每例 `.out`**（`P0`）。⇒ 照默认跑，**上一次的对照数据没了**。

### P0-3：42 例脚本**失败不报**

- 不检查 `run_g3.sh` 的退出码；首例之后**无条件** `BOOTED=1`（即使首例没烧成功，后面全 `--skip-boot`）；
  结尾一律打印 `FULL SWEEP DONE`，**没有聚合退出码**（缺失/`OTHER`/危险项都不影响退出码）。

⇒ **P0-2 与 P0-3 已在修**（`pre-flight-hardening` Agent：默认即报错、拒绝覆盖、
检查每例 rc、只有真烧录成功才置 `BOOTED`、聚合退出码、记录制品身份）。

## 4. P1 —— 会浪费一整轮，或让结果不可归属

### 4.1 长稳（8 h）相关

- 🔴 **`g3_soak.py` 的 `--hw-server` 默认空**；而走 WSL 侧 XSDB 时 `run_g3.sh` **强制要求它**，
  不传就 `FATAL`、**每轮 rc=2**。脚本自己的注释就写着"长稳会整轮整轮地空跑"。
  ⇒ **上板命令必须显式传** `--xsdb /tools/Xilinx/Vitis/2022.2/bin/xsdb --hw-server TCP:127.0.0.1:3132
  --uart-port <按 bInterfaceNumber=02 查到的 /dev/ttyUSBn> --win-root <WSL 可写目录>`（脚本三个默认值全是 **Windows 侧**的）。`/dev/ttyUSBn` 名称随 USB 枚举漂移；上板前用 `cat /sys/class/tty/ttyUSB<n>/device/../bInterfaceNumber` 找到值为 `02` 的通道 C，并将当次实际路径显式传入。
  **已在修成失败关闭**（WSL xsdb + 空 hw-server ⇒ 启动即报错）。
- **遇到确定失败不停**：循环到墙钟期限。配置错/连不上/注入未执行都会**白耗满 8 小时**。
  **已在修**（连续 N 轮失败即止损，并如实标注"提前停止"，不伪装跑满）。
- **`--out-dir` 复用会追加旧 TSV**，旧行缺 `process_rc`（Q7 之后）会被判 `unverified` ⇒ 最终 FAIL。
  ⇒ **必须用全新目录**。**已在修**（非空目录拒绝启动）。
- **墙钟阈值是 `hours*3600*0.98`**（8 h 约 **7 h50m** 即算达标）。这属于既有判据，
  **我没有擅自改**——已让 Agent 只把实际墙钟与目标差**打进 summary**，是否收紧**留给你定**。

### 4.2 其他

- **SD 冷启动必须重做**：卡上现在是 **v1.0 的 `BOOT.bin`（`69a33763…`）**，
  v1.1 的是 `14d4b2d5…`。照现状断电重上，**测到的还是 v1.0**。
- **QSPI "从未写入"没有原始依据**：该说法只出现在 SD 报告里、标为"项目记录"，
  **没有 QSPI 写入审计或读回证据**。若 BOOT_CFG 实际选中 QSPI，可能启动旧镜像。
- **多轮"弄脏轮"模式有问题**：注释说弄脏轮的系统 SHA "仅记录"，但自动长度路径仍把 `--expect-sha`
  传给每轮 `first.py`，合法但不同的载荷会在**仲裁处失败**；`SYSTEM_STATUS` 分支也**没检查 `RUN_KIND`**。
  ⇒ **只在 `--runs > 1` 时触发**；G3 默认 `--runs 1`，长稳每轮也是一次，**本次不受影响**，
  但**不要**用多轮弄脏配置做结论。
- **42 例的 `match` 列在架构失败时会误读**：架构 FAIL 时 judge 报告里的"系统 SHA"可能来自
  **PC 诊断译码**，而 `run_all_67.sh` 不看来源，可能记成 `match=YES`。
  ⇒ 看 `verdict` 列，别只看 `match`。

## 5. P2 —— 精度、清洁度、与"数字从哪来"

1. 🔴 **"0 例静默给出错误字节"要写准**：16 个失败例**确实回了数据**
   （`Result: 8100 bytes`），是客户端在 syndrome 非零后**拒绝输出通过校验的载荷**。
   准确表述是「**0 例"架构判据通过但系统 SHA 不符"**」，不是"失败时板端没吐字节"。
2. **本波的一个数字我曾经写错并已更正**：v1.0 与 v1.1 的 `source_manifest` 差异，
   真值是**共有路径中 31 项哈希不同（30 项真实源码 + 1 项 `.pyc`），另有 1 项仅 v1.0 有、
   3 项仅 v1.1 有（都是新 `.pyc`）**，不是此前文档/提交信息里的"26 项"。
3. 🔴 **`source_manifest.json` 混进了 `__pycache__/*.pyc`**（v1.1 有 **11 项**、v1.0 有 8 项）：
   `.pyc` 不是源码，且 `__pycache__/` **被 gitignore** ⇒ **干净 clone 上不存在** ⇒
   这份清单**在别的机器上校验不过**，可复现性被破坏。**对本次板测无影响**（bit/ELF 来自真实源码）。
   **已在修**（`write_source_manifest.py` 排除 `__pycache__`；已构建的包不动）。
4. **原始留证不在 Git 里**：26/16/0 与 8 h 的**逐例/逐轮原始日志命中 `.gitignore:41`**。
   本机可读，但提交材料若只留文档摘要，审阅者**无法复核逐例**。⇒ 应另存不可变归档 + 校验和。
5. **v2 输入来自外置盘且不校验**：`run_all_67.sh` 直接从 `/mnt/e/...` 读 FASTQ 与 `encoding.json`，
   **开跑前不核对数据集 `SHA256SUMS`**。⇒ 应逐例校验并留存清单哈希。
6. **新行为的主机测试覆盖不足**：`tests/host/test_echo_pure.c:53` 把 reserved 设成 `0xFF` 后
   **不检查返回值** ⇒ **reserved 非零拒绝没有主机判据覆盖**。
   `g3_recovery_probe.py` 的 `0xBB` 出现在**magic 也错**的垃圾包里 ⇒ 也**不能**据此说
   "reserved 拒绝已在板上验证"。
7. **`component.xml` 的那处删除**（`bd_tcl` view + 空 fileset）：审核 Agent 因"只许注释"的硬约束
   把它标成高优先级待核。**我判定可以降级**——**v1.1 的整机构建发生在该改动之后并成功**，
   且其 `util.rpt` 与 v1.0 逐行相同 ⇒ 该改动**已被构建结果覆盖**。它只是 Vivado 打包残留的展示元数据。
