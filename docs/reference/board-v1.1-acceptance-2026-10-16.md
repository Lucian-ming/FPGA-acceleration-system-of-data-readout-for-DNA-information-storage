⇒ **比历史那次更强的结论**：2026-10-16 上午那次 SD 冷启动只能靠"拨码 + QSPI 从未写入 +
无 JTAG 写操作"**推断**"从 SD 启动"；这次**多了两条直接证据**：

### 4.1 "从 SD 启动"的**直接证据**（芯片锁存的启动模式）

**不靠串口**——直接读 Zynq 的 **`SLCR.BOOT_MODE`（`0xF800025C`）**，它是 **BootROM 上电时
锁存的启动模式**，之后任何时刻可读，不受 USB 枚举/采集时机影响：

```text
BOOT_MODE (0xF800025C) = 0x00000005      ⇒ bits[3:0] = 5 = SD 卡

```

**编码依据**（不是我自己记的）：项目**自己现场实测过** `BOOT_MODE = 0` ⇒ **JTAG 启动模式**
（`docs/03-status.md` §1）；且 **Vitis 为 Zynq 平台生成的 `qemu_args.txt`** 里就是
`loader,addr=0xF800025C,data=0x00000005`（把启动模式设成 SD 来仿真 SD 启动）。
⇒ `0=JTAG`、`5=SD` 两头对得上。

**加上同期读回的身份**：

```text
XSDB 从板上读回 fw_build_id = db5705fb4d0bc003   （== 本包）

```

**证据链闭环**：① `BOOT_MODE` 锁存为 **SD**；② 板上运行的固件身份 **== v1.1 本包**；
③ **QSPI 从未写入**（记录在案，且本次明确不做）；④ 本次**全程无 JTAG 写操作**（`--skip-boot`）
⇒ **正在跑的那份 v1.1，只可能来自 SD 卡。**

⚠️ **边界**：`BOOT_MODE` 反映的是**锁存的启动器件选择**（strap），它证明"BootROM 被要求从 SD 启动"；
"加载**成功**"这一环是靠 ②③④ 合起来支撑的。这与"直接读到 FSBL 的启动打印"仍不是同一级——
详见 §4.2。**两条证据是互补的，不是替代关系。**

### 4.2 FSBL 串口日志：**五次尝试后判定"这条路抓不到"**（结构性原因）

**没有抓到 FSBL/BootROM 的串口打印。** 原因是**结构性的、不是操作失误**：

- **板子一断电，FT4232H（在板上）就从 USB 整个消失**；一上电又**重新枚举**
  ⇒ `usbipd` 的 attach 掉、`/dev/ttyUSB*` 全没、随后回来时**设备名还会变**。

- ⇒ **"提前挂好采集等上电"这个做法本身不成立**：采集读的是一个即将被销毁的设备节点。
  本次改用"**等设备消失→等它重现→重现瞬间 attach+chmod+采集**"的 watcher，
  但**用户连续断电两次**，第二次把第一次刚建立的采集打断了。

四次尝试的过程与每次的根因：

| 次 | 现象 | 根因 |
| --- | --- | --- |
| 1 | 0 字节 | 采集在上电前挂好，但设备随断电消失 |
| 2 | 0 字节 | 同上；且用户随后又断了第二次 |
| 3 | `PermissionError: Permission denied` | **我的 bug**：watcher 里写的是 `chmod` 而**漏了 `sudo`**（设备是 `root:plugdev` 的 `crw-rw----`） |
| 4 | 权限已对（`crw-rw-rw-`）、采集已建立 | 用户**第二次**断电把刚建立的采集打断 |
| 5 | 抓到 125 字节，**但只有 lwIP/EMAC 的网络打印** | **枚举+attach 耗时 > 启动输出耗时**（结构性，见下） |

**第 5 次是最接近成功的一次，恰好错过了要找的东西**：

```text
autonegotiation complete
link speed for phy address 1: 1000
unable to determine type of EMAC with baseaddress 0xE000B000

```

这三行来自 lwIP/EMAC 网络初始化。而 `main()` 的实际顺序是
`init_platform()` → … → **`print_app_header()`（横幅 + `[FW] build=`）** → `lwip_init()` → 网络配置
⇒ **抓到的窗口落在横幅之后**：横幅、`[FW] build=`、FSBL、BootROM **全在窗口之前**。

**时间线（watcher 日志实测）**：`23:04:09 设备从 WSL 消失` → `23:04:14 设备重现、采集建立`。
而 BootROM + FSBL + 应用横幅**全部挤在板子上电后那 1–2 秒内**。

⇒ **结构性原因**：UART 桥（FT4232H）挂在**板子上**，板子一断电它就从 USB 掉、上电才重新枚举；
等 Windows 枚举完成 + `usbipd attach` 到 WSL 完成（数秒），**能读端口时启动输出早已打完**。
**在这条 USB 路径上，抓不到启动序列最前面的部分。**

⇒ **结论：SD 冷启动的"启动序列直接证据"在本项目现有硬件路径下取不到。**
但 §4.1 的 **`BOOT_MODE` 寄存器证据在证据层级上不低于它**——两者都是"芯片自身状态"，
而不是"人眼看终端"。**§4.1 才是本次 SD 冷启动的主要证据，本节只是如实登记一次未成功的取证。**

### 4.3 两条必须记下的操作事实

- ⚠️ **FSBL 启动日志仍然没抓到。** 原因已定位：**板子一上电，板上 FT4232H 就重新枚举**
  ⇒ `usbipd` 从 `Attached` 掉成 **`Shared`**、`/dev/ttyUSB*` **全部消失**
  ⇒ 采集进程还活着，但读的是**已不存在的设备**（日志 0 字节）。
  ⇒ **"从 SD 启动"仍未拿到"直接读到 BootROM/FSBL 输出"这一级的证据**，
  仍属"拨码 + 无 JTAG 写 + QSPI 未写 + 身份读回"的**强推断**。
  **若要有直接证据**：需恢复 USB 通道后**再断电重上一次**，且采集必须在上电前就位。

- ⚠️ **串口号会漂，不能当固定值用**：上电前是 `ttyUSB0/1/2/3`（PS UART = `ttyUSB2`），
  重枚举后变成 **`ttyUSB0/1/3/4`** ⇒ **PS UART 落到了 `ttyUSB3`**。
  正确的定法是按 **FT4232H 的接口号**：**PS UART = interface 02**（`/sys/class/tty/ttyUSBn/device/../bInterfaceNumber`）。
  项目文档里"PS UART = `/dev/ttyUSB2`"**必须改写成"interface 02、设备名随枚举漂移"**。

## 5. 过程中两次失败的根因（操作教训，值得留档）

### 5.1 第一次：`Memory write error at 0x100000. AP transaction timeout`

- **现象**：`dow`（把 ELF 写进 DDR）失败；`jtag targets` 显示
  `DAP (APB AP transaction error, DAP status 0x30000021)`，**没有 Cortex-A9 目标**；
  但**板子在网络上是活的**（CAPS 仍 PASS）。

- **根因**：**陈旧的 `hw_server` / USB 句柄**。`/dev/ttyUSB*` 全部消失、
  `usbipd` 里 FT4232H 从 `Attached` 掉成 `Shared`（设备重新枚举）。

- **修法**（项目记录的恢复三步）：
  `usbipd attach --wsl --busid 6-2` → `sudo chmod 666 /dev/ttyUSB*` →
  **按 PID** 重启 `hw_server`（项目规则：不许 `pkill -f`）。
  修完 `targets` 立刻出现 `ARM Cortex-A9 MPCore #0 (Running)`。**全程不需要动拨码。**

- ⚠️ **这修正了记录里那条模糊描述**（`logs/board/sd-cold-boot-20261016.md` §5.2 说
  "切到 SD 启动后 JTAG 扫描链枚举不出来"）：本次症状不是"链空"，而是
  "**DAP APB abort、PS 够不着**"，根因是**陈旧句柄**而非启动模式。

### 5.2 第二次：`FW_BUILD_ID_ERROR 未知参数: --elf … --hw-server … --nm …`

- **根因**：新写的 `read_fw_build_id.tcl` 里写了 `main $argv`。
  **Tcl 的变量替换不拆词**，整个列表被当作**一个**参数传进去 ⇒ 参数解析必然失败。
  必须写 **`main {*}$argv`**（Tcl 8.5+ 的展开算子）。

- 本地 `tclsh` 最小复现确认：`$argv` 传 1 个、`{*}$argv` 传 6 个。

- ⚠️ **它失败关闭了**（没有假装通过）——这正是加这道核对的目的。

### 5.3 2026-10-17：**SD 启动模式下 JTAG 复位/烧录会与 BootROM 竞态**（新增）

- **现象**：同一份 v1.1-fwid 包，在 SD 启动模式下第一次 `run_g3.sh`（含真烧录）**烧录成功、身份核对 PASS**；
  紧接着第二次执行时，`dow` 报
  `Memory write error at 0x100000. AP transaction timeout`，
  随后**板上网络全断**（`ping` 100% 丢包），JTAG 只剩
  `DAP (APB AP transaction error, DAP status 0x30000021)`、**没有 Cortex-A9 目标**。

- **根因**：`rst -system` 复位 PS 后，**SD 启动模式下 BootROM 立刻从 SD 卡启动**
  （FSBL → PL 配置 → 应用），与 JTAG 随后的 `ps7_init` / `dow` **争用 DDR/AXI**。
  第一次成功、第二次失败，是竞态的时序差异，不是制品问题。

- **处置（两步，实测有效）**：
  1. `targets -set 1; rst -system`
     —— ⚠️ 必须**按目标索引**选 DAP；`targets -set -filter {name =~ "DAP"}`
     **匹配不到**（实际名字带状态后缀），只有 `*Cortex-A9*#0*` 这类通配能匹配。
     执行后链恢复，出现 `ARM Cortex-A9 MPCore #0 (Vector Catch)`。
  2. 对该 A9 目标 `con` —— PS 从 SD 正常启动，**4 秒内 `ping` 通**，CAPS 全字段匹配。

- ⚠️ **结论性约束**：`boot.tcl` 的 `rst -system → fpga → ps7_init → dow` 只能在
  **JTAG 启动模式（`BOOT_MODE=0`）** 下安全使用。**SD 模式下不要做 JTAG 复位或烧录**；
  长稳/回归一律用 `--skip-boot`，让固件由 SD 冷启动提供。

### 5.4 2026-10-17：串口权限 —— `/dev/ttyUSB*` 属 `plugdev`，本账号不在组内（新增）

- **现象**：`OPEN_FAIL PermissionError: [Errno 13] Permission denied: '/dev/ttyUSB2'`，
  G3 在「串口实录」步骤 **FAIL（失败关闭）**，后续 CAPS/四级取证被 SKIP。
- **处置**：`sudo -n chmod 666 /dev/ttyUSB*`。**每次 USB 重新枚举后都要重做**
  （`usbipd attach` 之后节点权限是 `root:plugdev 660`）。
- 仍然按 `bInterfaceNumber=02` 认 PS UART（**通道 C**），不要用固定名字。
