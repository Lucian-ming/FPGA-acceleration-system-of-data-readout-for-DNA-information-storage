## 3. 尚未关闭的问题

### P0 · 板端固定开销实测 5.284 s，待分解到具体阶段（2026-09-10）

**✅ 已测出总量**（`tools/board/g3_overhead_sweep.py`，64~4,096 源读段 7 档 × 3 次，
留证 `logs/overhead_sweep/20260910T075540Z/`，同轮 G3 判据哈希 PASS）：

```text
实测   T = 5.284 s + 0.5157 ms x N_records     R^2 = 0.99644
文档   T = 4.25  s + 0.58   ms x N_records
```

64 条读段（Stage1 工作量约 0.05 s）仍需 5.48 s，且 64/128/256 三档几乎完全平坦；
水印上传 0.010 s + 读段上传 0.022 s + 8,100 B 回传约 0.01 s 合计不到 0.05 s，
**故这 5.2 s 几乎全部是板端固定计算，不是通信**。

**占比（决定该项的真实价值）**：2,048 源读段时占 **71.4%**，全量时仅占 **9.0%**。
因此消除它主要改善**演示与小规模任务延迟**（7.40 s → 约 2.1 s），
**不改写全量性能结论**。

**✅ 根因已定位（2026-09-10）：不是计算，是每步白等一个 lwIP poll 周期。**
用 `tools/board/read_pipe_counters.tcl` 经 XSDB 直接读固件计数器
（256 源读段，`t_result=5.525 s`）：`PIPE_POLL_STEPS=20`、`WM_POLL_STEPS=4`，
即 **5.525 s / 20 步 = 276 ms/步**。
`echo.c::poll_callback` 的 `PROC_RUNNING` 分支每次回调只推进一个流水线状态；
`pipeline.h` 有 17 个 PIPE_* 状态，`PIPE_WM_TX` 按 `WM_REGIONS_PER_POLL=16`
分 4 批，合计约 20 步 × 276 ms = 5.52 s。**其中没有任何一毫秒是真实计算。**
（也解释了文档那个 4.25 s：17 状态 × 250 ms，量纲吻合。）

**⚠️ 已否证的假设**：曾点名「Stage 2.5 的 ARM 软件水印异或」为首要嫌疑，
代码审查否证——`apply_watermark_differential` 只对 10,125 字节做一次 u8 XOR，
量级在毫秒以下。

**⚠️ 过程教训**：`poll_callback` 里**早就有**插桩
`[PIPE] total %u poll steps, %u ms`，注释也写明「固定开销的量纲就是
poll 步数 × 250~500 ms」。但它走 `xil_printf` → UART，而 CH340 串口线未接，
**该信息从未被读到**，导致同一问题被以分档拟合的方式重查一遍。
**留证通道断了等于没有留证**——串口不通时应改用 XSDB 读内存符号。

**✅ 修复已实施并上板验证通过**（commit `a887dc4`，留证 `g3_runs/20260910T113815Z/`）：
`poll_callback` 改为单次回调内批量推进状态机。板级 G3 PASS——图片 SHA-256
`fcd0cf90…f2c3` 逐位相同，四级逐级取证全过。

```text
修复前  T = 5.284 s + 0.5157 ms x N_records    R^2 = 0.99644
修复后  T = 1.505 s + 0.5656 ms x N_records    R^2 = 0.98614
```

固定开销 **5.284 s → 1.505 s（3.5x）**；水印预载约 1.1 s → 2 ms；
2,048 源读段 7.315 s → 4.123 s（1.8x）。
**但斜率升高 9.7%，全量任务基本持平（58.7 s → 60.1 s）**——
本次收益只兑现在小规模/演示任务上，不改写 P1 的性能判决。

**⚠️ 第一版失败的教训（已写进 echo.c 注释与 [17](17-competition-strategy.md) §3.0.3）**：
把流式状态也批量推进会撑爆 BD 环（`submitted=640 > ring free=512`，
Stage1 停顿 ~30 s 直接 FAIL）。**「一次 poll 一步」不只是浪费，它同时是节流机制**；
`stage1_dna.c:178` 的注释早已写明「原实现靠下一个 poll 才回收，天然有 250 ms 余量」。

**❌ 剩余瓶颈已尝试压缩并放弃**（负结果，见 [17](17-competition-strategy.md) §3.0.4）：
用「按 RX ring 余量自适应让出」替代固定节拍，上板 FAIL 且失败数字与 v1 逐字相同
（`ring free=512` 恒满，门限从未触发）。真正约束是**硬件处理每帧的墙钟时间**，
原设计是**时间节拍器**而非容量节流器。按实测模型分解 4,096 记录的 3.82 s：
纯 Stage1 比对 1.93 s(50%)、固定项 1.50 s(39%)、DMA/poll/回传 **0.39 s(10%)**——
**即使全部消掉也只快 1.11x**，不足以匹配风险，故不再投入。
日后若重启，正确的控制变量是**在飞帧数**或 DMA 完成中断，不是 ring 余量。

**⚠️ 已撤回的推断**：此前把文档 4.25 s 的不可信归因于「只用 3 个大点外推、
杠杆臂过长」，该理由**已被实测否证**——只用 N≥4,096 的点重拟合得 5.089 s，
与全档 5.284 s 仅差 0.195 s。文档值与实测值对不上的成因待查，不得再引用「杠杆臂」。

### P0b · 出厂制品与源码不同源（2026-09-10 发现并已关闭）

**问题**：`hw/build/export/dna_lwip_app_b27.elf` 与当前源码**机器码不同源**。
用已提交源码重建，`.text` 差 768 B、`.rodata` 差 196 B——不是注释/行号差异。

**定性证据（符号级）**：出厂 ELF 中 `arp_keepalive` 出现 **0 次**，
而该函数由 `f67228e`「B29/B30 lwIP 单播保活/物理投递结算」引入并在
`sw/app/proto.c:29` 定义、`echo.c` 两处调用。
提交该 ELF 的 `928e156` 在 `f67228e` **之后**，即
**`928e156` 提交了一份陈旧的 ELF，不含源码里已有的 B29/B30 修复**。

**影响**：2026-09-10 之前所有基于 `export/` 的板测（含当日 G3 基线与
修复前的固定开销扫描）跑的都是**不含 B29/B30 的固件**。
这违反 `AGENTS.md`「RTL/固件变化后必须重建整套制品并刷新 SHA256SUMS」，
并触发 [13](13-final-delivery-roadmap.md) §6 终止条件「制品与源码无法证明同源」。

**已关闭**：从当前源码重建 ELF（含 B29/B30 与 P0 修复）→ bootgen 重生成
`BOOT.bin` → 刷新 `SHA256SUMS`（5 项 OK）→ 完整流程 G3 复验：

```text
PASS  制品同源性（hw/build/export/ vs SHA256SUMS）
PASS  图片 SHA-256 = fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3
PASS  四级逐级取证        Result: 8100 bytes, 4.28s
```

**⚠️ 校验方法学**：整文件 SHA-256 **不能**发现这个缺陷——出厂 `SHA256SUMS`
当时是自洽的（文件与自己的哈希相符），它只证明「文件没被改动」，
不证明「文件由该源码构建」。有鉴别力的判据是**符号级比对**
（`arm-none-eabi-nm` 找源码里有、制品里没有的函数）或按
`.text/.data/.rodata` 分段比对重建结果。
`hw/build/export/README.md` 2026-09-04 写的「三段逐字节相同」结论**已失效**。

## 4. 证据纪律

> **对外表述前先查 [18 证据台账](18-evidence-ledger.md)**：它把每条可以说的话与其判据、
> 证据路径、复现命令、边界钉在一起，并单列了一张**「不能说的话」**清单
> （每条都有实测支撑其为假）。本文给结论，台账给复现路径，两者配套使用。

1. 构建、仿真、包装和历史 XSA 都不能代替板端 G3。
2. 最终图片哈希是端到端判据；中间级别必须同时记录适用范围。
3. 修改 RTL/固件后必须重新构建整套制品并刷新 `SHA256SUMS`。
4. 新运行必须生成新的带时间戳留证目录，不得把旧运行 ID 当成新版本证据。
5. 任何“更快/更省电/更通用”的结论必须给出同口径基线、输入哈希、重复次数和失败样本。
