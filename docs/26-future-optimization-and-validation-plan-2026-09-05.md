# 26 · 未来优化与验证实施计划（2026-09-05）

> 本文是 G3/SE250 全量闭环之后的执行计划。目标不是继续堆叠演示轮次，而是把项目从「指定数据集上正确」推进到「可解释的 FPGA 加速、可配置的 DNA 读出、可复现的错误鲁棒性」。
>
> 本文只规划任务，不宣称尚未完成的性能、功耗或通用性结论。`data/R0.83_data/` 为只读基准，禁止覆盖其中任何文件。

## 1. 总目标与成功定义

### 1.1 总目标

形成一套可答辩、可复现、可继续扩展的 DNA 读出平台，包含四条主线：

1. **T：时间优化**：找准端到端瓶颈，降低每条记录耗时；
2. **A：通用参数化读出**：从固定 SE150/SE250 推进到可配置读长、水印和任务参数；
3. **B：错误鲁棒性验证**：建立可控 substitution/insertion/deletion、覆盖度和噪声实验；
4. **H：上位机产品化**：把 FASTQ 检查、参数选择、任务调度、译码、结果和诊断整合为可追溯工具。

### 1.2 不能混用的三个结论

| 结论 | 需要的证据 | 目前状态 |
|---|---|---|
| 功能正确 | 板端返回数据经 LDPC 后与参考图像逐位/逐哈希一致 | SE150/SE250 指定基准已闭环 |
| FPGA 更快 | 同输入、同正确性、同方向数下，与优化 C 单核/多核公平对照 | 尚需系统化基准 |
| 方案更通用 | 多个独立 payload、多个错误模型、多个覆盖度/读长通过 | 尚需建立数据扩展体系 |

**任何阶段不得用功能 PASS 代替性能 PASS，也不得用同一张图的重复运行代替泛化验证。**

## 2. 现状基线（执行前冻结）

执行任何优化前，先保存一份只读基线 manifest，至少包含：

- `hw/build/export/` 当前 `.bit/.xsa/.elf/BOOT.bin/SHA256SUMS`；
- 当前 `sw/app` 与 `clients/python` 的 Git commit；
- SE150、SE250 各一轮小规模和全量 `tools/run_g3.sh` 摘要；
- 四级 DDR 取证摘要；
- 当前实现报告中的 LUT、FF、BRAM、WNS/WHS；
- CPU 单核、多核、当前 FPGA 的同口径耗时；
- 板端电压/电流测量方法（若暂时没有功率计，必须写明“未测量”）。

基线文件建议放在：

```text
docs/benchmarks/baseline-20260905/
```

生成物不进入 `data/R0.83_data/`，大体积原始板测文件只保留外部留证路径，仓库内提交摘要、命令、哈希和 manifest。

## 3. 数据不足的解决方案

只有一套真实 DNA 数据并不阻塞方向 A/B，但必须把“真实数据”和“合成数据”的证据边界分开。

### 3.1 数据分层

| 层级 | 数据来源 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| D0 | `data/R0.83_data/` 原始 SE150/SE250 | 真实端到端闭环、板级工程可行性 | 对其他 payload 的泛化 |
| D1 | 同一编码参数、替换 source payload 后重新编码/生成读段 | 不同内容下算法与链路稳定 | 真实测序平台的全部噪声特征 |
| D2 | 对 D0/D1 注入可控 substitution/indel/覆盖度扰动 | 错误鲁棒性曲线、故障边界 | 真实平台分布的完全真实性 |
| D3 | 公开测序错误统计或独立公开数据（只读导入） | 外部数据交叉验证 | 与本项目编码分布完全匹配 |

报告中必须明确标注：`D0=真实基准`，`D1/D2=受控合成`，`D3=外部交叉验证`。

### 3.2 生成多个 payload（推荐优先做）

不要修改现有 `data/R0.83_data/`。新增工具链：

```text
tools/generate_payload_dataset.py
  source payload -> LDPC -> 4b5b/稀疏化 -> watermark XOR -> DNA -> reads

tests/datasets/<dataset-id>/
  manifest.json
  source.sha256
  codeword.sha256
  watermark.sha256
  reads.sha256
  expected.sha256
```

第一批至少生成：

1. 全零/全一仅用于边界和流水线自检，不作为真实性能结论；
2. 随机 payload 2 组；
3. 高低熵文本各 1 组；
4. 不同图片或二进制文件各 2 组；
5. 与 R0.83 相同长度、不同内容的 payload 2 组。

所有数据必须从编码端重新生成，禁止复制历史 `result.txt/decoded_image.jpg` 作为输入，禁止把正确结果偷偷放入生产路径。

### 3.3 受控错误注入

新增 `tools/mutate_reads.py`，输入 FASTQ 和 manifest，输出新目录，不覆盖原文件。参数至少包括：

```text
--sub-rate       substitution 比例
--ins-rate       insertion 比例
--del-rate       deletion 比例
--coverage       保留读段比例/重复采样倍率
--seed           随机种子
--orientation    正反向比例
```

每个实验必须保存：参数 JSON、随机种子、输入哈希、输出哈希、成功/失败、译码迭代轮数和最终图像哈希。

### 3.4 最小数据矩阵

第一阶段不追求海量数据，先做可解释的矩阵：

- payload：D0 + 4 个 D1；
- 读长：SE150、SE250；
- 覆盖度：0.5×、1×、2×；
- substitution：0%、0.5%、1%、2%；
- insertion/deletion：分别 0%、0.1%、0.5%；
- 每个点固定 3 个随机种子。

这将产生一个约 5×4×4×3 的分层测试矩阵，可先缩小为 smoke 子集，再将完整矩阵用于阶段验收。

## 4. T 线：时间优化实施步骤

### T0：统一计时口径（1 周）

1. 在 `tools/run_g3.sh` 和上位机记录 monotonic 时间；
2. 在固件状态机记录：配置、DMA、Stage1、Stage2、Stage3、回传等待；
3. 在 FPGA 侧增加可读计数器，至少记录每批启动/完成周期；
4. 统一输出 JSON：

```json
{
  "dataset_id": "...",
  "records": 129600,
  "stage1_s": 0,
  "stage2_s": 0,
  "stage3_s": 0,
  "upload_s": 0,
  "download_s": 0,
  "ldpc_s": 0,
  "e2e_s": 0,
  "sha256": "..."
}
```

5. 用 4,096、16,384、32,768、full 四档拟合固定开销和斜率；
6. 对每一档至少重复 3 次，报告中位数和最大/最小值。

**T0 门禁：** 没有完整分段计时，不进入 RTL 性能改造。

### T1：上位机与传输优化（1~2 周）

优先优化不改变 RTL 的部分：

1. FASTQ 流式读取，禁止一次性复制大数组；
2. 发送缓冲区复用，避免每条记录重复分配；
3. DMA 输入按批次预打包；
4. 双缓冲：上传第 N+1 批时，板端处理第 N 批；
5. 结果接收与 LDPC 预处理并行；
6. 将进度、超时和错误分层，不用固定大超时掩盖卡死；
7. C/原生扩展只替换经过 profiling 证明的热点；
8. 保持 Python 版本作为可读参考实现，C 版本必须逐位对照。

**验收：** 功能哈希不变；固定开销下降；CPU 占用、峰值内存和网络吞吐有表格证据。

### T2：Stage1 4 倍展开实验（2~3 周）

建立独立参数分支或可配置宏，不直接覆盖基线：

1. 保持 64 条读段批次不变；
2. 每周期从 1 个碱基扩展为 4 个碱基；
3. 设计 4 路局部计分寄存器和流水加法树；
4. 验证窗口边界、反向互补、最后一拍和 SE150/SE250 位宽；
5. 先跑 XSim，再跑综合，再跑整机实现；
6. 上板使用同一批数据，比较 Stage1 周期和端到端耗时。

**T2 门禁：** 4 倍展开必须在资源、时序、逐位正确性三项同时通过，否则回退，不进入 8 倍展开。

### T3：4/8 倍展开与批次规模探索（3~5 周）

依次评估：

```text
64×4
64×8
128×4（若资源允许）
```

每个配置记录 LUT、FF、BRAM、DSP、WNS/WHS、拥塞、功耗和每条记录周期。不要只看综合报告；必须以板端 `run_g3.sh` 结果为准。

### T4：流水重叠与 DDR 往返削减（并行进行）

1. 评估 Stage1 输出是否可以分批进入 Stage2；
2. 评估 Stage2/Stage3 是否能通过 AXIS 或片上 FIFO 减少一次 DDR 落盘；
3. 引入双缓冲和明确的 buffer ownership；
4. 加入背压、DMA 错误和中途取消测试；
5. 对比“只改 Stage1”和“只改数据流”的收益，形成消融表。

### T5：时钟与器件扩展（最后做）

测试 100/125/150 MHz，只有当时序和板级稳定均通过才保留。XC7Z020 方案只能作为扩展实验，不得与 XC7Z010 的正式成绩混报。

## 5. A 线：参数化与通用读出

### A1：配置契约

把以下参数统一纳入 manifest 和 PKT_CONFIG：

- `read_bps`；
- `watermark_symbols`；
- `num_lc/stride/ref_len`；
- `codeword_bits`；
- `score_min`；
- 读段方向模式；
- 输入数据集 ID 和哈希。

固件、RTL、Python 三方必须拒绝不匹配配置。错误几何必须在零数据处理前返回明确错误码。

### A2：多 payload 验证

先使用 D1 数据验证同一硬件参数下的不同内容，再考虑运行时可变水印。每次必须保存四级中间结果的 manifest，避免“最终图像一样但中间链路错位”。

### A3：运行时可变几何

只有 A1/A2 稳定后再考虑把几何从综合期常量下沉为运行时参数。优先支持两套已验证 profile，而不是一开始追求任意长度。

**A 线成功定义：** 至少 5 个不同 payload、SE150/SE250 各一组、所有结果通过唯一输出哈希和中间级别检查。

## 6. B 线：错误鲁棒性与边界曲线

### B1：先做仿真和主机模型

在上板前完成 mutation manifest、黄金模型和 LDPC 结果判据。每个错误点必须可重复，不能用“随机跑一次成功”作结论。

### B2：小规模板测

先用 2,048/4,096 条记录测试错误矩阵，确认：

- Stage1 score 分布；
- 错误读段比例；
- Voter 残差；
- LDPC 初始校验子和迭代次数；
- 最终恢复成功/失败。

### B3：边界曲线

输出：

```text
错误率 -> 成功率
覆盖度 -> 成功率
score_min -> 误接受率/误拒绝率
```

不能只给一个推荐阈值，要说明阈值变化对耗时和正确率的影响。

### B4：真实与合成证据隔离

论文/答辩中使用两张图：

1. D0 真实数据板端闭环；
2. D1/D2 受控实验鲁棒性曲线。

这样即使真实数据只有一套，也不会因为数据少而无法支撑方向 B。

## 7. H 线：上位机优化与产品化

### H1：核心库拆分

把上位机拆成稳定接口：

```text
fastq_reader
geometry_inspector
packet_builder
board_session
result_receiver
ldpc_decoder
verification_report
```

GUI 只调用这些模块，不在界面代码中直接拼协议或读取参考答案。

### H2：性能优化

1. 用 profiler 找出 FASTQ、编码转换、打包、LDPC 的真实热点；
2. 继续维护 Python 参考实现；
3. 对热点使用 C/Cython/共享库加速；
4. 对 C 译码器做随机向量、故障注入和 Python 逐位对照；
5. 避免重复内存拷贝；
6. 支持结果流式写盘，防止全量任务占用过多内存。

### H3：可观测性

GUI/CLI 至少展示：

- 当前阶段；
- 已发送/已接收记录数；
- 板端耗时预测与实际耗时；
- score 分布；
- DMA/网络重试；
- LDPC 迭代次数；
- 最终哈希；
- 失败阶段和可恢复建议。

### H4：交付门禁

上位机优化后必须通过：

- `tests/host/` 全部测试；
- Python/C LDPC 逐位一致；
- SE150/SE250 真实板测；
- D1/D2 合成数据；
- 错误协议、超时和断连恢复。

## 8. 统一验收矩阵

每一个优化版本都必须填写：

| 类别 | 判据 |
|---|---|
| 正确性 | 图片 SHA-256、四级 DDR、中间 manifest |
| 性能 | 分段耗时、端到端耗时、重复次数、统计量 |
| 资源 | LUT/FF/BRAM/DSP、WNS/WHS、拥塞 |
| 稳定性 | 连续多轮、跨规模、长时间、断连恢复 |
| 鲁棒性 | substitution/indel/覆盖度矩阵 |
| 可复现 | 命令、输入哈希、制品哈希、工具版本 |
| 可解释性 | 与基线的消融对比、失败原因 |

任何一项缺证据，只能标记为“部分通过”。

## 10. 竞赛最终叙事

推荐最终把项目讲成：

> 在资源受限的 AMD Zynq 平台上，针对 DNA 水印读出中无法使用精确种子匹配的问题，设计二维并行滑窗比对和软硬件协同流水线；通过真实板端闭环、可控错误模型和多 payload 验证，证明系统不仅能恢复数据，而且能量化说明 FPGA 在特定数据流和功耗约束下的价值。

不要把尚未实测的“百倍加速”“低 55 倍能耗”“支持任意 DNA 数据”写成现状结论；这些只能作为目标或后续实验假设。
