# 13 · 从当前状态到全流程结束的总收口计划

> 版本：2026-09-05。本文不是愿望清单，而是从当前 checkout 出发到“可以交付、可以答辩、可以复现”的终态门禁。任何未通过的阶段都不能在宣传中写成已完成。

## 1. 最终目标

最终交付物不是一张能显示图片的演示板，而是一套在 AMD/Xilinx Zynq 平台上可复现的 DNA 信息存储读出系统：

```text
输入 FASTQ + manifest
→ 上位机检查与参数下发
→ PS/PL 真实接口流水线
→ Stage1 比对、Stage2 投票、Stage3 反稀疏化
→ 板端真实回传
→ LDPC 译码
→ 输出原始文件
→ 自动生成证据报告
```

### 1.1 终态必须同时满足的五个目标

| 目标 | 终态判据 |
|---|---|
| 正确 | 至少 5 个独立 payload、SE150/SE250 profile、最终哈希和中间级别检查通过 |
| 性能 | 与优化 C 单核/多核同口径对照；Stage1 优化版本的收益可重复，不能靠低效 Python 做基线 |
| 鲁棒 | 有 substitution/insertion/deletion、覆盖度和阈值边界曲线，并保留失败样本 |
| 工程 | 冷启动、连续任务、全量任务、断连/超时恢复和长稳测试通过 |
| 交付 | 一键构建/烧录/验收、制品哈希、报告、演示脚本和答辩材料完整 |

若只满足其中一两项，项目仍是“功能样机”，不是终态产品。

## 2. 对现状的毫不留情评价

### 2.1 已经真正做成的部分

- 不是纯仿真：已经有真实 Zynq 板端 G3 闭环；
- SE150/SE250 全量和连续任务已有实测；
- RTL、PS、AXI、DMA、DDR、TCP、LDPC 组成了完整系统；
- 自动化回归和压测已经具备工程雏形；
- 文档、哈希、运行留证意识明显强于普通竞赛项目。

### 2.2 目前仍然不够格的部分

1. **性能故事尚未成立。** 当前 Stage1 仍未证明击败优化 C；现在最硬的成果是“做成了”，不是“更快”。
2. **通用性几乎没有被真正证明。** SE150/SE250 主要仍是同一 R0.83 内容体系；重复处理同一张图不是泛化。
3. **鲁棒性证据缺少曲线。** 目前知道一些最低覆盖度和阈值边界，但还没有系统的测序错误率→恢复率实验。
4. **上位机仍是系统瓶颈和可维护性风险。** Python、C LDPC、协议、GUI、诊断逻辑需要统一接口和性能数据。
5. **功耗结论不能宣传。** 估算不是实测；没有板端电流、任务能耗和 CPU 同口径数据，就没有“低功耗优势”。
6. **系统仍然依赖固定板级条件。** 当前板能跑，不等于换板可迁移；没有资料的新板只能做实验线。
7. **项目容易被包装过度。** “通用 DNA 读出”“百倍加速”“工业级稳定”目前都不能直接写成事实。

**结论：项目有竞争力，但竞争力来自复杂系统闭环和工程验证，不来自已经被证明的绝对性能或通用性。后续必须补齐后两项，否则答辩会被一句 CPU 对比或换数据集问题击穿。**

## 3. 总体阶段图

```text
G0 终态冻结与证据基线
 ↓
G1 计时、统计与工具可靠性
 ↓
G2 上位机和传输优化
 ↓
G3 Stage1 并行化性能实验
 ↓
G4 多 payload 通用性
 ↓
G5 错误鲁棒性
 ↓
G6 长稳、功耗与故障恢复
 ↓
G7 竞赛版冻结与独立复核
 ↓
G8 最终演示、报告和交付
```

G3、G4、G5 可以并行准备数据，但不能跳过 G0/G1。没有可比基线，后面所有“优化”都可能是错觉。

## 4. 分阶段执行计划

### G0 · 终态冻结与基线（1～2 天）

**任务**

1. 冻结当前可复现制品的 `.bit/.xsa/.elf/BOOT.bin/SHA256SUMS`；
2. 冻结 SE150/SE250 profile、阈值和 manifest；
3. 记录当前资源、时序、板端耗时、CPU 耗时；
4. 对压测脚本建立版本号和输入哈希；
5. 生成一个“当前版本不可变基线”摘要。

**出口门禁**

- `verify_repo_binding.sh --require-synced` PASS；
- 当前板各 profile 至少一轮 G3 PASS；
- 输入、制品、工具版本全部可追溯；
- 任何后续版本都能与该基线直接比较。

### G1 · 计时和统计可信（3～7 天）

**任务**

1. 修复压测统计接口问题；
2. 给每轮增加 `failure_class`；
3. 记录 FASTQ、上传、DMA、Stage1/2/3、回传、LDPC 和端到端时间；
4. 生成 JSONL 和简短 Markdown 摘要；
5. 将边界探索、故障注入、工具异常与产品失败分开。

**出口门禁**

- 10～20 轮 smoke 统计无字段错误；
- 同一输入重复运行的计时波动可解释；
- 能回答“时间到底花在哪一级”；
- 工具失败不会被误报成硬件失败。

### G2 · 上位机和传输优化（1～2 周）

**任务**

1. FASTQ 流式读取和 buffer 复用；
2. 批量打包，避免每条记录重复分配；
3. 上传、板端计算、结果接收和 LDPC 预处理尽可能重叠；
4. 拆分协议会话、结果接收、LDPC、报告生成模块；
5. C LDPC 与 Python 参考实现逐位对照；
6. 保留 Python 参考版本，不能为了速度删除可读基准。

**出口门禁**

- SE150/SE250 G3 哈希不变；
- 总耗时和固定开销有实际下降；
- 主机峰值内存、CPU 占用和网络吞吐有记录；
- 断连、超时、错误配置能给出明确错误。

### G3 · Stage1 并行化（2～4 周）

**任务**

按风险从低到高做：

```text
64×1 基线 → 64×4 → 64×8 → 128×4（资源允许）
```

每一档都完成：

1. RTL 设计和局部 TB；
2. 真实 AXIS ingress/result 回归；
3. SE150/SE250 黄金向量；
4. 综合和实现；
5. 板端小规模；
6. 板端全量；
7. 与 CPU 公平比较。

**出口门禁**

- 逐位正确；
- LUT/FF/BRAM/DSP、WNS/WHS、拥塞均合格；
- Stage1 周期和端到端耗时确实下降；
- 若没有收益，必须保留失败实验和原因，不得强行宣传。

### G4 · 多 payload 通用性（2～3 周，可与 G3 后半段并行）

**任务**

1. 用 `tools/generate_payload_dataset.py` 生成至少 4 个新 payload；
2. 每个 payload 生成独立 manifest、编码、读段和参考哈希；
3. 每个 payload 跑 2,048、4,096、16,384 和 full 档；
4. 运行时检查 payload/profile/读长/水印不匹配；
5. 报告最终哈希和 Stage1/2/3 中间结果。

**出口门禁**

至少 5 个 payload（含 D0）通过；任何 payload 失败都要保留失败原因，不能只挑成功样本展示。

### G5 · 错误鲁棒性（2～4 周）

**任务**

用 `tools/mutate_reads.py` 建立受控矩阵：

- substitution：0%、0.5%、1%、2%；
- insertion/deletion：0%、0.1%、0.5%；
- coverage：0.5×、1×、2×；
- 每个点至少 3 个随机种子；
- 扫描 `score_min`，记录误接受和误拒绝。

**出口门禁**

形成可读曲线：

```text
错误率 → 恢复成功率
覆盖度 → 恢复成功率
阈值 → 正确率/耗时/误接受率
```

必须同时保留失败样本、原始 bit 错误、初始校验子和 LDPC 迭代次数。

### G6 · 长稳、功耗和故障恢复（1～2 周）

**任务**

1. 多尺度连续任务和全量双轮；
2. TCP 断连、结果超时、DMA 错误、非法配置注入；
3. 记录板端电压、电流、任务能耗和温度；
4. 与 CPU 完成同任务能耗对照；
5. 统计长跑吞吐、失败率、恢复时间和性能退化。

**出口门禁**

- 产品失败与预期故障注入分开统计；
- 能耗为实测值，不再使用估算值；
- 连续任务无不可诊断挂死；
- 任何异常都能定位到协议、固件、RTL 或数据层。

### G7 · 竞赛版冻结（约 1 周）

**冻结内容**

- FPGA 器件和板卡；
- Vivado/Vitis 版本；
- RTL、PS、上位机和 GUI；
- SE150/SE250 制品；
- 演示 payload；
- 报告数字和图表；
- 一键构建、烧录和验收命令。

**冻结门禁**

- 冻结后只允许修复阻断性问题；
- 任何修复都必须重新生成制品和哈希；
- 至少一名未参与实现的人按文档独立复现；
- 现场演示不依赖隐藏文件、历史正确结果或人工替换输出。

### G8 · 最终交付

提交以下四类成果：

1. **代码**：RTL、PS、上位机、测试和构建入口；
2. **硬件**：bitstream、XSA、ELF、BOOT.bin、哈希清单；
3. **证据**：G3、性能、泛化、鲁棒、长稳和功耗摘要；
4. **表达**：3 分钟演示、10 分钟答辩、架构图、消融表和风险边界。

最终演示必须现场展示：输入 profile、处理进度、板端返回、LDPC 结果、最终哈希和耗时，而不是只展示一张预生成图片。

## 5. 最终验收表

| 项目 | 必须回答的问题 |
|---|---|
| 正确性 | 换 payload 后还能否逐位恢复？ |
| 性能 | 与优化 C 比到底快不快？瓶颈是哪一级？ |
| 资源 | 并行化换来了什么，代价是什么？ |
| 鲁棒性 | 错误率和覆盖度到什么边界会失败？ |
| 稳定性 | 连续跑、全量跑、断连后能否恢复？ |
| 能耗 | 完成同一个任务消耗多少焦耳？ |
| 可复现 | 别人能否不用人工修路径独立跑通？ |
| 边界 | 哪些事情明确还不支持？ |

## 6. 终止规则

出现以下任一情况，不得继续堆功能，应先停下来修基础问题：

- 无法得到阶段级耗时；
- 同一输入重复结果不一致；
- 制品与源码无法证明同源；
- 新 payload 失败但没有保留失败证据；
- 压测工具把脚本异常报成硬件失败；
- 性能结论依赖未优化 CPU 或估算功耗；
- 演示只能依靠预生成正确结果。

**真正的结束不是“还能再加一个功能”，而是所有终态门禁都有证据，剩余限制被明确写出来。**
