## 1. 最终目标

最终交付物不是一张能显示图片的演示板，而是一套在 AMD/Xilinx Zynq 平台上可复现的 DNA 信息存储读出系统：

```text
输入 FASTQ + manifest
→ 上位机检查与参数下发
→ PS/PL 真实接口流水线
→ Stage1 比对、Stage2 投票、Stage3 反稀疏化
→ 板端真实回传
→ LDPC 译码
→ 输出原始文件
→ 自动生成证据报告
```

### 1.1 终态必须同时满足的五个目标

| 目标 | 终态判据 |
|---|---|
| 正确 | 至少 5 个独立 payload、SE150/SE250 profile、最终哈希和中间级别检查通过 |
| 性能 | 与优化 C 单核/多核同口径对照；Stage1 优化版本的收益可重复，不能靠低效 Python 做基线 |
| 鲁棒 | 有 substitution/insertion/deletion、覆盖度和阈值边界曲线，并保留失败样本 |
| 工程 | 冷启动、连续任务、全量任务、断连/超时恢复和长稳测试通过 |
| 交付 | 一键构建/烧录/验收、制品哈希、报告、演示脚本和答辩材料完整 |

若只满足其中一两项，项目仍是“功能样机”，不是终态产品。

## 2. 对现状的毫不留情评价

### 2.1 已经真正做成的部分

- 不是纯仿真：已经有真实 Zynq 板端 G3 闭环；
- SE150/SE250 全量和连续任务已有实测；
- RTL、PS、AXI、DMA、DDR、TCP、LDPC 组成了完整系统；
- 自动化回归和压测已经具备工程雏形；
- 文档、哈希、运行留证意识明显强于普通竞赛项目。

### 2.2 目前仍然不够格的部分

1. **性能故事尚未成立。** 当前 Stage1 仍未证明击败优化 C；现在最硬的成果是“做成了”，不是“更快”。
2. **通用性几乎没有被真正证明。** SE150/SE250 主要仍是同一 R0.83 内容体系；重复处理同一张图不是泛化。
3. **鲁棒性证据缺少曲线。** 目前知道一些最低覆盖度和阈值边界，但还没有系统的测序错误率→恢复率实验。
4. **上位机仍是系统瓶颈和可维护性风险。** Python、C LDPC、协议、GUI、诊断逻辑需要统一接口和性能数据。
5. **功耗结论不能宣传。** 估算不是实测；没有板端电流、任务能耗和 CPU 同口径数据，就没有“低功耗优势”。
6. **系统仍然依赖固定板级条件。** 当前板能跑，不等于换板可迁移；没有资料的新板只能做实验线。
7. **项目容易被包装过度。** “通用 DNA 读出”“百倍加速”“工业级稳定”目前都不能直接写成事实。

**结论：项目有竞争力，但竞争力来自复杂系统闭环和工程验证，不来自已经被证明的绝对性能或通用性。后续必须补齐后两项，否则答辩会被一句 CPU 对比或换数据集问题击穿。**

### G1 · 计时和统计可信（3～7 天）

**任务**

2. 给每轮增加 `failure_class`；

4. 生成 JSONL 和简短 Markdown 摘要；
5. 将边界探索、故障注入、工具异常与产品失败分开。

**出口门禁**

- ✅ 10～20 轮 smoke 统计无字段错误；
- ✅ 同一输入重复运行的计时波动可解释；
- ✅ 能回答“时间到底花在哪一级”；
- ✅ 工具失败不会被误报成硬件失败。

> **2026-09-11 四条全部达成**，依据见
> [`docs/benchmarks/measured_timing_accountability.md`](benchmarks/measured_timing_accountability.md)。
> 两条关键结论：
> （a）时间构成——PL 真实计算约 50%、**poll 定时器空等约 29%**、PS 固件执行 9.1%、
> 通信与主机侧合计不到 10%；
> （b）12 次重复的变异系数 11.97% **不是测量噪声而是量化**——样本聚成四簇、
> 簇间差恒为 0.47~0.49 s，对应 lwIP 慢定时器节拍；簇内抖动仅 0.3%。
> **推论：报任何板端耗时都必须给重复次数与中位数**，单次结果精度只有 ±0.5 s。

### G5 · 错误鲁棒性（2～4 周）

**任务**

用 `tools/mutate_reads.py` 建立受控矩阵：

- substitution：0%、0.5%、1%、2%；
- insertion/deletion：0%、0.1%、0.5%；
- coverage：0.5×、1×、2×；
- 每个点至少 3 个随机种子；
- 扫描 `score_min`，记录误接受和误拒绝。

**出口门禁**

形成可读曲线：

```text
错误率 → 恢复成功率
覆盖度 → 恢复成功率
阈值 → 正确率/耗时/误接受率
```

必须同时保留失败样本、原始 bit 错误、初始校验子和 LDPC 迭代次数。

## 6. 终止规则

出现以下任一情况，不得继续堆功能，应先停下来修基础问题：

- 无法得到阶段级耗时；
- 同一输入重复结果不一致；
- 制品与源码无法证明同源；
- 新 payload 失败但没有保留失败证据；
- 压测工具把脚本异常报成硬件失败；
- 性能结论依赖未优化 CPU 或估算功耗；
- 演示只能依靠预生成正确结果。

**真正的结束不是“还能再加一个功能”，而是所有终态门禁都有证据，剩余限制被明确写出来。**

### 7.1 目标指标一：端到端耗时/吞吐

| 假设 | 尝试方法 | 首轮成本 | 成功信号 |
|---|---|---:|---|
| ~~H1：碱基维度 4/8 路展开有效~~ | **部分成立后关闭**：4 路已实测 1.929x 并收敛；**8 路证伪**（LUT 外推 125%） | — | ❌ 不再投入，见 [17](17-competition-strategy.md) §2.1 |

| ~~H3：二维展开可组合~~ | **证伪**：128×4 在 XC7Z010 上放不下 | — | ❌ 关闭 |
| **H0（新增，最高优先级）：4.25 s 固定开销可大幅压缩** | PS 侧分阶段插桩，定位 Stage 2.5 软件异或等热点 | 低 | 固定开销 → 1 s 时全量 4-way 达约 2,000 reads/s，首次超单核 CPU |
| H4：候选位置分层搜索 | 粗粒度窗口筛选后精确复核 | 中 | 候选位置显著减少且零误定位 |
| H5：分数提前终止 | 当前分数不可能超过 best 时提前结束 | 低 | 平均周期下降，最坏情况仍正确 |
| H6：比较器位并行化 | 单周期计算多个碱基并用流水加法树 | 中 | Fmax 不下降，Stage1 斜率下降 |
| H7：水印窗口移位广播 | 预取连续窗口，减少 BRAM/MUX 访问 | 中 | 关键路径和 BRAM 读次数下降 |
| H8：多引擎复制 | 两个半规模 Stage1 并行处理 batch | 高 | 总吞吐接近 2 倍且 DDR 不成为瓶颈 |
| H9：输入/计算/输出三段重叠 | DMA 双/三缓冲 + AXIS 流水 | 中 | 固定等待和 DMA 空洞消失 |
| H10：Stage1→Stage2 流式衔接 | 小批次 FIFO 替代完整 DDR 中转 | 高 | 端到端延迟下降且背压无丢包 |
| H11：PS 轮询改事件驱动 | 中断/状态事件替代固定 poll 节奏 | 低 | 固定开销进一步下降，异常可恢复 |
| H12：结果传输压缩/批量化 | 减少帧间空洞和协议往返 | 低 | 网络占用下降且物理 ACK 仍完整 |
| H13：只对不确定读段做反向搜索 | score/confidence 足够高时减少反向工作 | 中 | 平均工作量下降，低置信度不漏检 |
| H14：动态 batch | 根据剩余读段数、DDR 空间和 score 分布调整批量 | 中 | 小任务延迟下降，大任务吞吐不退化 |

## 8. 发散实验的筛选规则

每个假设先做小实验，不要一开始写入主线架构。每个实验必须填写：

```text
hypothesis_id
目标指标
基线版本
输入/制品哈希
实验命令
资源与时序
耗时/功耗
正确性结果
失败原因
是否进入下一轮
```

### 8.1 推荐优先级

先做“低成本、高信息量”实验：

```text
H5/H9/H11/H13/E6/E7/R1/R2/G1/G3/C1
→ H1/H2/H4/H6/H7/H15/E1/E2/R3/R5
→ H3/H8/H10/E4/R4/R7/R8/G2/G5
```

### 8.2 失败也算产出

以下结果都应保留：

- 64×8 资源超限；
- 128×4 时序失败；
- 提前终止导致召回率下降；
- 自适应阈值在某错误率下失效；
- 多 payload 暴露固定常量；
- 流式 DDR 方案被带宽或背压击穿。

失败实验的价值是缩小搜索空间，不能因为没有变成最终功能就删除。

### 8.3 进入主线的硬条件

只有同时满足以下条件，候选方向才进入 G3～G6 主线：

1. 有明确可测指标；
2. 首轮实验不是只在 Python 模型中成立；
3. 没有破坏当前 SE150/SE250 基线；
4. 能设计出反向故障注入或失败判据；
5. 成功收益足以覆盖新增复杂度；
6. 能在比赛截止时间前完成板级复现。

**发散不是无限堆功能。允许广泛试错，但每条路线都必须快速得到“继续、暂停或淘汰”的决定。**
