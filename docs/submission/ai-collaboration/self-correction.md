# 自我纠错轨迹

以下四条都来自 BKB220 板级迁移的真实记录，来源可在 [migration-source-table.md](../../board/bkb220/migration-source-table.md) 对应小节复核。记录重点是模型/执行者如何撤回证据不足的判断，并把修正转成后续检查规则。

## 1. MDIO 无应答：把自己的寄存器错误当成板卡缺项

**当时的错误结论**

前几轮 PHY 扫描没有找到有效 ID，结论一度写成“ENET0 未通过”，并把下一步指向需要原理图或物理层检查。探测代码本身有两处错误：把 PHY_MAINT 的位当成完成标志，并且没有使能管理端口。

**什么证据推翻它**

来源表 §9.5.1、§9.6 记录了驱动定义：MDIO 完成状态应读 NETWORK_STATUS[2]（XEMACPS_NWSR_MDIOIDLE_MASK），管理端口使能 MDEN 是 NETWORK_CONTROL bit 4（XEMACPS_NWCTRL_MDEN_MASK）。修正轮询与使能后，PHY 立即有响应；读到 PHYID1/PHYID2 为 0x001C/0xC915，识别为 Realtek RTL8211E，并观测到 1000BASE-T 全双工 link up。

**改成什么做法**

寄存器级探测先对照 Xilinx 驱动头文件核对寄存器与位定义，再执行访问；完成标志和使能分别按 NETWORK_STATUS[2] 与 NETWORK_CONTROL bit 4 判定。

**沉淀成哪条规则**

不要凭同名外设的经验推断位定义。无应答首先检查探测器自己的完成判据、使能和初始化顺序，再把原因归到原理图、引脚或器件。

## 2. 假阻塞：把 Vitis 2022.2 不提供的 lwip220 写进阶段卡

**当时的错误结论**

阶段卡把 lwip220 写成 Vitis 2022.2 的必需组件；构建环境找不到该组件时，任务被卡住，形成假阻塞。

**什么证据推翻它**

来源表 §12.5 记录了这次阶段卡错误；[docs/07 工具链说明](../../07-board-build-and-acceptance.md) 明确了安装树差异：WSL Vitis 2022.2 提供 lwip211 系列，lwip220 属于 Vitis 2026.1。仓库 create_vitis.tcl 的选择顺序本就会从 lwip213 回落到 lwip211，再到 lwip210。

**改成什么做法**

按当前安装树查询实际可用库，使用项目入口支持的回落版本构建，并把实际库版本与目标版本差异写进结果；不再把 lwip220 固定为 2022.2 的前置条件。

**沉淀成哪条规则**

工具版本约束以现场安装内容为准。缺少指定版本时，先查可用替代项并如实标注；不能因版本号不同就判整包失败，也不能静默说成同版本。

## 3. 探针配置不等于制品配置：PHY 正常但实际 P4 包没有配置 MIO

**当时的错误结论**

F3 探针用单独生成的 ps7_init 读到了 PHY，于是把这组 ENET0 属性的有效性扩大成“整机配置已验证”。F4 首次 G3 失败时，又把现象归因到 Realtek 驱动自协商超时；这解释没有覆盖实际制品的配置状态。

**什么证据推翻它**

来源表 §12.1–§12.3 给出完整对照：板上读回的 MIO_PIN_52/53 是 0x1201，而 GEM MDIO 应为 0x1280；实际 P4 包的 ps7_init 没有 MIO16–27 和 MIO52–53 写入，探针版本则有对应写入；PHY 扫描决策变量 phymapemac0[] 全为 0。检查 hw/boards/bkb220.tcl 的历史配置也发现，所需 ENET0 MIO/MDIO 属性没有进入 profile。根因是探针旁路配置可用，但生产 profile 没有把它带进被构建的制品。

**改成什么做法**

把缺少的 ENET0 属性补入 profile，按正规流程重建同源 P4 包，再检查新包 ps7_init 是否包含预期 MIO 写入，最后重跑真实板 G3。来源表 §12.4 和 §13 记录了修复后重建与 G3 PASS。

**沉淀成哪条规则**

探针、仿真或单独生成的配置只能证明该配置本身在对应条件下工作。要证明板上制品正确，必须从实际构建/烧录包核对属性、源集和 manifest，并由真实板判据闭环。

## 4. CRLF 让串口采集 PASS 被判成 FAIL

**当时的错误结论**

G3 串口实录检查报告没有可确认输出，被判 FAIL；当时的正则使用行尾锚点，结果把已有串口采集误判为空。

**什么证据推翻它**

来源表 §13.1 记录采集器返回 CAPTURE_DONE chars=7781，Windows 侧写出的 uart_cap.out 使用 CRLF。run_g3.sh 的匹配模式以 $ 作为行尾，实际内容在换行前多了回车符，锚点因而不匹配。

**改成什么做法**

在解析该外部采集文件前用 tr -d '\r' 归一化，再按标记匹配；修复后串口判据不再把 CRLF 当成缺失输出。

**沉淀成哪条规则**

跨 Windows 与 WSL 的文本边界要显式处理行尾；当日志内容和判据不一致时，先核对原始字节、采集结果和解析逻辑，分别判断设备失败还是工具误报。
