## 1. 0.653 秒的拆分

[最新上传计时记录](<<仓库根目录>/docs/benchmarks/bkb220-p16-speed-a-upload.md>)给出整轮约 10.18 秒、LDPC 0.653 秒（6.4%）；该记录注明 A/B 两包的 LDPC 数值沿用此前测量，本轮没有重测。[时间预算](<<仓库根目录>/docs/benchmarks/bkb220-p16-time-budget.md>) §2 是较早的 13.272 秒整轮口径，因此列出 4.9%。两份记录的 LDPC 数值相同，整轮分母不同。

仓库里没有 `logs/g3/**/dec_input*.txt`。我用现有的 `tests/golden/se250/dec_input.txt` 作高迭代样本；它是 64,800 bit，译码 45 轮，但它不是本次 SE150 G3 输入，不能据此断言 G3 实际迭代数就是 45 或 47。

**本机 CPU 实测**：对该样本调用验收所用译码 CLI 三次，完整命令为：

```bash
env PYTHONDONTWRITEBYTECODE=1 OPENBLAS_NUM_THREADS=1 \
python3 tools/ldpc_decode.py decode tests/golden/se250/dec_input.txt \
  -o <本机路径> --payload <本机路径> --input-bytes 6750
```

计时由外层进程对每次新启动的子进程取墙钟：**0.607–0.632 秒，中位 0.630 秒**。输出写到 `<本机路径>`，没有写仓库文件。

| 分段 | 实测结果 |
|---|---:|
| `native_ldpc.load_pchk()` 解析校验矩阵 | 0.229 秒，单次暖文件缓存测量 |
| `hard_decode()` | 0.324–0.338 秒，三次中位 0.330 秒；每次 45 轮 |
| 输入文本读取校验 | 约 0.003 秒 |
| 读 permutation、解交织及数组转换 | 合计约 0.004 秒 |
| CLI 中其余部分 | 约 0.071 秒的差额，含进程启动、导入、输出格式化等，未再细拆 |

以上分段来自不同计时点，不能要求小数位完全相加；但它显示了主要两项：**Python 循环解析矩阵约 0.229 秒，迭代译码约 0.330 秒**。

`hard_decode()` 是 64,800 个变量、10,800 个校验行的 Min-Sum 译码。该样本每行 21–22 条边，共 237,599 条边；每轮主要处理 `10,800×22` 的边数组和 64,800 位决策数组。静态数算约有 25–30 个数组索引、NumPy 运算或规约点，包含符号/幅值 gather、行乘积、排序取最小与次小值、并列最小值处理、`bincount` 汇总、硬判决和 syndrome 检查。

我对 45 轮核心另作阶段计时：每轮约 7.16 ms，其中“行符号、排序、最小值和并列处理”合计约 **4.61 ms/轮，占迭代循环约 64%**；其余 gather 约 0.72 ms、消息构造约 0.90 ms、`bincount` 约 0.41 ms、硬判决及 syndrome 约 0.52 ms。**结论：迭代体内主要耗时在 NumPy 的排序和并列处理；Python 单轮循环调度不是主要热点。**整次 CLI 还有明显的 Python 矩阵解析开销。

**C 路径实测**：同一输入的 `c_ldpc.decode_bits_c()` 完整进程式测量（每次新进程，读取输入、调用 C 译码、格式化输出到 `<本机路径>` 并计算载荷哈希）为 **0.162–0.201 秒，中位 0.182 秒**。缓存后 C 核心为约 0.074 秒。45 轮样本上 Python 与 C 的信息位一致，且都在 45 轮收敛。相对 Python CLI 样本墙钟约省 **0.448 秒**；这是本机样本实测，不是 G3 板验收实测。

## 2. 上位机还能压多少

| 优化 Python 核心：预分配 scratch、用 `int32` 索引、以 `partition` 取两个最小值、减少临时数组 | **静态分析；收益未验证。** 排序/并列处理组当前约 0.208 秒/45 轮，是优化靶点。粗略预期总轮次省 **0–0.15 秒**，不能当实测收益。 | 仍需保留并列最小值语义和 syndrome 判据。全排序替换成选择算法后必须重跑译码及哈希。 |
| 位打包 | **未验证，预期很小**：内部迭代仍需 LLR 幅值与符号，打包主要影响最终载荷输出。按代理 CLI 中约 0.071 秒的全部非解析、非核心差额看，输出优化的上限受此约束；实用收益预计低于约 0.03 秒。 | G3 还写出完整 `decoded_bits_run$r.txt` 留证；去掉该输出会改变现有产物。 |
| 16 线程 / 多进程 | **未实测。**当前 C 译码源码是串行循环；译码轮次之间有数据依赖，不能并行算同一输入的不同迭代。若已切 C，整个 45 轮核心约 0.074 秒，因此任何并行方案可省时间的绝对上限也只有约 0.074 秒，实际收益更低且未验证。 | 同一验收的多轮还受 Voter 状态顺序约束。这个方向不值得优先做。 |

## 3. 把译码放后台与下一轮重叠

技术上可以：第 `r` 轮 `first.py` 结束后启动后台译码，同时开始第 `r+1` 轮 `first.py`；文件名按轮次独立，`first.py` 不依赖上一轮 PC 侧的译码输出。完成 `r+1` 的 `first.py` 后 join 第 `r` 轮，按轮次检查退出码、SHA 和 dirty/judge 类型。`run_g3.sh` 当前是严格串行，未这样实现。

**墙钟收益外推**：`first.py` 及板端阶段约 9.53 秒，足以覆盖 0.653 秒译码。每个轮间边界最多隐藏约 **0.653 秒**；三轮最多隐藏两次，即约 **1.306 秒**。实际收益、主机 CPU 竞争程度均未实测。单轮运行没有下一轮可重叠。

这不能保持完全相同的 fail-fast 时序：当前 clean 轮 LDPC 非零退出会立即 `break`；若已启动下一轮 `first.py`，错误被发现前下一轮已经下发。最终 SHA 仍可在 join 后逐轮判定，不能因此报 PASS；但会多跑一轮，并可能改变失败后的板端累加器状态。dirty 轮译码失败本来是可接受情况，dirty 轮 SHA 只记录、不作判据；并行版必须按轮保存 `RUN_KIND`、退出码、日志和输出，并正确更新 `RUNS_COMPLETED`。因此这是“允许一轮预取”的验收脚本改动，不是无语义变化的简单 `&` 加 `wait`。时间预算文档要求改后至少重跑三轮全量判据；本只读任务没有改脚本或触板验证。

## 4. 与 CPU 对照的关系

**CPU 基线计时不包含 LDPC。** [`tools/run_cpu_benchmark.py`](<<仓库根目录><本机路径>>)的 C 基线计时围绕 `c_align_all()`，测的是 C/OpenMP 位运算与 popcount 的读段比对；数据准备在计时外。 [`measured_cpu_vs_fpga.md`](<<仓库根目录>/docs/benchmarks/measured_cpu_vs_fpga.md>)把板端 LDPC 单列，而 CPU 行是 C 比对基线；最新上传 benchmark 也明确 CPU 数字只算比对内核。

所以优化 LDPC **会缩短 FPGA 回传后的上位机端到端时间**，不会改变该报告的 CPU 比对时间或 `t_result` 对比口径。不能把这 0.653 秒算进 CPU 的 16 线程比对基线。
