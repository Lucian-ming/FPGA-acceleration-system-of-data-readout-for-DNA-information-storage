## 1. 矩阵身份：标准 DVB-S2 R=5/6

**实测解析结果：这是标准 DVB-S2 normal frame、R=5/6 的校验矩阵，列顺序经过重排。** `load_pchk` 按小端 int32 读取 `0x5080` 魔数和 `10800×64800` 尺寸；正数列地址按 1 起始存储，负数分隔行，解析时减 1。文件为 993,612 B，共 237,599 条边；行度是 1 行度 21、10,799 行度 22。

ETSI 的 normal frame 参数是 `N=64800、K=54000、Q=360`，R=5/6 的地址步长 `q=30`。我从矩阵恢复了 150 组信息位地址表，并将每组地址集合逐项与规范 Table B.9 比较：**150 组、600 个基地址全部匹配**；54,000 个信息列也全部满足规范的地址生成式。[ETSI EN 302 307-1 §5.3.2.1、Table 7a/B.9](https://www.etsi.org/deliver/etsi_en/302300_302399/302307/01.03.01_60/en_302307v010301p.pdf)

PCHK 把校验位列放在前 10,800 列、信息位列放在后 54,000 列；这是相对常见“信息位在前”的列重排。仓库的 `hard_decode` 也从 `PARITY_COLS` 之后提取信息位。[native_ldpc.py](<仓库根目录>/clients/python/native_ldpc.py)

## 2. H 有紧凑生成表示

**校验位部分实测为双对角累加器。** 第 0 行连校验列 `{0}`；第 `r>0` 行连 `{r−1,r}`。因此前 10,799 个校验变量度为 2，最后一个度为 1。

**信息部分也有紧凑结构，但不是 main 试的自然行序移位。** 对第 `t` 组信息位、组内位置 `m`（`t=0..149, m=0..359`），PCHK 列为 `10800+360t+m`。设该组在 `m=0` 时连接的基地址集合为 `B_t`，则实测对全部 150×360 列成立：

`check_row = (x + 30m) mod 10800，x ∈ B_t`

前 15 组每组 13 个基地址，后 135 组每组 3 个，共 **600 个基地址**；每个模 30 余数类恰好有 20 个基地址。自然行序中 `m` 增加对应的是校验行加 30，不是连续行块中行号加 1。若把校验行按 `r mod 30` 分组，信息部分就是 360 周期的循环结构。这解释了 main 的朴素比较为何不匹配。

- 规范式信息地址表：`600×14 bit = 1,050 B`。组度由组号决定，无需另存标志。
- 适合逐校验行处理的转置表：600 条 `(t,s)` 记录，`t` 8 bit、`s=floor(x/30)` 9 bit，共 **1,275 B**。对 `r=30k+a`，每条记录可直接生成信息列 `10800+360t+((k−s) mod 360)`。两种格式都只有约 1 KB；实际多路读取时需要考虑表的输出宽度。

**结论：H 不需要保存展开边表。** 校验位双对角部分可直接生成，信息部分可由规范的 600 个地址生成。以上本机解析和 Table B.9 对照均已完成。

## 3. XC7Z020 资源预算与 DDR 方案

资源余量来自现有 P16 构建：LUT 19,213、BRAM36 95、DSP 217；当前 P16 用 45/140 个 BRAM36，WNS 为 +0.617 ns。[P16 100 MHz 构建摘要](<仓库根目录>/docs/benchmarks/bkb220-p4-p16-100mhz-build.md)

下面的 BRAM 数是**静态容量估算**，假定实现仓库现有译码算法。该算法每轮从信道先验重建 `llr_next`，逐校验累加消息，没有持久化每条边的 C2V 消息数组；若改成需要边消息状态的算法，预算会不同。[c_ldpc_accel.c](<仓库根目录>/clients/python/c_ldpc_accel.c)

| 存储项 | 假定位宽与规模 | BRAM36 估算 |
|---|---:|---:|
| 紧凑 H 表 | 1,050–1,275 B | 1 |
| permutation | 64,800 个索引；原文件 32 bit，值可无损缩成 16 bit | 32 |
| `llr_cur` 与 `llr_next` | 各 64,800×8 bit | 32 |
| natural 输入位与 decoded 位 | 各 64,800 bit | 4 |
| **紧凑 H 合计，8-bit LLR、单端口容量下界** |  | **69；余量 95 中剩 26** |
| 展开 H | 237,599×16 bit；按 22 槽/行对齐 | **约 117，仅 H 就超过余量** |
| **展开 H 加其余存储** | 上述 permutation 和 LLR 状态 | **约 185** |

BRAM 数考虑了器件常见宽深配置和整块取整。`permutation64800` 有 64,800 项、覆盖 0–64,799 且无重复；压成 16 bit 后约 129,600 B、约 32 块。展开边地址为 475,198 B；117 块估算未含可选 CSR 行指针。上一轮约 103 块是按总 bit 数除以 BRAM 容量得到的下界，忽略了实际宽深配置和取整。

**LLR 位宽是重要条件。** 现有 C/Python 使用 double；直接复刻 double 状态不适合这片 BRAM。8-bit 的 69 块是实现规划假设，数值饱和和译码结果尚未验证。若用 16-bit `llr_cur/next`，紧凑 H 加板上 permutation 的估算为 101 块，超过 95；把 permutation 留在 DDR、装载时流式解交织可省约 32 块。若另采用需要每边消息状态的译码算法，还要增加约 39 块（6-bit 密集打包）到 59 块（8-bit）——当前仓库算法不需要这一项。

并行端口是主要风险。若按每个处理 lane 保存私有的两个 LLR 数组，紧凑 H 的总量约为 `37+32p` 块：1 路 69、4 路 165、22 路 741。这个是朴素复制上界，不能据此断言最优 banking 必须这样做；但“理想 bank、不复制”的 69 块下界也尚无无冲突方案支持。实测用简单 `column mod bank_count` 映射时，4 bank 每行最多有 14 条边落在同一 bank，22 bank 时最多 8 条；因此不能假定 4/22 路并行可以无停顿。该统计不排除存在更好的图着色或调度方案。

| 资源 | 紧凑 H | 展开 H | 当前余量与结论 |
|---|---:|---:|---|
| BRAM36 | 69 块（8-bit、单端口容量下界）；多路 banking 未证 | 约 185 块 | 95；紧凑单路有容量空间，展开表不能全放片上 |
| LUT | **未综合** | **未综合** | 19,213；仓库没有译码 RTL，不能给出可信消耗数 |
| DSP | 预计 0 | 预计 0 | 217；现有算法只需比较、加法和符号运算 |

DSP 为 0 是算法实现选择的静态估算，不是综合结果。新增逻辑是否满足 LUT 和时序，也没有证据；当前 WNS 已只有 +0.617 ns。

**DDR 流式展开 H 的带宽量级可接受。** 16-bit 地址每轮搬 `237,599×2 = 475,198 B`；50 轮为 **23,759,900 B（约 23.8 MB）**。若使用固定 22 槽/行，数字为 475,200 B/轮，差 2 B。按板上 DDR3 32-bit、1066 MT/s 的理论带宽 4.264 GB/s，纯 H 传输约 **0.112 ms/轮、5.6 ms/50 轮**。若假设 PL 侧 64-bit AXI、100 MHz，理论接口上限 800 MB/s，则约 **0.594 ms/轮、29.7 ms/50 轮**。这些是带宽推导，不是实测；DMA 效率、仲裁和 LLR 访问未验证。22 路计算可能被 100 MHz 接口喂数速度限制。紧凑 H 则只需约 1 KB 表，不需要每轮搬边地址。

## 4. PL 时延外推与 PC 对照

以下是**外推，不是综合或板测**：100 MHz，按仓库译码循环做一轮扫描最小值/符号、一轮累加消息、一轮 syndrome，再加节点初始化和硬判决。设 `E=237,599`、`N=64,800`，每轮周期估算为 `3×ceil(E/p)+2×ceil(N/p)`，另加一次初始 syndrome。未计 DMA、端口冲突和其他固定开销。

| 并行边数 `p` | 每轮估算周期 | 45 轮估算 | 相对 Python 0.653 s | 相对 C 0.182 s |
|---:|---:|---:|---:|---:|
| 1 | 842,397 | 约 0.381 s | 约 1.7×快 | 约 2.1×慢 |
| 4 | 210,600 | 约 0.095 s | 约 6.8×快 | 约 1.9×快 |
| 22 | 38,292 | 约 0.017 s | 约 37.7×快 | 约 10.5×快 |

PC 的 Python 0.653 s、矩阵解析 0.229 s、45 轮迭代 0.330 s按题给数据；C 0.182 s也是题给本机实测值。本轮在当前 `docs/03-status.md` 和 `docs/benchmarks/` 中没有找到这些 Python 分段和 C 计时的同一轮原始记录。比较也存在计时边界差异：PL 外推不含 DMA，而紧凑 H 不需要 PC 的矩阵解析时间。

据此，**1 路预计能快于 Python 总耗时，但不能快于给出的 C 实测；4/22 路若无冲突、达到 100 MHz，预计可快于二者。** 4/22 路的端口调度、位宽和时序均未证明，不能把该预测当成可交付性能。

## 6. 结论、门槛与工作量

**H 能搬：是。** 上一轮“展开表约 103 块，因此必然装不下”的结论不成立，因为 PCHK 的信息部分与累加器部分都有紧凑生成规则。**紧凑单路、8-bit 固定点状态有 BRAM 容量空间；展开 H 全驻 BRAM 不可行。** 4/22 路译码能否放下并且更快，目前不能定论：端口复制会超过 BRAM 余量，banking、LUT 和时序都需要真实实现证明。

要下结论，至少需要：固定点位宽和饱和规则在现有黄金输入上保持译码输出一致；找到可验证的无冲突读写调度；综合后满足余下 LUT/BRAM；P16 加译码器后 100 MHz 时序仍通过；最后用 DMA 和板端输出完成端到端判据。最可能失败的是 LLR 的多读多写端口冲突，其次是固定点行为偏离软件结果和布线压垮当前时序余量。

粗略估算，RTL 原型、固定点对照和存储调度约需**数个人周**；达到时序收敛、板端验收可能是**数周级**，这是工程量级估计，未验证。当前值得先做的是软件 C 替换和重叠测量；若有独立低延迟需求，再推进 PL 原型。
