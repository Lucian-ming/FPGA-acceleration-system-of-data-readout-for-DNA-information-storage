## 结论先行

按本轮口径，[上传段基准](<<仓库根目录>/docs/benchmarks/bkb220-p16-speed-a-upload.md>) §5 的整轮约 **10.18 s**：水印约 0、读段上传 **0.20 s**、板端 `t_result` **9.33 s**、上位机 LDPC **0.653 s**。旧的上传 3.9 s 数字已作废。

## 1. DDR 搬运账

下表是按现有缓冲区和接口尺寸核算的**业务数据区流量**。读写是对 DDR 中应用数据区的逻辑读写；每轮输入为 103,616 条。

| 阶段 | DDR 读 | DDR 写 | 依据 |
|---|---:|---:|---|
| 原始水印接收 | — | 10,128 B | 客户端传输长度；其中 10,125 B 有效 |
| 水印展开 | 10,125 B | 191,400 B | PS 从原始水印展开 50×957 个 32-bit 符号 |
| Stage1 水印预载 | 191,400 B | — | MM2S 读取展开区，送入核内水印 BRAM |
| 读段接收 | — | 4,144,640 B | 103,616×40 B |
| Stage1 | 4,144,640 B | 4,973,568 B | MM2S 读段输入；S2MM 写 103,616×48 B 结果 |
| Voter | 4,973,568 B | 10,128 B | 逐条读 Stage1 结果；写 1,266×8 B，末拍含填充 |
| PS 水印差分 | 20,250 B | 10,125 B | 读 Voter 输出和原始水印各 10,125 B，原位写回 10,125 B |
| Decoder | 10,128 B | 8,104 B | 读 1,266×8 B；写 1,013×8 B，末拍含填充 |
| 结果发送 | 8,100 B | — | PS 从结果区读取有效码字 |

**静态推导合计：DDR 读 9,358,211 B，写 9,348,093 B，总计 18,706,304 B（约 17.84 MiB）。** 这是应用数据区账，不是物理 DDR 总线的完整计数。它不包括 Ethernet RX/TX 缓冲区、临时接收缓冲、SG 描述符的抓取与状态回写，以及缓存行实际回写流量；因此不能把它称为实测的完整 DDR 流量。

水印和输出区的填充也已区分：Stage2 输出 10,128 B 中 10,125 B 是有效位流；Decoder 写 8,104 B，其中 8,100 B 是返回给主机的有效结果。

**带宽判断：现有证据不支持“DDR 带宽或延迟是当前限制项”。** 本轮 `t_result` 为 9.33 s；PL 占比约 87.8%（约 8.2 s），PS 可归因工作约 194 ms。PL/PS 分解是推导，PS 数字来自固件埋点，不是 DDR 硬件周期计数。平均业务数据区流量约 2.0 MB/s，但这是跨整段墙钟时间的平均值，不能当成 DDR 实测吞吐。现有基准没有 DDR 带宽或延迟计数器，故严谨结论是：**未测得 DDR 瓶颈；按数据量和 Stage1 计算占比推断，DDR 不像当前主瓶颈，但不能声称已用硬件计数器排除所有 DDR 等待。** 依据见[精细时间预算](<<仓库根目录>/docs/benchmarks/bkb220-p16-time-budget.md>) §3、§6。

## 2. 减少 DDR 搬运有没有真实空间

- **Stage1 输出绕过 DDR、直接进入 Voter：** 可省掉 Stage1 写入和 Voter 再读取的逻辑流量，共 **9,947,136 B**。这是流量减少，不是省时承诺；当前没有这两段的独立 DDR 等待测量，**可确认的省时为 0 s**。需要改 PL 数据接口、背压和任务完成控制，且可能改变现有 Stage1 DDR 取证路径。

- **读段直通，省去 `DDR_READS_BASE` 暂存：** 现有应用区有读段写入和 Stage1 再读取，共 **8,289,280 B**。零拷贝可以避免部分显式暂存，但数据仍需在可供 MM2S 读取的内存中驻留；Ethernet 接收缓冲仍会产生流量。实现需解决 pbuf 生命周期、TCP 缓冲、记录对齐和 DMA 完成同步。上传段已经只有 0.20 s，**最大端到端收益不超过这 0.20 s，且零拷贝的实际收益未测**。

- **合并 Voter、PS 差分与 Decoder：** PS 差分这一步涉及约 **30,375 B** 的读写；Voter 和 Decoder 之间还各有约 10 KB 的缓冲流量。数据量很小，合并后可省的时间没有独立测量。若把水印异或移入 PL，必须逐位保持 LSB-first 和现有判据。当前**不给时省记账**。

- **BD 环和 cache 策略：** [精细时间预算](<<仓库根目录>/docs/benchmarks/bkb220-p16-time-budget.md>) §6 实测的 cache flush+invalidate 合计约 **58 ms**，BD 提交/回收合计约 **102 ms**；这些子项与 `TX_STREAM` helper 计时存在包含关系，不能相加。PS 侧全部可归因工作约 **194 ms**，这是这类 PS 优化的总上限，不代表可全部回收。直接取消 DMA 所需的 cache 一致性操作可能造成错误；扩大 BD 环本身也没有可证实的省时量。**当前对这两项记账收益为 0 s。**

因此，虽然可以在结构上减少数 MB 的 DDR 读写，**搬运字节数不能直接换算成墙钟收益**。尤其不能把 9.95 MB 或 8.29 MB 的减少写成秒级加速。

## 3. 板子能否边收边算

**可以设计，但未验证；可隐藏的上传时间最多约 0.20 s。** 读段上传已从旧基线压到 0.20 s，远小于 9.33 s 的板端处理段。即使完全重叠，单轮也只能从约 10.18 s 降到约 9.98 s；协议和流控开销还可能抵消部分收益。

现行协议要求先 `CONFIG`、水印和全部 `BATCH`，再由 `POST` 校验收到的总条数并启动流水线。Stage1 的输入来自 DDR 读段区，固件还会预置输出 RX BD 后再启动。边收边算需要至少做到：

1. 明确开始与结束语义，允许读段尚未全部到齐时启动 Stage1；
2. 只提交已完整写入 DDR 的 64 条记录帧，正确处理不同 `PKT_BATCH` 边界；
3. 按**在飞帧数或 DMA 完成事件**发放输入额度，保证输出 BD 可用且不会读未写数据；
4. 收到结束标记后核对总数，再按原样完成 Stage2、差分和 Stage3。

`docs/05` 记录的两次失败与新提案**不是完全相同的机制**：失败的是批量推进流水线时把 RX 提交到 `submitted=640 > ring free=512`，Stage1 停顿约 30 s；新提案可以用受控的上传生产者—Stage1 消费者额度来重叠。但二者仍共享 RX BD 环和 DMA 资源，过量提交仍会触发同类故障。`ring free` 不能单独作为安全额度；应跟踪在飞帧或 DMA 完成。该失败记录是机制参考，不能当成新方案必然失败或已经可行的证据。

若保持记录顺序、帧边界、总数、Voter 阈值和数据内容不变，算法判据原则上可保持不变；仍必须通过同一全量 SHA `fcd0cf90…f2c3` 及现有分级检查。若 Voter 也提前消费未完成的 Stage1 数据，就超出了单纯上传重叠，需要另行设计和验证。

## 4. “发送与处理同步”具体能省多少

- **若“发送”是上位机上传读段：** 这是上一节的方案，实测上传为 0.20 s，理想重叠上限 **0.20 s**。当前上传段已很短，按实测账性价比不高。

- **若“发送”是板端回传 8,100 B 结果：** 固件 `send_result` 的实测约 **17.2 ms**，包含在 `t_result` 的 POST 至完整结果收齐时间内。若能让 Decoder 产出部分结果时就开始发，省时上限约 **17.2 ms**；实际收益未验证。它要改 Decoder 输出、cache 可见性和 TCP 缓冲的所有权交接，**不值得单独承担这类改动**。

两种“发送”不能把 0.20 s 和 17.2 ms直接当成已实现收益相加；前者是主机上传阶段，后者是板端 `t_result` 的末段。

## 5. 其他重叠机会

- **Voter 与 Stage1 重叠：** 当前 Stage1 完成后才启动 Voter。无睡眠埋点中 `VOTER_WAIT` 记录约 **602 ms**，但同一基准明确说明无睡眠下的函数级计时受高频轮询影响，不能作为可兑现的省时上限。若改为逐块流入 Voter，理论上可隐藏部分后处理时间；Voter 当前从 DDR 按任务总数读取，需要改成安全的增量输入与结束控制。**收益未验证，602 ms 只能作为探查线索，不能报成预计收益。** 若严格保持记录次序及投票语义，最终 SHA 判据可以不变；DDR 中间结果的取证方式可能要调整。

- **Voter 与 Decoder 重叠：** 当前 PS 还要先对 10,125 B 共识结果异或水印，Decoder 才读取 10,128 B 输入。要重叠需把差分下沉或增加流接口。两段硬件的现行独立耗时在本轮基准中没有可用分解，**省时无法可靠量化，当前记 0 s**。

- **上一轮 LDPC 与下一轮板端任务重叠：** 这是当前最有账可算的额外机会。[精细时间预算](<<仓库根目录>/docs/benchmarks/bkb220-p16-time-budget.md>) §5 仍把它列为开放项，LDPC 实测约 **0.653 s**，上传基准中的 A/B 沿用此数、未在同小时重测。它能减少多轮总墙钟约 **0.653 s/轮间**，不减少单轮响应延迟；要改 `run_g3.sh` 的逐轮调度并保留每轮结果，循环末等待 LDPC 完成。

- **结果回传与下一轮任务重叠：** 单看回传只有 17.2 ms；若同一 DDR 结果区和连接状态未隔离，提前开始下一轮会覆盖或混淆结果。需要独立缓冲和连接管理，收益远低于 LDPC 跨轮重叠，现无量化依据。

## 6. 排序与明确的零收益项

按**已知收益、风险和改动面**排序：

1. **多轮时优先评估 LDPC 与下一轮重叠：约 0.653 s/轮间。** 这是有数据支撑的吞吐机会，改验收脚本即可；单轮延迟收益为 **0 s**。
2. **Stage1 与 Voter 重叠：可能有价值，但收益未验证。** 602 ms 的无睡眠 `VOTER_WAIT` 不是可承诺的收益。涉及 PL 数据接口和增量控制，先补有效阶段计时再决定。
3. **上传与 Stage1 重叠：最多约 0.20 s。** 改协议、固件状态机和 BD 流控；风险明显高于当前上限，按现有账不优先。
4. **减少 DDR 搬运：当前可证明省时为 0 s；PS 优化总上限约 0.194 s。** 主要 DDR 旁路改动复杂，带宽瓶颈未被测出。
5. **结果发送与 Decoder 重叠：最多约 17.2 ms。** 改动面不小，单独做不值。

**明确记为 0 收益（当前没有证据证明能缩短总墙钟）：** 单纯扩大 BD 环；仅合并 DDR 数据区而不改变关键路径；单独融合几 KB 的 Voter/Decoder 中间缓冲。它们可能减少字节数或避免故障，但不是已证实的加速。

本次只做了静态文档和代码核对，没有运行测试、仿真或板卡任务。未完成项是实际 DDR 带宽/延迟测量、Stage2/Stage3 有效阶段计时，以及任何流式或零拷贝改动的全量 SHA 验证。
