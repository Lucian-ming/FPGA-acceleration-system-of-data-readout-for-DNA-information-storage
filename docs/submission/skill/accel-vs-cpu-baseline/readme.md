# 技能包：给加速器找一个「打得过也说得清」的软件基线

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

做了 FPGA 加速，要回答「到底快了多少」。这件事有两个坑：

1. **基线太弱**：拿未优化的 Python 或单线程朴素实现当对照，加速比很好看，但评委一问就塌；
2. **基线不可比**：拿桌面/笔记本 CPU（几十瓦、多核、宽 SIMD）对比嵌入式 FPGA，
   赢了不服人、输了不甘心，而且**回答不了「为什么要用 FPGA」**。

这份技能包给的是一套**分层基线**的做法，以及把「同片 CPU」作为主基线的理由和实现框架。

## 使用方法

### 1. 至少报三条基线，而不是一条

| 基线 | 回答的问题 | 怎么做 |
| --- | --- | --- |
| **同片 CPU（主基线）** | 把这段计算放进 PL，比留在同一颗 SoC 的 ARM 上快多少 | 同一块板、同一份数据，PS 裸机跑优化过的 C |
| 优化过的桌面 CPU 单核 / 多核 | 和通用计算机比处在什么位置 | 同一算法的 `-O3` 实现，多核用 OpenMP |
| 未优化参考实现 | 只用来验证正确性，**不作为加速比分母** | Python / 朴素 C |

**同片 CPU 是最有说服力的那条**：器件相同、供电相同、数据通路相同，
差别只有「算在 PS 还是算在 PL」，正好就是你的设计决策本身。

### 2. 软件基线必须是「认真优化过的」

否则加速比是虚的。至少做到：

- 开 `-O3`，指定目标架构（`-mcpu=cortex-a9 -mfpu=neon`）；
- 数据布局对齐硬件的做法（例如位平面 + 按位运算），而不是逐元素比较；
- **检查编译产物**：ARMv7 上 `__builtin_popcountll` 会退化成库函数调用，
  必须用 NEON 指令自己写，再用 `objdump` 确认真的生成了 `vcnt`。
  没确认过的「优化实现」，很可能慢了好几倍，让你的加速比虚高。

### 3. 板上跑软件基线的框架（不必改生产固件）

参考模板：[`baremetal_baseline.tcl.in`](baremetal_baseline.tcl.in)。流程是：

```text
主机准备数据 ──► XSDB 复位 PS + ps7_init ──► dow -data 把数据写进 DDR
      │                                            │
      │                                     dow 裸机 ELF ──► con（跑）
      │                                            │
      └── 同一份 C 在主机编译出参考答案        轮询 DDR 里的完成标志（mrd -force）
                       │                            │
                       └──────► 逐条比对 ◄──── 读回结果与计时
```

要点：

- **写一个独立的裸机程序**，和生产固件分开：不碰生产代码就不会引入回归；
- 计时用硬件计数器（`XTime`），只计算法本身，准备阶段另计；
- 结果写回 DDR 之前 **`Xil_DCacheFlush()`**：调试器读的是 DDR，不是 CPU 缓存，
  不刷新就会读到旧数据；
- **同一份 C 文件在主机上再编译一次**当参考答案，逐条比对（分数、位置等全部字段），
  全部一致才采信耗时。**只报速度不报正确性的基线没有意义**；
- 轮询完成标志用 `mrd -force`，避免反复 `stop` 打断计时。

### 4. 报告口径

- 统一到「每单位工作量」（每条记录、每帧、每样本），而不是总时长；
- 注明重复次数、取中位数还是均值；
- 给出对方的核数、频率、编译选项；
- 未测的项目（比如功耗）**明确写「未测」**，不要用估算填表。

## 失效条件

- 同片 CPU 基线只在 SoC 类器件（Zynq / MPSoC / Versal）上成立；纯 FPGA 板没有这条基线。
- 若加速核与 CPU 跑的**不是同一个算法**（例如硬件做了近似、剪枝），加速比不可比，
  必须先说明算法等价性，或改用「达到同等结果质量所需时间」作为口径。
- 本框架测的是**计算本身**。端到端还包含传输、DMA、后处理，两者不要混用。
- 裸机单核结果不能直接乘以核数当多核结果，多核要实测。

## 已验证效果

本项目旧板 **XC7Z010** 于 2026-09-22 的历史实测（SE150 数据集；不是 BKB220 新板 CPU 基线）：

| 实现 | 每条记录耗时 | 全量任务 |
| --- | ---: | ---: |
| 同片 ARM Cortex-A9 单核（裸机、-O3、NEON popcount） | **12.10 ms** | 约 1,254 s（外推） |
| PL 加速核（4 路 @100 MHz） | **0.2451 ms** | **25.69 s（实测）** |
| 项目 48 核服务器参考实现（Xeon Gold 5220R ×48 @2.20 GHz） | — | 675 条 / 41.07 s（滑动相关 **16.6 条/s**） |

- **同片对比：PL 快约 49 倍**，这是最能说明「为什么要做这个加速器」的一条；
- **CPU 基线已按 2026-10-20 要求统一为项目 48 核服务器**；旧的笔记本 16 线程数据已删除。该基线与板端 `t_result` 的输入规模、计时边界不同，**不相除、不写成严格加速比**；
- 正确性：1,024 条读段的结果与主机参考**逐条完全相同**，之后才采信耗时；
- 稳定性：16 / 256 / 1,024 三档测出的每条记录耗时分别是 12.086 / 12.101 / 12.103 ms。

### BKB220 P4 / P16 的边界

2026-10-12 新板阶段样本给出同板 P4/P16 的 `t_result` 对照：全量 P4 为 26.51 s，P16 为 8.61 / 8.71 / 8.61 s。随后正式六档矩阵已完成，见 `bkb220-p4-p16-performance-matrix.md`；该早期样本保留为历史测量，不作当前绝对值。上传转正记录的最新同小时参考 `t_result` 为 9.33 s。以上均比较 PL 配置且不含上传与 LDPC，**不能替代同片 ARM 基线**。上表 12.10 ms/记录的 ARM 数字来自旧板；没有同一输入、同一口径的新板 ARM 重测前，不得把它与 BKB220 P16 时间拼成严格公平加速比。

模板 `baremetal_baseline.tcl.in` 只负责驱动板端程序、轮询状态和导出结果。它不会自行证明结果正确；主机端逐字段比较器必须在任一字段不一致时返回非零，超时或板端错误状态也必须判失败，速度只有在这些检查通过后才能进入基线表。

## 来源

来自一次「基线不可比」的教训：项目早期的对外材料写过「相较传统 CPU 方案约三个数量级的加速」，
而后来按同一口径实测，发现连优化过的桌面 CPU 多核都打不过。
返工之后确立了两条规矩：**基线必须是优化过的**，**对照必须同口径**；
再往后才想清楚，嵌入式加速器真正该打的那条基线是**同一颗芯片上的 CPU**。
