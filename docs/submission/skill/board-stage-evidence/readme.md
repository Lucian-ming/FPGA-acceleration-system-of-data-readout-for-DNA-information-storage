# 技能包：端到端结果对了，不等于每一级都对——逐级取证与判据鉴别力

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

多级流水的加速系统（采集 → 预处理 → 计算 → 后处理），最终输出能和参考结果对上。
问题是：**这能证明什么？**

- 它能证明「这一次、这组参数下，整条链路是通的」；
- 它**不能**证明每一级都正确——上游的错误常常被下游吸收掉（投票、纠错码、滤波、量化）；
- 更危险的是：某些缺陷**注回去，最终结果仍然完全不变**。此时端到端判据对这个缺陷是瞎的。

## 使用方法

### 1. 每一级都留一份中间结果，并各自有参考

让每一级把输出写进可读位置（DDR 固定区间 / 文件），再用调试器或脚本导出，
与纯软件黄金模型逐级比对。典型判据表：

| 级 | 比什么 | 通过标准 |
| --- | --- | --- |
| 预处理/展开 | 逐字节 | 100% 相同 |
| 主计算 | 关键字段（分数、位置） | 分数 100% 相同；位置允许落在**并列最优集**内 |
| 中间聚合 | 逐位 | 差异数 ≤ 已知容差，且容差有出处 |
| 最终产物 | 哈希 | 逐位相同 |

**写判据时不要偷懒用「全绿」掩盖差异**：本项目写过「Stage1 4011/4096 逐位相同」，
读者只会觉得有 85 条错了；实际是分数 4096/4096 全同、85 条位置落在同分并列集内。
**差异要写清楚是什么、为什么允许**，否则答辩时会被追着问。

### 2. 给判据做故障注入，证明它会红

**没红过的判据不算判据。** 做法：把一个已知缺陷注回去，看判据是否变红。

如果注回去判据仍然全绿，说明这条判据对该缺陷**没有鉴别力**，必须另找判据。

### 3. 特别当心「结构性参数错了但结果不变」

常见于几何参数、步长、索引起点这类**只影响中间表示、不影响下游统计**的参数。
对这类参数要单独找一个**对它敏感**的判据（例如展开后的参考数据本身的哈希），
而不是靠最终结果。

### 4. 重复任务要能自证「状态真的被清干净」

连续跑两轮同样的任务、得到同样的结果，**不能**证明中间状态被复位了——
如果累加器只增不减、判决只看符号，残留值往往不会改变结论。
正确做法：**第一轮故意用不同的参数「弄脏」状态**，第二轮用判据参数跑；
两轮的原始回传若完全相同，反而说明判据没有鉴别力，应当判失败。

## 失效条件

- 逐级取证需要中间结果可读。若某一级只存在于片内 FIFO，就得先加一条导出通路（或计数器）。
- 导出动作本身不能干扰运行：**跑完再读，不要中途复位**，否则读到的是被清掉的中间态。
- 容差必须有出处（算法允许的并列、数值精度），不能为了让判据变绿而临时放宽。
- 故障注入要能安全回滚，建议用编译开关或独立分支，不要手改生产源码。

## 已验证效果

本项目的四级取证（每次板级验收自动执行）：

```text
展开参考数据   47,850 / 47,850  逐位相同
主计算         4,096 / 4,096    分数相同；4,011 位置相同，其余 85 条在同分并列集内
中间聚合       1,265 / 1,266    逐位相同（差异在容差内）
最终产物       图片 SHA-256 逐位相同
```

**鉴别力实测（主机黄金模型范围）**：在 `tools/make_golden.py` 这条主机侧链路，
把「几何参数写死成另一种读长」的缺陷注回去，15 个产物里有 14 个逐字节不变，
最终图片哈希也不变；这里 Stage1 直接在整条 `ref` 上滑窗，几何只影响水印区域展开。
所以主机链路唯一敏感的判据是展开后参考数据的哈希。

**板上范围不同**：`wm_regions` 预载到 BRAM 后是 Stage1 实际比较的对象，板上几何错误应影响输出。
因此不要把主机黄金模型的“图片哈希不敏感”结论外推到板上；板上仍应同时检查几何/展开中间值、逐级 DDR 导出和最终哈希。

**另一次**：曾用「两轮结果相同」证明累加器被复位，后来发现该判据恒绿——
因为累加器是带饱和的符号累加，残留值不改变符号判决。改成「第一轮用不同阈值弄脏」后，
旧实验两轮原始回传相差 24,839 / 64,800 bit，判据这才真正有了鉴别力。该数字是历史实验，不作为当前 BKB220 的复位判据。

### 把逐级取证扩展到「新载荷」（2026-10-16）

原版逐级取证的参考向量是**针对某一个固定载荷**做的。想让它覆盖新载荷，要按下面做，
**每一步都有坑**：

#### 1. 参考向量必须按「与板端任务完全相同的参数」生成

两处最容易错：

- **记录数**：中间级（聚合/纠错）是**跨记录投票**出来的，记录数变了结果就变。
  参考向量与板端任务必须用**同一个记录数**。
- **判决门限**：门限是个**比例参数**映射出来的**整数**（本项目里 `0.45 × 150 = 67`，
  要得到 65 就得用 `0.435`）。**用错门限生成出来的参考向量，在对应档位上会直接译不出来**——
  注意：这**不是**"参考向量错了"，是**参数配错**，症状却长得一样。

#### 2. 生成完，**必须独立验证它对应的确实是那个载荷**

做法：把参考向量里的**期望中间结果**喂回真正的解码链路，看它解出来的最终产物哈希
是否等于该载荷的已知哈希。

⚠️ **这个验证方法本身必须先拿一个已知正确的样本做对照实验**：
先用它去还原**已有的、已知哈希的**那份参考向量，必须得到那个已知哈希。
**对照不过就不要相信后面任何结论。**

本项目在这里**连续错了两次**：手工推导"取码字的前 N 个字节"、以及
"取码字校验位之后的部分 + 自定义字节序"，**两次都不对**。
原因很朴素：中间结果里存的是**含噪的接收比特**，不是干净码字，
所以必须走真正的解码流程。**别自己发明提取方式，直接用工程里已经验证过的解码器。**

#### 3. 参考向量的查表键可能不够用

按「最终产物哈希 + 读长」查参考目录，**假设了"一个载荷哈希对应一份参考向量"**。
但这个假设会破：**同一个载荷在不同噪声条件下跑两次任务，载荷哈希完全相同，
而读段不同 ⇒ 中间级参考向量完全不同**。此时查表返回哪一个都是错的，
拿错了就会**产生假 FAIL**——这比"未取证"更糟。
⇒ **发现这种碰撞时，宁可让该项显示"未取证"，也不要用可能拿错的参考去判。**

#### 4. ⚠️ **不同层的容差不同，不能拿一层的"过"去解释另一层的"不过"**

这是本次最有价值的一条。现象：**中间级 4/4 全过，端到端哈希却不过。**

- 中间级判据**容许**极小残差（本例 0.01% 的比特差，判 PASS，且这属于已知的并列打破现象）；
- 端到端哈希**一个字都不容**。

两者**都没错**——它们量的不是同一件事。所以：

> **当不同层的判据给出矛盾结论时，第一步不是"哪层坏了"，而是"两层看的到底是不是同一个东西"。**

本项目的矛盾最后定位到**载荷提取方式**：输入是二进制载荷，而工具默认按图片的
"文件结束标记"去截长度——**板端码字一直是对的**（架构判据过了、中间级也全过），
**错的是把它还原成载荷的那一步**。改对参数后，同一次板端状态立刻全绿。

⇒ **实操结论：看到"下层过、上层不过"，先怀疑长度/格式/提取语义，不要先怀疑硬件。**

### BKB220 P16 当前实测

2026-10-12，BKB220 / `xc7z020clg400-2` / SE150 / P16（16 路、`PIPE_TREE=1`）完成 smoke、全量三轮及连续脏轮/干净轮测试：

- smoke：4096 条板端记录，图片 SHA-256 `fcd0cf90…f2c3`，四级取证通过；
- 全量：每轮 103,616 条记录，三轮图片哈希一致，四级取证通过；
- 状态复位：先以 `score_min=0` 执行弄脏轮，再跑判据轮；两轮回传相差 **1500/64800 bit**，以此证明扰动确实进入状态，随后干净轮结果才可采信。

这些早期结果证明列出的 P16 测试通过；后续 P4/P16 六档矩阵、v1/v2 数据集对照和 2 h 长稳已有单独记录。v2 有 8 个 challenge 例仍失败。**2026-10-16 更新**：v2 的 `score_min=67` 已板测（26 通过 / 16 安全失败 / **0 例静默给出错误字节**）；8 h 长稳已跑满（1750 轮、0 失败）；新载荷四级取证已备好 5 份参考向量、并在其中 1 个载荷上完成板端逐级验证（4/4 通过）；**功耗仍未测**（缺仪器）。摘要见 `docs/board/bkb220/migration-source-table.md` §15–§18 及对应 benchmark；原始板端运行留证位于仓库外的 `D:\bkb220_board_smoke\g3_runs\`，不能称为已入库日志。

## 来源

三件事：

1. 一次上板，最终图片正确，但后来发现某一级整体错位了一条记录——
   下游的多数投票把它吸收了，端到端判据没红；
2. 一次故障注入实验发现「改了几何参数，14/15 个产物一字不变」；
3. 一次把恒绿的判据当成了通过标准，写进了文档，几周后才被推翻。

共同点：**它们都不产生错误的最终答案，所以整套验证金字塔对它们失明。**
