# 技能包审阅与补齐记录

审阅日期：2026-10-12。范围为本目录入口和 8 个技能包 README、两个随包脚本；事实核对以 `docs/03-status.md` 当前断点、`docs/board/bkb220/migration-source-table.md` §9–§15、`docs/benchmarks/bkb220-p4-p16-100mhz-build.md`、`docs/05-implementation-plan.md` 与 `tools/readme.md` 为准。旧板记录作为历史保留，不覆盖当前 BKB220/P16 状态。

## 逐包结论

### 1. `board-bringup-debug`

- **问题 / 触发**：USB、JTAG、串口或网口不通时，按 USB 枚举→驱动→工具→应用分层定位；触发条件明确。
- **步骤**：Windows USB VID 查询和 XSDB/JTAG 查询可以照做；原来的网口步骤只有主机网卡状态与 ping，不能定位 PS GEM/PHY。
- **会红吗**：USB/JTAG 有明确的“枚举不到 / target 为空”观察结果；原网口步骤没有板端 PHY 判据，主机适配器 `Up` 容易被误当成板端通过。
- **时效性**：原始案例是 2026-09-22 的旧板 XC7Z010，已标成历史。新增 BKB220 的 `ps7_init`、ENET0 MIO、MDEN/MDIO 完成位、PHY ID、锁存低 link 位与 CAPS/TCP 分层检查；明确区分探针配置和正式烧录包。
- **结论**：核心分层方法可复用；BKB220/MDIO 缺口已补。

### 2. `fpga-timing-probe`

- **问题 / 触发**：改 RTL、加并行度或换器件前评估资源和目标频率；适用场景写清楚。
- **步骤**：Tcl 参数、顶层和 HDL 文件参数可照做；之前的示例器件是 XC7Z020 `-1`，不匹配当前 BKB220 的 `xc7z020clg400-2`，日志路径也未明确，现已改正。
- **会红吗**：原脚本即使没有时钟或 WNS 为负仍会 `exit 0`。已改为 `SYNTH_IMPL=1` 时无时钟/无 setup 或 hold 路径、或 WNS/WHS 为负均 `exit 2`；综合-only 的负 slack 明确只是估算，不作为接受判据。资源仍只报告、不自动套项目预算，README 已要求先声明余量阈值。命令示例把 Vivado `.log/.jou` 放到独立 `logs/vivado/<run-id>/`。这次改动未重新运行 Vivado，只做了静态阅读。
- **时效性**：旧 XC7Z010→XC7Z020 OOC 表已注明是历史摸底。新增 BKB220 完整 route 结果：P4 15,447 LUT、WNS/WHS +0.680/+0.036 ns；P16 33,987 LUT、+0.617/+0.017 ns，均 100 MHz、失败端点 0。OOC 数字不与整机数字混用。
- **结论**：脚本与说明已按当前器件和可判红要求补齐；exit 0 只表示 OOC 判据通过，不代表整机或板端通过。

### 3. `bottleneck-attribution`

- **问题 / 触发**：PS/PL/DMA/网络性能不明时，先做分档、分段计时和对照实验；触发条件及步骤清楚。
- **步骤**：规模拟合、独立计数、去除嫌疑项、对照理论周期均可照做；正确性哈希被要求随性能对照检查。
- **会红吗**：有“总时长变化”和正确性判据，但没有统一自动化容差；应由实验报告预先声明阈值与重复策略，不能把“逐毫秒不变”脱离测量精度照搬。
- **时效性**：200 µs、旧固件和 0.2451 ms/记录数据已标为旧板 XC7Z010 历史结果。新增 BKB220 P4/P16 全量 `t_result` 26.51 s 对 8.61/8.71/8.61 s（约 3.05 倍），并注明不含上传与 LDPC、不是整轮。六档正式性能矩阵仍待完成。
- **结论**：方法有效；补充了新板数据和性能声明边界。

### 4. `accel-vs-cpu-baseline`

- **问题 / 触发**：需要报告 FPGA 加速比时建立同片 ARM、优化桌面 CPU 与参考实现三层基线；触发清楚。
- **步骤**：同数据、编译优化、NEON 反汇编确认、计时和逐字段比较均写明；XSDB 模板给出了 DDR/Cache 顺序。
- **会红吗**：README 要求所有字段一致才采信；模板此前对超时和板端错误状态仍会继续导出。已改为超时或 `0xAB5E0BAD` 时非零退出。模板本身仍不做主机逐字段比较，比较器必须将不一致转成非零结果；本轮未连接板卡或运行 XSDB。
- **时效性**：12.10 ms ARM 与约 49 倍结果是 XC7Z010 历史数据，不是 BKB220 当前 CPU 基线。已加说明：BKB220 P4/P16 `t_result` 是 PL 配置比较，不能冒充同片 ARM 对照；同板六档矩阵仍未完成。
- **结论**：历史基线边界已澄清，模板状态门禁已补；可复用的主机逐字段比较器仍是缺口。

### 5. `board-stage-evidence`

- **问题 / 触发**：多级数据通路端到端结果正确，但担心中间级错误被投票、纠错等机制吸收；触发条件非常明确。
- **步骤**：逐级导出、参考比较、故障注入、脏轮→干净轮可照做；给出了中间结果和容差写法。
- **会红吗**：要求故障注入必须使判据变红、复位用不同参数验证，具备鉴别力原则；每个新设计仍需选择自己的注入点。
- **时效性**：原来的“14/15 不变、图片哈希不变”只适用于主机黄金模型，先前表述容易被误解为板上也不敏感。已限定主机 `make_golden.py` 范围，并说明板上 `wm_regions` BRAM 是 Stage1 实际比较对象。新增当前 BKB220 P16 smoke、全量三轮、四级取证及 1500/64800 bit 脏轮鉴别力证据；原始运行目录明确标作仓库外。
- **结论**：鉴别力边界和新板 P16 证据已补。

### 6. `ip-packaging-hygiene`

- **问题 / 触发**：IP 打包、仿真和综合可能引用同名模块的不同变体；触发明确。
- **步骤**：`component.xml`、清单、回归引用、零引用文件与删除出口都写清了。静态门禁要求显式 HDL 文件，不适合通配源集，失效条件已注明。
- **会红吗**：规则明确映射到 `check_ip_packaging.sh` 并接入 `run_sim.sh`；仍须在每次修改后运行并保留退出码，文档自身不是门禁。
- **时效性**：旧 2-way/4-way 事故保留为历史。已删除没有依据的“此后一年内”时长说法；补充当前 P4（4/0）和 P16（16/1）身份必须由 `component.xml` / `PACKAGED_VARIANTS.txt`、回归源集和 manifest 三方核对，并提醒 CAPS/TCP 分不出 P4/P16。
- **结论**：已有规则有效；新增 P16 识别判据。

### 7. `ai-agent-collaboration`

- **问题 / 触发**：多会话共用看板或 Git 暂存区时，进度不可见、提交内容串扰；触发、看板字段、路径限定提交步骤都清楚。
- **步骤**：脚本动作与 Git 写法可照做；真实使用还要按仓库规则指定唯一 Git 写入者。
- **会红吗**：`agent_view.sh` 对必填字段有硬校验；“带路径 commit”是 Git 命令约束，不是自动检测。需要交叉检查提交范围和最终 `main...origin/main`。
- **时效性 / 打包问题**：AI 协作技能目录里没有 `agent_view.sh`；README 却把它列为附件，并使用 `./agent_view.sh`。已改为指向 `tools/agent_view.sh` 唯一源码，并明确技能目录单独复制时脚本不会随包提供。为避免制造第二份脚本，本轮没有复制源文件。
- **结论**：方法与本轮 Git 规则一致；作为独立技能目录仍缺可直接运行的看板脚本，需 main 决定比赛包是否另行包含仓库 `tools/agent_view.sh`。

### 8. `claims-ledger`

- **问题 / 触发**：估算被写成实测、旧结论散落复用、答辩口径不一致；触发明确。
- **步骤**：两张表、配置范围、实测/历史/外推/估算分级与改结论同步更新均可照做。
- **会红吗**：台账是人工门禁，没有自动检查；要求对外发布前逐项核对，但缺少机器校验。新增证据路径必须区分受版本管理摘要、忽略的 `logs/` 与仓库外材料。
- **时效性**：旧 CPU 与旧硬件例子仍可作历史教学，不能代表新板；新增 BKB220 P16 可说/不可说样例，限定 8.61 s 是 `t_result`，不含上传、LDPC，也不是正式六档矩阵或 CPU 加速比。
- **结论**：证据分级方法有效；增加当前 P16 口径与证据交付状态纪律。

2. **高：裸机基线缺主机逐字段比较器。** 模板现在能对超时和板端错误码返回非零，但无法自行证明每条结果正确。补齐时要基于实际结果二进制布局，比较全部字段并对错项非零退出；布局未核实前不凭空造比较器。
