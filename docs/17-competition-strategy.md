## 1. 必须先接受的结论：加速叙事已经死了

项目名为「FPGA acceleration system」，但**用本项目自己的实测数据外推，它在这块芯片上永远追不上对照 CPU**。

### 1.1 定量外推（全部基于已有实测，无估算成分）

板端实测模型（`docs/benchmarks/measured_cpu_vs_fpga.md` §3.3）：

```text
T_board = 4.25 s + 0.58 ms × N_records        N_records = 2 × N_source_reads
其中 0.58 ms = 0.470 ms(Stage1 比对) + 0.11 ms(S2MM DMA + DDR 回写)
```

4-way 只加速 0.470 ms 那一项（实测 1.929x，`docs/benchmarks/stage1_4way_ip_integration.md` §6.1），
即 `0.470/1.929 + 0.11 = 0.354 ms/记录`。据此外推：

| 场景 | FPGA 吞吐 | CPU 单核 1,364.9 | CPU 16 线程 14,003.1 |
|---|---:|---|---|
| 8,192 读段 2-way（**实测**） | 591 reads/s | 慢 2.31x | 慢 23.7x |
| 8,192 读段 4-way（外推） | 816 reads/s | 慢 1.67x | 慢 17.2x |
| 全量 51,781 读段 4-way（外推） | 1,267 reads/s | **仍慢 1.08x** | 慢 11.1x |
| 全量 4-way（2026-09-10 按常数重算） | ~~1,368 reads/s~~ | ~~打平 1.00x~~ | — |
| **全量 4-way（2026-09-11 板端实测外推）** | **1,055 reads/s** | **仍慢 1.29x** | 慢 13.3x |

> **⚠️ 2026-09-11 修正：上面划掉那一行是错的。**
> 它按「Stage1 占每记录成本 81%」外推，而 **4-way 上板后实测 Stage1 只占 37.1%**
> （由 2-way/4-way 两条板端斜率反解，见
> [`measured_4way_board.md`](benchmarks/measured_4way_board.md)）。
> 板端每记录成本比实测 **1.218x**，而非核心加速比 1.929x——
> Amdahl 上限 `1/(0.629+0.371/1.929)=1.22x`，与实测吻合。
> **4-way 上板后仍打不平单核 CPU，比原先的估计更差。**

**最致命的一条**：CPU 16 线程跑完全量只要 `51,781 / 14,003.1 = 3.70 s`，
而板端**光固定开销就是 4.25 s**。

> 即使 Stage1 速度为无穷大、比对不花任何周期，端到端也追不上多核 CPU。
> **这不是优化问题，是架构层面的判死。**
>
> **2026-09-10 实测加强**：固定开销实测为 **5.284 s**（见 §3.0），
> 比原先引用的 4.25 s 更大，与 3.70 s 的差距进一步拉开。

### 1.2 为什么会这样：这是器件级差距，不是设计不好

Stage1 是全局滑窗互相关——**天生适合 FPGA 的完美并行负载**，而 FPGA 仍然输。原因很简单：

- XC7Z010 只有 **17,600 LUT**；
- i5-13500H 有 AVX2（256-bit SIMD popcount）× 16 线程。

两边跑的是**同一种暴力算法**，比的就是原始算力。**17,600 个 LUT 打不过一颗现代 CPU。**
承认这一点，比再做一版展开有价值得多。

## 2. 已证伪：不要再投入的方向

### 2.1 ❌ Stage1 继续展开（8-way / 128×4 / 二维展开）

（`logs/vivado/recovery_20260909/physopt/util.rpt`，Design State: Physopt postRoute）。

按实测增量外推：

|---|---:|---:|---|

| 4-way（实测） | 15,483 | **88.0%** | 已贴顶 |
| 8-way（外推 +4 路 × ~1,634 LUT/路） | ~22,000 | **~125%** | **放不下** |

> 关闭 8-way 此前的依据是「资源放不下」，现在多了一条「即便放得下收益也微乎其微」。
| 128×4 | 更高 | — | **放不下** |

> 这是**有价值的负结果**，按 [13](13-final-delivery-roadmap.md) §8.2 必须留证，
> 但**不得再占用工期**。

## 3. 板端固定开销：实测 5.284 s（原为「4.25 s 且从未被测量」）

### 3.0 ✅ 2026-09-10 已实测（本节 3.1/3.2 的推测部分按此修正）

板卡重新上电后用 `tools/board/g3_overhead_sweep.py` 在 **64~4,096 源读段共 7 档
× 3 次** 密集采样（2-way 制品 `f2096d3d`，G3 判据哈希同轮 PASS），
留证 `logs/overhead_sweep/20260910T075540Z/`：

| 源读段 | 记录数 | 结果阶段中位数 |
|---:|---:|---:|
| 64 | 128 | 5.484 s |
| 128 | 256 | 5.395 s |
| 256 | 512 | 5.407 s |
| 512 | 1,024 | 5.850 s |
| 1,024 | 2,048 | 6.381 s |
| 2,048 | 4,096 | 7.315 s |
| 4,096 | 8,192 | 9.542 s |

```text
实测拟合   T = 5.284 s + 0.5157 ms x N_records      R^2 = 0.99644
文档模型   T = 4.25  s + 0.58   ms x N_records
```

**结论一：固定开销确实存在且更大——实测 5.284 s，比文档的 4.25 s 高 24%。**
64 条读段（128 记录，Stage1 实际工作量约 0.05 s）仍要等 5.48 s，
且 64/128/256 三档几乎完全平坦，证明这是一段与输入规模无关的板端固定计算。
水印上传 0.010 s、读段上传 0.022 s、8,100 B 回传约 0.01 s，**三者合计不到 0.05 s**，
所以这 5.2 s 几乎全部是板端计算，不是通信。

**结论二（推翻本文原先的一个论断）：§3.1 原先把 4.25 s 的不可信归因于
「只用 3 个大点外推、杠杆臂过长」，这条已被实测否证。**
只用 N>=4,096 的点重新拟合得到 `5.089 s + 0.5436 ms x N`，
与全档拟合的截距只差 **0.195 s**——拟合方法不是问题所在。
真正的差异是文档那个 4.25 s 与今天实测的 5.28 s 对不上（同一 2-way 制品）。
成因待查，**不得再引用「杠杆臂」作为理由**。

**结论三（修正本文原先过于乐观的收益测算）**：原 §3.2 写「压到 1 s 可使全量
4-way 达约 2,000 reads/s」，实测重算后是 **1,543 reads/s**，原估算偏高约 30%。

**结论四（最重要，改变 P0 的定位）：固定开销主导的是小规模任务，不是全量任务。**

| 源读段 | 总耗时 | 固定开销占比 | 吞吐 |
|---:|---:|---:|---:|
| 2,048（演示常用规模） | 7.40 s | **71.4%** | 277 reads/s |
| 8,192 | 13.73 s | 38.5% | 597 reads/s |
| 51,781（全量） | 58.69 s | **9.0%** | 882 reads/s |

因此 **P0 的真实价值是「演示与小规模任务的延迟」，不是「全量吞吐」**。
它仍然值得做——评委现场看到的正是小规模任务，7.4 s 里有 5.3 s 在空等；
但**不能再宣称它能改写全量性能结论**。

**结论五：§1 的核心判决不仅成立，而且更强。**
多核 CPU 跑完全量只要 3.70 s，而板端固定开销实测 **5.284 s > 3.70 s**。

全量 4-way 实测外推为 **1,368 reads/s，与单核 CPU 的 1,364.9 恰好打平（1.00x）**，
比本文原先估的「慢 1.08 倍」更接近、但依然谈不上加速。

### 3.0.1 ✅ 根因已定位：不是计算，是每步白等一个 lwIP poll 周期

用 `tools/board/read_pipe_counters.tcl` 经 XSDB 直接读固件内的计数器
（256 源读段 / 512 记录，`t_result = 5.525 s`）：

```text
PIPE_POLL_STEPS  20        <- 5.525 s / 20 = 276 ms/步
WM_POLL_STEPS     4        <- 50 区域 / WM_REGIONS_PER_POLL(16) = 4 批
```

**机制**：`sw/app/echo.c::poll_callback` 中 `PROC_RUNNING` 分支每次回调只调用
一次 `run_processing_pipeline()` 就 `break`，即**每次 lwIP poll 回调只推进一个
流水线状态**。`sw/app/pipeline.h` 有 **17 个 PIPE_* 状态**，其中 `PIPE_WM_TX`
按 `WM_REGIONS_PER_POLL=16` 分 4 批重复，合计约 20 步。
而 `tcp_poll(newpcb, poll_callback, 1)` 的回调间隔实测 **276 ms**。

```text
20 步 x 276 ms = 5.52 s   ≈ 实测 t_result 5.525 s
```

**硬件早就算完了，PS 在等定时器。** 这 5.28 s 里没有任何一毫秒是真实计算。
（顺带解释了文档那个 4.25 s：17 个状态 × 250 ms = 4.25 s，量纲完全吻合。）

**⚠️ 撤回本文原先的首要怀疑对象**：§3.2 曾断言「首要怀疑对象是 Stage 2.5 的
ARM 软件水印异或」。**该假设已被代码审查否证**——`stage2_voter.c::apply_watermark_differential`
只是对 10,125 字节做一次 `u8` XOR，量级在毫秒以下，不可能是 5 s 级开销。

**⚠️ 另一个必须记录的事实**：`poll_callback` 里**早就有**这行插桩
`[PIPE] total %u poll steps, %u ms (WM preload: %u steps)`，
且注释明确写着「固定开销的量纲就是『poll 步数 × 250~500 ms』」。
但它走 `xil_printf` → UART，而板子的 CH340 串口线未接（Windows 侧只有 FTDI/JTAG），
**这行信息从未被任何人读到过**，于是同一个问题被重新以「分档拟合反推常数项」的方式
又查了一遍。教训：**留证通道断了，等于没有留证**。

### 3.0.2 修复方案与预期收益

**改法（低风险）**：把 `PROC_RUNNING` 分支改为在**同一次 poll 回调内循环推进**
状态机，直到遇到真正需要等待硬件的状态或 `PIPE_DONE_STAGE3`：

```c
case PROC_RUNNING: {
    int guard = 0;
    do {
        int st = run_processing_pipeline(conn);
        pipe_poll_steps++;
        ...
    } while (pipe_state != PIPE_FAIL && pipe_state != PIPE_DONE_STAGE3
             && ++guard < PIPE_MAX_STEPS_PER_POLL);
    break;
}
```

必须保留的约束：
- **不得改动任何寄存器写序列的相对时序**（B27 的教训：写序列本身就是被测对象）；
- 每个状态内部原有的有界忙等（`wm_wait_region_bd`、各级 DONE 轮询）保持不变；
- 需要 `guard` 上限，避免单次回调占用过久饿死 lwIP 的 TCP 处理。

**预期收益（按实测常数外推）**：固定开销 5.28 s → 约 0.1~0.3 s。

| 场景 | 现在 | 修复后（预期） |
|---|---:|---:|
| 2,048 源读段（演示规模） | 7.40 s | **约 2.2 s（快 3.4x）** |
| 51,781 源读段（全量） | 58.69 s | 约 53.6 s（快 1.1x） |

与 §3.0 结论四一致：**这是演示体验的胜利，不改写全量性能结论。**

### 3.0.3 ✅ 修复已实施并上板验证通过（commit `a887dc4`）

**改法**：`poll_callback` 的 `PROC_RUNNING` 分支改为在同一次回调内 `do-while`
连续推进状态机，上限 `PIPE_MAX_STEPS_PER_POLL = 64`。

**⚠️ 第一版失败，且失败本身是重要发现——流式状态不能批量推进。**
v1 把所有状态一律批量推进，上板直接 FAIL
（留证 `g3_runs/20260910T113222Z/uart.log`）：

```text
[STAGE1] IP core START
[ERROR] STAGE1 停顿 ~30s
  TX frames sent=64/64   TX BD done=7/64
  RX records done=128/4096   submitted=640   ring free=512
[DMA] STAGE1 stall  ->  [POST] Pipeline failed
```

RX BD 环只有 512 项，一次投了 640。**原来那个「一次 poll 一步」不只是浪费，
它同时是 BD 环的节流机制**：靠回到 lwIP 等下一次 poll，给 DMA 排空与 BD 回收
留出时间。`stage1_dna.c` 的 `PIPE_WM_TX` 分支里那句「原实现靠下一个 poll 才回收，天然有 250 ms
余量」早就写明了这一点——**警告在那里，第一版没当回事**。

v2 因此只批量推进配置/等待类状态，进入 `PIPE_TX_STREAM` / `PIPE_PROGRESS`
立即让出。失败现场的三个数字与 uart.log 路径已写进 `echo.c` 注释。

**板级验证**（`tools/run_g3.sh --limit 2048`，留证 `g3_runs/20260910T113815Z/`）：

```text
PASS  图片 SHA-256 = fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3
PASS  四级逐级取证（Stage1 / Stage2⊕水印 / Stage3 均逐字节吻合）
UART  [PIPE] total 88 steps in 14 callbacks, 3876 ms (WM preload: 4 steps)
```

**实测收益**（`tools/board/g3_overhead_sweep.py`，同一工具同一口径）：

| 源读段 | 记录数 | 修复前 | 修复后 | 提速 |
|---:|---:|---:|---:|---:|
| 64 | 128 | 5.484 s | **1.603 s** | 3.4x |
| 128 | 256 | 5.395 s | **1.547 s** | 3.5x |
| 256 | 512 | 5.407 s | **1.877 s** | 2.9x |
| 512 | 1,024 | 5.850 s | **1.795 s** | 3.3x |
| 1,024 | 2,048 | 6.381 s | **2.796 s** | 2.3x |
| 2,048 | 4,096 | 7.315 s | **4.123 s** | 1.8x |

全档重新拟合（同一工具、同一档位、每档 3 次取中位数）：

```text
修复前   T = 5.284 s + 0.5157 ms x N_records     R^2 = 0.99644
修复后   T = 1.505 s + 0.5656 ms x N_records     R^2 = 0.98614
```

**固定开销 5.284 s → 1.505 s（3.5x，减少 3.78 s）**；水印预载 4 poll 步约 1.1 s → **2 ms**。

**⚠️ 必须如实记录：斜率反而升高了 9.7%（0.5157 → 0.5656 ms/记录）。**
原因是流式阶段的 poll 回调数随帧数增长，修复前它被淹没在固定等待里，
修复后固定项塌缩、这部分才暴露成斜率（R² 也从 0.996 降到 0.986，
说明修复后的模型不像原来那样是干净的一次函数）。
因此**不得把本次收益线性外推到全量任务**：

| 场景 | 修复前 | 修复后 | 变化 |
|---|---:|---:|---|
| 64 源读段 | 5.484 s | 1.603 s | **3.4x** |
| 2,048 源读段（演示规模） | 7.315 s | 4.123 s | **1.8x** |
| 51,781 源读段（全量，按模型外推） | 58.7 s | 60.1 s | **基本持平甚至略差** |

这与 §3.0 结论四完全一致：**固定开销只主导小规模任务**。
本次修复是演示体验的胜利，**对全量吞吐没有帮助，也不改写 §1 的性能判决**。

### 3.0.4 ❌ 继续压缩流式阶段：已尝试并放弃（负结果留证）

修复后 `PIPE_TX_STREAM` / `PIPE_PROGRESS` 仍是一步一个 poll 回调。
2026-09-10 尝试用「按 RX ring 剩余容量自适应让出」替代固定节拍：
新增 `PIPE_STEP_YIELD` 返回码，由 `PIPE_TX_STREAM` 自己在
`XAxiDma_BdRingGetFreeCnt(RxRingPtr) < 200` 时才让出。

**上板 FAIL，且失败数字与 v1 逐字相同**
（留证 `g3_runs/20260910T115133Z/uart.log`）：

```text
TX frames sent=64/64   TX BD done=7/64
RX records done=128/4096   submitted=640   ring free=512
```

**根因：判据选错了。** `ring free=512` 说明 RX ring 始终是满余量，
门限**从未触发**，等于没加节流。真正的约束不是 ring 占用率，
而是**硬件处理每一帧所需的墙钟时间**——原设计「一帧一个 poll」
本质是个**时间节拍器**，不是容量节流器。

### 3.0.5 ✅ 分解已完成：PS 只执行 378 ms，其余是等待

2026-09-11 给 PS 加了按状态累计耗时的插桩（`echo.c`，纯观测，
写序列 172 条逐字节未变）。板端实测（2,048 源读段，G3 PASS）：

```text
WM_PREP       1     7 ms      VOTER_PREP     1    18 ms
WM_TX         4     6 ms      VOTER_START    1   107 ms
RX_PREP       1    11 ms      VOTER_WAIT    61     7 ms
TX_PREFILL    1     4 ms      DONE_STAGE2    1    54 ms
START_IP      1     2 ms      DECODER_PREP   1    71 ms
TX_STREAM    11     5 ms      DECODER_START  1    18 ms
PROGRESS      1     0 ms      DECODER_WAIT   1     3 ms
DONE_STAGE1   1    59 ms
[in-state]        378 ms      [waiting]   3276 ms
```

**读法（分解的目的就是区分这两件事）**：PS 真正在执行的只有 **378 ms（10.4%）**；
3276 ms 的等待里**约 2.1 s 是 PL 真在算**（4,096 记录 × 0.5157 ms），
剩下**约 1.2 s 才是 poll 粒度造成的空等**。
`TX_STREAM` 命中 11 次、状态内仅 5 ms，却每次让出去等约 276 ms —— 它是空等的主要来源。

至此 [03](03-status.md) 的 P0 由「总量已测、待分解」**关闭为已分解**。

### 3.0.6 ❌ 压缩 TX_STREAM：四次尝试全部失败，**彻底放弃**

| # | 控制变量 | 上板结果 |
|---:|---|---|
| 1 | 一律批量推进（无节流） | FAIL `done=7/64, submitted=640` |
| 2 | `BdRingGetFreeCnt < 200` | FAIL，数字与 #1 **逐字相同** |
| 3 | 批量 + 有界忙等，仍用 `GetFreeCnt` | FAIL `done=18/64, submitted=1344`（走得更远） |
| 4 | 改用未完成记录数 `submitted - done > 384` | FAIL，数字与 #3 **逐字相同** |

**#3 的诊断价值最高**：它证明有界忙等确实有效（BD 18 vs 7、记录 832 vs 128），
同时暴露 **`XAxiDma_BdRingGetFreeCnt()` 返回的是 SG 驱动 Free 组的 BD 数，
不是「还能往硬件投多少」**——失败现场 `submitted-done = 512 = MAX_BD_COUNT`
（环已饱和）而它仍返回 512。**第 2、3 次都栽在这同一个指标上。**

**#4 换成正确的控制变量后结果一字不差**，说明停顿的成因**不在提交速率这一层**。
另外 #4 自身还有个设计错误：等待循环里仍调用 `submit_rx_records()`，
**一边限流一边喂料**。

**放弃理由**：四次尝试、两个控制变量、同一个死法；而按 §3.0.5 的分解，
可回收的空等上限约 1.2 s / 3.85 s ≈ **1.45x**，且每次尝试都要烧一轮板子。
日后若重启，**不要再从提交速率入手**——先回答「DNA 核在一个 poll 周期内
到底能吃下几帧」，那才是没被测过的那一层。

**放弃理由：剩余收益不足以匹配风险。** 按修复后实测模型
`T = 1.505 s + 0.5656 ms × N` 分解 4,096 记录的 3.82 s：

| 分量 | 耗时 | 占比 |
|---|---:|---:|
| 纯 Stage1 比对（真实硬件工作） | 1.93 s | 50% |
| 固定项 | 1.50 s | 39% |
| DMA / poll / 回传 | **0.39 s** | **10%** |

**即使把流式 poll 开销全部消掉，上限也只有 1.11x。**
而同一思路已连续失败两次，每次都要烧一轮板子并让 Stage1 挂死 30 s。
按 [13](13-final-delivery-roadmap.md) §8.2「失败也算产出」保留本条，
**不再投入**。若日后要重启，正确的控制变量是**在飞帧数**
（`tx_frames_sent - tx_done`）或 DMA 完成中断，**不是 ring 余量**。

### 3.1 现状（2026-09-10 前的推测记录，保留以备追溯）

固定开销在 2,048 读段任务中占 **63%** 的时间。
`docs/benchmarks/measured_cpu_vs_fpga.md` §3.3 把它解释为
「PS lwIP TCP 握手、CAPS/CONFIG 交互、DMA 启动开销与 Voter 累加器初始化」。

**这个解释在数量级上不成立：**

| 项 | 量级 | 依据 |
|---|---:|---|
| 4.25 s @ 100 MHz | **4.25 亿周期** | — |
| 水印 TCP 上传 | **0.01 s** | 板测日志 `t_wm` 实测 |
| 水印预载进 BRAM | ~10 万周期 | 顶层 TB 实测 `@989995000` ns |
| Voter 累加器初始化 | ~4 万周期 | 40,500 项量级 |
| 合计可解释部分 | ~14 万周期 | **差约 3,000 倍** |

**结论：性能模型里最大的一项，是猜的，并且被当作事实写进了报告。**
这与本项目的证据纪律（`AGENTS.md`「没有实测的数据不得写成已完成指标」）直接冲突。

### 3.2 P0 任务：拆解固定开销

在 PS 侧插入分阶段时间戳，至少覆盖：
连接建立 / CAPS / CONFIG / 水印接收 / 水印展开 / BRAM 预载 / Voter 初始化 /
DMA 描述符配置 / **Stage 2.5 软件水印异或** / 各级等待 / 结果回传。

**首要怀疑对象是 Stage 2.5 的 ARM 软件异或**，或某个按 40,500 长度做的 PS 侧软件循环。

**收益测算（2026-09-10 按实测重算，替代原先偏高约 30% 的估计）**：
若固定开销由 5.284 s 降到 1 s——

- **全量任务**：4-way 由 1,368 → 1,543 reads/s（单核比 1.00x → 1.13x），提升有限；
- **2,048 源读段（演示规模）**：7.40 s → **约 2.1 s，快 3.5 倍**，这才是主要收益。

> 因此 P0 的定位是**演示体验与小规模任务延迟**，成本低、见效快、
> 且顺带修掉一个证据缺陷（§3.0 结论一/二）。
> 但它**不改写全量性能结论**——§1 的判决不受影响。

## 5. 长期方向（赛后 / 若项目继续）

按「能不能改变数量级」排序，而不是按好做程度。

### 5.1 ❌ ~~算法级：用种子索引替换全局暴力滑窗~~ —— **已证伪，不要做**

> **2026-09-10 撤回。本文原先把它列为「🥇 唯一有希望让 FPGA 真正赢的技术路线」，
> 这个判断是错的，而反证一个月前就在仓库里。**

原推荐的理由是「生物信息学早已不用暴力滑窗，BWT/FM-index、minimizer + 哈希种子
可把候选位置从 4 万降到个位数」。**该推荐建立在一个错误类比上**：本系统的 Stage1
**不是**普通的读段-参考基因组比对。

`tools/bench_align.py::seed_feasibility` 实测（256 条读段）：

```text
最佳位置处的最长连续精确匹配
  读段 vs 水印（接收端真正拥有的）   中位 5 nt，最大 7 nt
  读段 vs 真实序列（接收端拿不到）   中位 7 nt，最大 150 nt
→ 16-mer 精确命中概率 ≈ 1.53e-05
```

**根因**：接收端能拿来做索引的只有**水印序列**，而读段是 4b5b 稀疏流与水印异或的
产物——两者按构造只有约 50% 碱基相同。在 40,500 nt 的参考上要让种子有选择性，
至少需要 16 nt 量级的精确种子；而实际最长精确匹配只有 **5~7 nt**。
**任何基于精确种子的索引在这里几乎永不命中。**

`bench_align.py` 的文件头一句话就写着「以及**种子法为何失效**的实证」。
它零引用、不在任何文档里，所以本文才会在不知情的情况下把它推翻的方向列为第一优先级
——**这本身就是「代码卫生」的代价**：一个无人可见的脚本，等于这条结论不存在。

**仍然开放的算法方向**（与已证伪的精确种子法不同，它们不依赖精确匹配）：
- **粗到细的分层相关搜索**（[13](13-final-delivery-roadmap.md) §7.1 H4）：
  先用低分辨率/子采样相关粗筛候选窗口，再对少数候选做全精度复核。
  它容忍 50% 的碱基差异，因为判据是**相关峰**而不是精确命中。
  必须证明零误定位且召回率不下降。
- **分数提前终止 / 上界剪枝**（H5）：当前分数不可能超过 best 时提前结束。
  注意 64 lane lockstep 下单 lane 提前退出未必省周期。

### 5.2 🥇 换器件：暴力相关既然无法回避，就只能靠更大的芯片

按 §2.1 的 ~1,634 LUT/路外推：

| 器件 | LUT | 可容纳 | 相对 2-way |
|---|---:|---|---:|
| XC7Z010（当前） | 17,600 | 4-way | 1.93x |
| XC7Z020 | 53,200 | 16~32-way | ~8~15x |

但注意：展开到 15x 后，**固定开销会重新成为绝对瓶颈**（Amdahl）。
所以 §3 的 P0 是换芯片的**前置条件**，不是替代品。
迁移风险见 `AGENTS.md`：DDR/MIO/PHY/时钟/XDC 未知的新板不能直接迁移。

### 5.3 🥈 换价值轴：延迟与集成，而不是吞吐

FPGA 真正不可替代的场景不是「比 CPU 快」，而是：

- **流式在线处理**：与测序仪对接，边测边解，主机不必先落盘整个 FASTQ
  （[13](13-final-delivery-roadmap.md) §7.4 G5）。这是**延迟**优势，CPU 批处理拿不到。
- **自包含嵌入式装置**：不需要一台笔记本在旁边。
- **能效**：粗算可能赢多核 CPU 1.5~2 倍——**但必须实测**，否则一个字都不能写。

### 5.4 🥉 算法-硬件协同：把软信息交给 LDPC

当前 Stage2 输出硬判决 0/1。若把比对置信度（`top1 - top2`、得分分布）
作为软信息喂给 LDPC（[13](13-final-delivery-roadmap.md) §7.3 R4），
在低覆盖度/高错误率下成功率有望显著提升。这是**正确性维度**的收益，
不与 §1 的性能死局冲突，且是本系统相对通用 CPU 流程的真正结构性优势。

### 5.5 🥇 压缩那 62.9% —— 2026-09-11 上板实测后新增的第一顺位

**4-way 首次上板把长期方向的排序整个换掉了**（`docs/benchmarks/measured_4way_board.md`）。

板端两条斜率反解出：**Stage1 只占每记录成本的 37.1%**，其余 62.9% 是
DMA 搬运 / Voter / poll 开销 / 回写。文档此前一直假定 Stage1 占 **81%**——
那个数字是理论周期推算，不是测量。

这条实测同时给上面几个方向重新定了价：

| 方向 | 实测前的理由 | 实测后 |
|---|---|---|
| §5.2 换器件（16~32-way） | 「相对 2-way ~8~15x」 | **仍然对，但天花板远低于那个数**：Stage1 加速 ∞ 倍，端到端上限也只有 `1/0.629 = 1.59x`。**换芯片之前必须先压 62.9%，否则买到的算力大半用不上** |
| §5.1 算法方向（H4/H5） | 「让 Stage1 少算」 | 同上受 1.59x 封顶 |
| **压缩 62.9% 本身** | 此前不在长期方向列表里 | **现在是第一顺位**——它是上面所有方向的公共前置条件 |

**但必须先拆开这 62.9%**。当前只知道它的总量，不知道 DMA / Voter / 回写各占多少。
`measured_timing_accountability.md` §5.1 已标明：板端没有 PL 级独立计时器，
`[waiting]` 里 PL 计算与 poll 空等**无法直接分离**。

**因此下一步不是优化，是测量**：给 Voter 与 Stage3 加与 Stage1 同规格的
周期计数器（Stage1 已有 `pipe_poll_steps` 一类计数），让三级各自可独立读出。

> **✅ 2026-09-11 实测更新（P7 闭环）**：
> 硬件周期计数器已在真实板卡实测闭环（`docs/benchmarks/measured_p7_cycle_counters.md`）。
> 4,096 条记录实测结果揭示了极震撼的真相：
> - **PL Stage 2 Voter** 耗时仅 **29.6 ms**（0.93%）；
> - **PL Stage 3 Decoder** 耗时仅 **0.02 ms**（0.0007%）；
> - **PL 纯硬件总耗时不足 30 ms**！
> - **真正的耗时元凶（占 99% 以上）锁死在 PS 侧**：
>   1. **`[waiting]` lwIP poll 轮询空等 2,776 ms（87.5%）**：固件依赖慢速定时器回调推进状态机，绝大部分墙钟耗时在空等唤醒；
>   2. **`[in-state]` 全局 Cache 维护 396 ms（12.5%）**：大范围无差别 `Xil_DCacheInvalidateRange` 与哨兵扫描耗尽 CPU。
>
> **因此，PL 侧 Voter/Decoder 硬件微架构优化彻底失去意义（收益上限 < 1%），彻底关闭**。

### 5.6 🥇 PS 固件新靶心：中断驱动与精细化 Cache（P12）

实测把 62.9% 的瓶颈精确推到了 PS 固件上。下一步提速的唯一有效靶心：

1. **状态机驱动改造（消除 2,776 ms 空等）**：
   - 将当前依赖 `tcp_poll`（250~500 ms 慢速节拍）的回调式推进，改造为 AXI DMA / IP 中断服务程序（ISR）触发，或在主循环中以事件泵快速推进；
   - 目标：将 4,096 记录下的 2,776 ms 等待时延直接压缩至接近零（仅保留硬件实际完成中断到处理的微秒级开销）。
2. **精细化局部 Cache 维护（消除近 400 ms 开销）**：
   - 将粗暴的整段 DDR Cache Invalidate 改造为按各阶段真实产出字节边界（如 Voter 10,128B、Decoder 8,100B）局部刷新；
   - 避免跨几 MB 到十几 MB 内存区域的无效遍历与哨兵轮询。
