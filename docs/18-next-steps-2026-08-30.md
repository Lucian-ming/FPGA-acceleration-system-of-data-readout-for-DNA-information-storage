## 1. 现状

2026-08-30 第五次上板，**G3 端到端闭环**：板端回传经 `tools/ldpc_decode.py` 译码后
图片 SHA-256 = `fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3`，
与判据逐位相同；回传比特流与 `tests/golden/dec_input.txt` 0/64,800 处差异；
板上四级 DDR 快照逐级比对全过（`tools/board_stage_check.py`）。

2026-08-29~30 两天共修掉 7 个缺陷：

| 编号 | 缺陷 | 层 |
| --- | --- | --- |
| B21 | RX BD 按 16 KB 切，收满 13 条即反压锁死 | 固件 |
| B22 | Stage3 等待循环从不读 DONE，超时阈值 ≈ 69 小时 | 固件 |
| B23 | AXIS 输出 TDATA 比 TVALID 早一拍 | RTL |
| B24 | packer 违反 AXI-Stream；结果 FIFO 被反复 pop | RTL |
| B25 | 水印预载写地址与数据不同拍，整条水印偏一个符号 | RTL |
| B26 | 入口采样早于 FIFO 稳定，结果整体错位一条读段 | RTL |
| B27 | 写 START 任何值都启动，固件把跑一半的任务重启 | RTL+固件 |

**其中 B23~B27 五个，在修复前的所有仿真里都是绿的。** 它们全部落在同一条缝上：
仿真喂黄金数据、板上走真实 DMA/DDR/寄存器接口。这是本轮最重要的结论，
已写进 `AGENTS.md` 的「事实边界」与「常见陷阱」。

## 3. 排队（按优先级）

### P0 · 本轮收尾（进行中）

1. ~~**长回归跑完并回填**：`run_m2_full.sh`、`run_m3_bd.sh bd2/bd3ext/bd3b`。~~

   而 RANDOM 的 ready 对象是一次性的（`event_count` 默认 1）、`send_*ready()` 又非阻塞，

   「repeats until the channel is given different policy」）只 send 一次即可，

   同时给 `run_snapshot` 加了日志上限 `M3_XSIM_LOG_CAP_MB`（默认 512 MiB），
   任何 VIP 刷屏都不该再有机会填满磁盘。

### P1 · 扩大闭环边界（当前最大的未知）

3. **全量数据集跑通**。板端固件与 RTL 不用改，容量也够，
   **但上位机的超时必须改**（见下），别被「不用改代码」误导：

   | 项 | 数值 |
   | --- | --- |
   | 全量 51,781 条 × 2 方向，对齐 64 | 103,552 条记录 |
   | 固件上限 `TASK_MAX_READS` | 107,968 ✅ |
   | Stage1 输出需求 | 4.74 MB |
   | Stage1 输出区预算（108,000 × 48 B） | 4.94 MB ✅ |

   它顺带压测了几件只有规模上去才暴露的事：RX BD 环回绕从 3 次变成 **101 次**、
   TX 从 64 帧变成 1,618 帧、DNA 核连续运行时长约 25 倍。

   **⚠️ 但上位机必须改：180 s 超时一定会被撞穿。** 已核实（`clients/python/protocol.py`
   的 `recv_exact` 用 `sock.settimeout(timeout)`，`first.py:629` 传 180 s）：
   板端从收到 `PKT_POST` 到 `send_result()` 之间**一个字节都不发**
   （`echo.c` 的 `poll_callback` 只在 `PROC_DONE` 才发结果），
   所以**整条流水线的处理时长是一整段静默**，180 s 不是「两次打印的间隔」而是「总时长」。

   实测 4,096 条记录的 result 阶段是 32.4 s。但**这 32.4 s 的内部拆分至今没有测过**，
   而全量会不会超时完全取决于拆分：

   - `first.py` 的 `stats.t_result` 包的是 `recv_result()`，即「发完 POST 到收完结果」的
     **全部板端时间**（水印预载 + Stage1 + Stage2 + Stage3 + 回传），不是任何单独一级；
     `读段 0.35s`（`t_batches`）量的是**上传耗时**，也不是 Stage1 的处理时间。
     这两个数都容易被误读成某一级的耗时，别拿它们当拆分依据。
   - 若**随条数线性增长的部分**（Stage1/Stage2）占大头，全量约 25 倍 → 数百秒，必然超时；
   - 若**与条数无关的常数项**（水印预载 50 个区域、Decoder 的 AXI 读写往返）占大头，
     全量可能只增加几秒 → 根本不会超时。

   **两种可能都存在，不要先入为主。** 分档测量（下一段）会直接给出答案：
   把三档的 result 耗时对条数做线性拟合，截距就是常数项、斜率就是每条成本。

   两个选择，建议先测量再定：
   - **最省事**：把 `first.py:629` 的 `timeout=180.0` 调大（先按实测总时长的 2 倍取）。
     只改上位机，不动板端。
   - **更稳妥**：板端在流水线运行期间定期发一个心跳/进度包，客户端据此刷新超时。
     这要动协议（新包类型），但能顺带给长任务一个可观测的进度，
     也避免以后每换一次规模就要重调超时。

   **先做的事**：用 `--limit` 分档测量（4,096 → 8,192 → 16,384），
   拟合出「固定开销 + 每条耗时」，再决定超时取值和是否值得上心跳包。
   不要一上来就跑全量——撞上超时会分不清是超时还是流水线真的挂了。
   顺带：想知道每一级各花多少，最省事的办法是在 `echo.c` 的各 `PIPE_DONE_*` 打一条
   带 `XTime`/计数的时间戳到 UART，一次上板就能把拆分测出来，
   这也正是 P2 第 6 项「性能」要的第一份数据。

   **另一个风险点**：`srpe_batch` 的 partial batch idle timeout 路径在最后一批的行为。

4. **二次任务 / 状态复位**。同一次连接内连续跑两次任务，判据是**两次都拿到同一张图片哈希**。
   `docs/12` §11 早就列了「二次任务是否真正清零 Voter 累加器」，至今没有任何证据。
   这里是天然的雷区：B27 的 START 语义、B21 的 BD 环指针、Voter 累加器、
   Stage3 的 `done` 清除时机，任何一个没复位干净都会在第二次任务上翻车。

### P2 · 需要改硬件才能推进（前置条件已满足）

5. **SE250 / PL 几何参数化**。现有比特流只支持 150 bp（`READ_BASES_PER_READ`）。
   SE250 是 64,800 × 250 bp，与 SE150 不可混用。要改 RTL 参数并重新综合。
   按 `docs/14` 的约定，这一项以 G3 闭环为前置——现在满足了。
6. **性能**。当前 4,096 条记录约 33 s，线性外推全量约 14 分钟。
   **瓶颈至今没有量化过**，先测量再优化：流水线由 lwIP `tcp_poll` 驱动，
   间隔 500 ms，水印预载 50 个区域要走 100 次 poll（≈50 s）就是一个明显的嫌疑。
   不要在没有测量的情况下先动 Stage1 架构。

## 4. 技术债（按性价比排序）

1. **`sw/app/echo.c` 已 2,135 行**，B22 和 B27 两个缺陷都源自这个文件的随意性：
   对 `DECODER_REG_START` 写了 11 次（其中 9 次是 0）、`dump_dma_regs()` 读完寄存器
   一行都不打印、看门狗阈值折算下来要 83 分钟才触发。建议按流水级拆分，
   并把可在主机上测的部分（几何推导、DDR 布局、协议解析）补上单测。
2. **RTL 文件的 GBK 编码已经咬过两次**，其中一次把注释写成 806 个 U+FFFD、
   不可逆，只能从 HEAD 重打补丁才救回来。建议一次性规范化为 UTF-8，
   并加 `.gitattributes` 固定，避免下一个人再踩。
3. **`sw/workspace/` 里累积了 `dna_platform_b20/b23/b25/b27` 四套平台**，
   占空间且容易误用旧 ELF。建议只保留与当前 `hw/build/export/` 同源的那一套。

## 6. 判据纪律（不因闭环而放松）

- 唯一最终判据仍是板端真实回传经 LDPC 后的图片 SHA-256。
- 仿真全绿不代表板上正确——本轮 5/7 的缺陷就是这么漏过去的。
- 新增或修改任何跨 IP 接口（AXIS 握手、DMA、寄存器时序、FIFO 读延迟）时，
  判据必须建在真实接口上，不能用 VIP 内存喂黄金数据糊过去。
- 改动 RTL 或固件后必须整套重建 `hw/build/export/` 并刷新 `SHA256SUMS`，
  否则制品与源码不同源。
