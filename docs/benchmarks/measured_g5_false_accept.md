# G5 · 「误接受率」的定义与实测：阈值挡得住诱饵，挡不住错位

> **评测日期**：2026-09-11
> **工具**：`tools/g5_false_accept.py`（定义写在文件头）、`tools/run_g5_matrix.sh`
> **留证**：`logs/g5_matrix/run1/`（`summary.tsv`、每点 JSON、`res_D2_at65/`；
> 加噪数据可由 seed 复现，故不入库）
> **对照门禁**：[13](../13-final-delivery-roadmap.md) §4 G5「阈值 → 正确率/耗时/**误接受率**」
>
> **这一条门禁此前挂着不是因为难测，是因为「误接受」从来没有定义。**
> 本文先给定义，再给测量。

---

## 1. 定义

### 1.1 判定单位是「记录」，不是「读段」

上位机对每条源读段发**两份**记录：正向与反向互补，交织成 `[fwd0, rc0, fwd1, rc1, …]`
（`clients/python/fast_readout.py::batch_seqs_to_records`）。板端对每条记录**独立比对、
独立投票**，`score < SCORE_MIN` 的记录直接跳过不投票（`docs/05` 寄存器 0x30，固件固定 67）。

所以一条源读段贡献两条记录，**其中恰好一条方向正确**。

### 1.2 三类记录与两个比率

真值由数据集生成器写进 FASTQ header（`@read_000000_pos_12519_orient_rc`），
**是外部给定的，不是从比对结果反推的**。

| 类别 | 定义 | 期望 |
|---|---|---|
| **真记录** | `orient == orient_true` | 被接受且定位到 `pos_true` |
| **诱饵记录** | `orient != orient_true` | **应被拒绝**——它在参考上没有任何正确位置 |
| **错位真记录** | 方向对但报告位置 ≠ `pos_true` | 同样是污染 |

```
误接受率 FAR(τ) = |通过阈值但票投错地方的记录| / |通过阈值的记录|
误拒绝率 FRR(τ) = |定位正确却被阈值挡掉的真记录| / |定位正确的真记录|
```

**FAR 的分母取「被接受的记录」而不是全部记录**，因为这个比值才有运行意义：
**它就是投票累加器里垃圾票的占比**。

### 1.3 同分并列单列一类

Stage1 的分数是整数（匹配碱基数），同分并列真实存在。主机模型
`tools/readout.py::_align_one` 走 FFT，float64 舍入误差会让 `argmax` 在并列集里
挑一个**不可复现**的位置，而 RTL 确定性地取最小位置
（`tools/make_stage1_tie_golden.py` 的文件头有实测）。

因此对每条「位置不符」的真记录，本工具**再用整数精确滑窗复核两处的分数**：
分数相等记为**并列错位**（编码本身的性质，不是缺陷），分数更高才记为**真错位**。
两者都算误接受，但必须分开报——**并列是阈值调不掉的地板，真错位才随噪声变化**。

## 2. 主机模型的板端等价性（先立这条，否则下面的数字没有落点）

本测量在主机上复算。它可信的依据是既有 G3 运行里的 Stage1 四级取证
（`logs/g3_2026/g3_4way_board.log:44`，2-way 的 `g3_revert_check.log` 逐字相同）：

```text
=== Stage1 输出 @0x10600000  vs  stage2_in.hex — ✅ PASS ===
  整条 48 B 逐位相同：4011/4096
  码字相同：4096/4096   score 相同：4096/4096
  position 差值 top3：[(0, 4011), (-30838, 3), (-8146, 2)]
```

**板端与主机模型在 4,096/4,096 条记录上得分完全相同**；位置不同的 85 条（2.08%）
得分同样相同——即全部落在并列集内，与 §1.3 描述的机制一致。

> **边界**：本文所有 FAR/FRR 数字是**主机复算**，不是板端直接读出。
> 上面这条只证明「主机模型与板端在得分上等价、位置差异仅限并列」，
> 它使主机复算的 FAR 可信，**但不等于板端实测了 FAR**。
> 要升格为板端结论，需对同一输入导出 `dump_stage1.bin` 并逐记录比对。

## 3. 实测

数据集 `D1_text_manifesto`（真值 header 齐备），每点 512 源读段 = **1,024 条记录**，
加噪由 `tools/mutate_reads.py` 注入，**每点 3 个随机种子**。

### 3.1 分数分隔度：这一张表解释了后面所有曲线

| 噪声 | 真记录最低分 | 真记录中位 | 诱饵最高分 | **间隔** | 并列错位 | **真错位** |
|---|---:|---:|---:|---:|---:|---:|
| 无 | 72.0 | 83.0 | 68.0 | **+4.0** | 0.0 | 0.0 |
| sub 0.5% | 72.0 | 83.0 | 67.7 | **+4.3** | 0.0 | 0.0 |
| sub 1% | 70.0 | 82.0 | 68.0 | **+2.0** | 0.0 | 0.0 |
| sub 2% | 69.3 | 82.0 | 68.3 | **+1.0** | 0.0 | 0.0 |
| sub 4% | 67.7 | 80.3 | 67.7 | **±0.0** | 0.0 | 0.0 |
| ins=del 0.1%（sub 1%） | 59.3 | 81.0 | 68.0 | **−8.7** | 0.3 | **70.7** |
| ins=del 0.5%（sub 1%） | 59.7 | 76.7 | 68.3 | **−8.7** | 4.0 | **235.0** |

（每格为 3 个种子的均值；记录总数 1,024）

**两种错误的作用机制完全不同，这是本轮最重要的发现：**

- **替换错误只压缩「间隔」**：真记录与诱饵的分布一起下移，两者始终可分，
  直到 **sub ≈ 4% 时间隔归零**——这就是纯替换场景下阈值法的边界；
- **插删错误直接制造「真错位」**：读段移帧后**真的**在别处更像，
  0.1% 的插删就产生 70.7/1,024 条真错位，而这**不是阈值能解决的问题**。

### 3.2 阈值曲线（FAR / FRR vs τ）

| 噪声 | τ=64 | τ=67（固件现值） | τ=70 | τ=75 |
|---|---|---|---|---|
| 无 | 7.25% / 0% | **0.58% / 0%** | **0% / 0%** | 0% / 3.1% |
| sub 1% | 7.30% / 0% | 0.65% / 0% | **0% / 0.07%** | 0% / 3.8% |
| sub 2% | 6.63% / 0% | 0.45% / 0% | **0% / 0.07%** | 0% / 5.7% |
| sub 4% | 6.39% / 0% | 0.45% / 0% | **0% / 0.59%** | 0% / 9.2% |
| ins=del 0.1% | 16.95% / 1.5% | 8.94% / 3.0% | 6.09% / 5.5% | 3.72% / 12.2% |
| ins=del 0.5% | 41.53% / 6.9% | **32.04% / 15.9%** | 28.02% / 25.3% | 22.94% / 42.2% |

（格式：**FAR / FRR**，3 种子均值）

**种子稳定性**：纯替换各点三种子的 FAR@67 极差 ≤ 0.58 个百分点；
插删点极差较大（0.1% 点 1.81、0.5% 点 6.92 个百分点），符合「真错位是小概率事件」的预期。

### 3.3 独立生成路径的交叉核对

`tests/datasets/D2_controlled_noise`（由 `generate_payload_dataset.py` 生成，
**与 `mutate_reads.py` 是两条独立代码路径**，sub 1% + ins/del 各 0.2%，实测综合错误率 1.39%），
2,048 源读段 = 4,096 条记录：

| τ | 接受 | 误接受 | 其中诱饵 | 其中真错位 | FAR | FRR |
|---:|---:|---:|---:|---:|---:|---:|
| 64 | 1,990 | 508 | 135 | 373 | 25.53% | 2.44% |
| **65**（板端该数据集实际所用） | 1,866 | 406 | 61 | 345 | **21.76%** | 3.88% |
| 67 | 1,719 | 309 | 9 | 300 | 17.98% | 7.18% |
| 70 | 1,596 | 243 | **0** | 243 | 15.23% | 10.93% |

间隔 −10。FAR@67 落在本文矩阵 `ins=del 0.1%`（8.94%）与 `0.5%`（32.04%）之间，
**两条独立生成路径一致**。

注意 τ=70 这一行：**诱饵已被清零，FAR 仍有 15.2%**——
剩下的全是真错位，再抬阈值也只是在等比例地砍掉真记录与错位记录。

## 4. 结论

1. **固件当前的 `SCORE_MIN=67` 在纯替换场景下是次优的。**
   实测 τ=70 在 sub 0~4% 全区间给出 **FAR = 0%**，而 FRR ≤ 0.59%。
   67 这个值来自 `int(0.45 × 150)`，是设计时选的比例，不是测出来的；
   实测显示真记录最低分 ≥ 67.7、诱饵最高分 ≤ 68.3，**分界线就在 69~70 之间**；
2. **但在含插删的场景下抬阈值换不来干净。** τ 从 67 抬到 70，
   0.5% 插删点的 FAR 只从 32.0% 降到 28.0%，FRR 却从 15.9% 涨到 25.3%——
   因为此时误接受的主体已经从「诱饵」变成「真错位」，
   **而真错位的分数和真记录一样高，阈值在原理上就分不开它们**；
3. **同分并列不是实际问题**：生产几何下并列错位 ≤ 4/1,024，
   板端与主机的 85 条位置差异也全部落在并列集内、得分相同；
4. **FAR 高不等于恢复失败。** `D2_controlled_noise` 在板端 `score_min=65` 下
   **3/3 逐位恢复原始 payload**（`measured_board_multi_payload.md` §6 重复实验表），
   而同一数据集在同一阈值下的 **FAR = 21.76%**——
   **超过五分之一的票是垃圾票，多数投票在 2× 覆盖度下照样把它们淹掉了**。
   **FAR 衡量的是累加器的污染程度，不是任务成败**，两者不可互相替代；
   报告里把 FAR 说成「失败率」是错的。

---

## 5. 待办与事实边界

1. **未改固件。** 把 `SCORE_MIN` 从 67 调到 70 需要重建 + 烧录 + 重跑 G3 + 更新
   `SHA256SUMS`（源码与制品必须同一个提交），**本轮不做**；
   且要先确认真实数据 D0 的插删水平——若 D0 含插删，抬阈值可能反而变差；
2. **全部基于合成数据 D1/D2。** D0 是真实测序数据，**FASTQ 没有真值位置字段**，
   因此 **D0 上无法测 FAR**。这是方法上的硬边界，不是没做；
3. FAR/FRR 是主机复算（§2 给了等价性依据），**不是板端直接读出**；
4. 全部为 SE150 / 150 bp / 正反双向。覆盖度不在矩阵内——
   它只改变记录条数，不改变单条记录的得分分布，
   覆盖度对**恢复成功率**的影响由 `tools/run_robustness_scan.py` 覆盖；
5. 插删场景下「真值位置」本身是模糊的：读段第 10 位缺失后，
   前 10 个碱基对应 `pos_true`、其余对应 `pos_true+1`，**两个位置都不完全正确**。
   本文把「报告位置 ≠ header 位置」一律计为错位，
   **这是偏保守的口径**，真实污染程度不会高于本文数字。
