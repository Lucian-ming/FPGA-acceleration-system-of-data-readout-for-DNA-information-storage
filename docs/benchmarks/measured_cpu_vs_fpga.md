## 1. 评测背景、硬件环境与契约规范

### 1.1 实验背景与核心原则
长期以来，FPGA 加速对比中常存在两类严重失真现象：
1. **稻草人对比 (Strawman Fallacy)**：以上位机未优化的纯解释型 Python 暴力滑窗为 CPU 代表，得出虚高数十倍乃至上百倍的“伪加速比”；
2. **功耗虚构 (Fabricated Efficiency)**：在未接入外置物理功率计的情况下，以芯片手册标称常数（如 2.5W）或 TDP 估算强行进行除法，伪造 `reads/(s·W)` 能效比。

本报告落实严格的度量纪律：
- **CPU 基准**：采用现代多核高度优化 C 语言实现（`-O3 -march=native` 位平面位运算 + `__builtin_popcountll`），测试单核至 16 核梯度；
- **物理板卡实测**：直连当前运行中的真实 Zynq XC7Z010 物理板卡（现行 2-way 100MHz 位流），下发不同数据规模（2,048、4,096、8,192 源读段），每档测量 3 轮；
- **判据硬门禁**：物理板卡每次回传均经 LDPC 软件译码并重构图片，核验最终 SHA-256 必须严格匹配 `fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3`；
- **能效标注**：功耗与能效比字段统一显式标记为 `UNMEASURED / N/A`。

### 1.3 数据集契约与记录换算
依据 `docs/02-data-contract.md` 契约规范：
- **源读段 (Source Reads)**：测序 FASTQ 文件中的原始读段条数 $N_{\text{source}}$；
- **评估记录 (Evaluated Records)**：由于测序读段方向随机，系统必须以正向与反向互补双向比对（`orientation = both`），实际进入流水线的记录数 $N_{\text{records}} = 2 \times N_{\text{source}}$（向上补零至 64 整数倍）；
- 涉及吞吐率与延迟时，本报告**同时分列给出每源读段 (per source read) 与每记录 (per record)**。

### 3.3 板端耗时线性模型分析
观察板端结果耗时中位数随着记录数增长的变化：
- 4,096 条记录：6.734 s
- 8,192 条记录：9.359 s（边际增量 $\Delta t = 2.625\text{ s}$，平均 $\approx 0.641\text{ ms/记录}$）
- 16,384 条记录：13.867 s（边际增量 $\Delta t = 4.508\text{ s}$，平均 $\approx 0.550\text{ ms/记录}$）

拟合得到板端实测模型为：
$$T_{\text{board}} \approx 4.25\text{ s} + 0.58\text{ ms} \times N_{\text{records}}$$
- **常数项 ($\approx 4.25\text{ s}$)**：对应 PS lwIP TCP 连接握手、CAPS/CONFIG 交互、DMA 启动开销与 Voter 累加器初始化；
- **一次项系数 ($\approx 0.58\text{ ms/记录}$)**：与 100MHz 下 2-way 纯硬件流水线理论周期（$0.470\text{ ms/记录}$）非常贴近，额外约 $0.11\text{ ms}$ 为 S2MM DMA 中断与 DDR 回写搬运开销。

> **⚠️ 2026-09-11 更正：上面这句「Stage1 占 0.470/0.58 = 81%」的拆分是错的。**
> 那 0.470 ms 是**理论周期推算，不是测量**。2026-09-11 用 2-way 与 4-way 两条
> **板端实测斜率**反解得到：**Stage1 只占每记录成本的 37.1%**，
> 其余 62.9% 是 DMA 搬运 / Voter / poll 开销 / 回写。
> 依据是 4-way 上板后端到端每记录成本比仅 **1.218x**（核心加速 1.929x），
> Amdahl 上限 `1/(0.629+0.371/1.929)=1.22x` 与实测吻合。
> 详见 [`measured_4way_board.md`](measured_4way_board.md)。
> **此前一切基于 81% 的性能外推都应按 37% 重算。**

### 4.2 科学结论与边界澄清

1. **彻底粉碎稻草人加速比假象**：
   - 若将 FPGA 物理板卡（端到端 401.3 reads/s）与单核 Python 暴力滑窗（78.5 reads/s）对比，表面上能获得 **5.1x** 的加速比；
   - 但若与高度优化的现代 CPU C 实现对比，**单核 CPU (1T) 即具备 1,364.9 reads/s 的吞吐，为 FPGA 物理板端的 3.40 倍**；
   - **在 16 线程满载下，优化 CPU 吞吐达 14,003.1 reads/s，高达 FPGA 物理板端的 34.89 倍**！
   - **结论**：在未完成面向高规格器件的硬件级大幅度展开（如 8-way / 16-way 并行）以及流式全重叠 DMA 架构改造前，**严禁宣称当前 100MHz 2-way FPGA 已在绝对吞吐上击败优化 CPU**。

2. **计时重叠边界与流水线特性 (Timing Overlap Boundaries)**：
   端到端数据读出链路包含以下四个核心阶段：
   - **MM2S 上传**：主机内存 $\to$ FPGA DDR/BRAM DMA 传输；
   - **FPGA 硬件计算**：Stage1 滑窗比对 $\to$ Stage2 差分投票 $\to$ Stage3 反稀疏化；
   - **S2MM 接收**：FPGA DDR $\to$ 主机内存 DMA 传输；
   - **LDPC 软件译码**：主机/PS CPU 执行 LDPC 信道纠错译码。

   **不可简单相加的边界原理**：
   - 在本轮实测的同步停等（Stop-and-Wait）单批次测量下，总耗时为各阶段顺序累加：
     $$T_{\text{e2e}} = T_{\text{upload}} + T_{\text{hw}} + T_{\text{download}} + T_{\text{ldpc}}$$
   - 在双缓冲 / 流式流水线（Streaming Pipeline）架构下，第 $k+1$ 批上传、第 $k$ 批硬件计算、第 $k-1$ 批接收与第 $k-2$ 批 LDPC 译码在时间上高度重叠，系统稳定吞吐受限于最慢瓶颈阶段：
     $$\text{Throughput} = \frac{1}{\max(T_{\text{upload}}, T_{\text{hw}}, T_{\text{download}}, T_{\text{ldpc}})}$$
   - 因此，**严禁将未考虑流水线重叠的独立阶段耗时简单折叠或算术相加**，必须严格区分「纯硬件流水线周期」、「板端单批端到端耗时」与「上位机完整回传耗时」。

3. **严守功耗未测事实**：
   - 现阶段由于实验现场未接入外置数字功率测试仪，所有功耗与能效比数据均标注为 `UNMEASURED / N/A`；
   - 坚决杜绝使用 2.5W 或 TDP 估算进行能效比除法，绝不伪造能效胜出结论。
