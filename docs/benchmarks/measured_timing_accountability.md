## 1. 时间到底花在哪一级

G1 出口门禁的核心问题。答案由两侧计时拼成——**主机侧看得见通信，板端才看得见计算**。

### 1.1 主机侧（2,048 源读段 / 4,096 记录，中位数）

```text
水印上传   0.010 s
读段上传   0.162 s
结果阶段   3.969 s   <- 板端计算 + 回传，主机只能看到一个总数
总计       4.158 s
```

### 1.2 板端（同规模，`[PIPE-BREAKDOWN]` 按流水线状态累计）

```text
WM_PREP       1     7 ms      VOTER_PREP     1    18 ms
WM_TX         4     6 ms      VOTER_START    1   107 ms
RX_PREP       1    11 ms      VOTER_WAIT    61     7 ms
TX_PREFILL    1     4 ms      DONE_STAGE2    1    54 ms
START_IP      1     2 ms      DECODER_PREP   1    71 ms
TX_STREAM    11     5 ms      DECODER_START  1    18 ms
PROGRESS      1     0 ms      DECODER_WAIT   1     3 ms
DONE_STAGE1   1    59 ms
[in-state]        378 ms      [waiting]   3276 ms
```

### 1.3 合并口径（这才是「花在哪一级」的完整答案）

| 层级 | 耗时 | 占比 | 依据 |
|---|---:|---:|---|
| 主机 FASTQ 解析 + 打包 | ~0.11 s | 2.6% | `fast_readout` 实测（W2-H） |
| 水印 + 读段上传（TCP） | 0.172 s | 4.1% | 主机侧 `t_wm`/`t_batches` |
| **PS 固件执行** | **0.378 s** | **9.1%** | 板端按状态累计 |
| **PL 真实计算** | **~2.1 s** | **~50%** | 4,096 记录 × 0.5157 ms（斜率实测） |
| **poll 定时器空等** | **~1.2 s** | **~29%** | `[waiting]` 3.276 s 减去 PL 计算 |
| 结果回传（8,100 B） | ~0.01 s | 0.2% | 板端 `Delivery settled after 4 ms` |
| 主机 LDPC 译码 | ~0.09 s | 2.2% | `check-dumps` 主机译码耗时 |

**结论**：一半时间是 PL 在做有用功；**约 29% 是在等 lwIP 的 poll 定时器**，
不是任何一级在算。这一项的压缩已尝试四次全部失败并放弃，
见 [17](../17-competition-strategy.md) §3.0.6。

## 2. 重复运行的计时波动为什么是那个幅度

G1 另一条门禁：**同一输入重复运行的计时波动可解释**。

同一输入（2,048 源读段）连跑 **12 次**，`t_result` 排序后：

```text
3.49  3.50  3.50  3.50  |  3.96  3.97  3.97  3.97  |  4.44  4.44  4.53  |  4.93
```

| 统计量 | 值 |
|---|---:|
| n | 12 |
| min / 中位数 / max | 3.492 / 3.969 / 4.926 s |
| 标准差 | 0.481 s |
| 变异系数 | 11.97% |
| 极差 / 中位数 | 36.1% |

**12% 的变异系数看起来很大，但它不是测量噪声——是量化。**

样本明显聚成四簇，**簇间差恒为 0.47 / 0.47 / 0.49 秒**。
这与板端 poll 回调的节拍一致：`stage1_dna.c` 的注释记载
「两个独立的 `tcp_slowtmr` 驱动源叠加，有效间隔 250~500 ms」，
而整条流水线要走十几个 poll 步，**总耗时因此落在 ~0.5 s 的格点上**。

**可解释性判据成立**：波动 = 落在哪个格点，由任务开始时刻与定时器相位的关系决定，
与输入无关、与硬件状态无关。**同一簇内的抖动仅 ±0.01 s（0.3%）**，
那才是真正的测量噪声。

> **推论（报告性能数字时必须遵守）**：单次运行的耗时最多只能精确到 ±0.5 s，
> **报任何板端耗时都必须给出重复次数与中位数**，不得用单次结果做比较——
> 两个配置相差 0.4 s 完全可能只是落在了不同格点上。

## 4. 事实边界

1. **PL 计算的 ~2.1 s 是按斜率 0.5157 ms/记录推算，不是直接测量**——
   板端没有 PL 级的独立计时器，`[waiting]` 里 PL 计算与 poll 空等**无法直接分离**，
   只能由「总等待 − 模型推算的计算量」得到。该拆分的误差未量化。
2. 全部数据为 SE150 / 150 bp / 2,048 源读段；其他规模的量化格点数会变
   （poll 步数随帧数增长），**不要把 0.5 s 格点外推到全量任务**。
3. 主机侧 FASTQ 解析与 LDPC 译码耗时取自既有报告，非本轮重测。
