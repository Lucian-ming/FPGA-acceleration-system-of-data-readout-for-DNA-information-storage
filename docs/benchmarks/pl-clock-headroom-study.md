# PL 时钟裕量评估：100 MHz 以上是否值得（2026-10-14）

## 结论

**当前唯一有实测布线证据的频率是 100 MHz。** 指定的 K=2 + 片上 LDPC 实现以 100 MHz 收敛，WNS 为 +0.334 ns、WHS 为 +0.036 ns，失败端点为 0。按该次布线结果线性外推，当前最差路径的时序上限约为 **103.46 MHz**；这不是 103.46 MHz 实测，更不是可发布频率。

| 目标频率 | 同一布线结果按周期缩短后的估算 WNS | 当前布线结果能否满足 | 不改 RTL、只换约束/实现策略后能否称为“稳定可用” |
| ---: | ---: | --- | --- |
| 105 MHz | −0.142 ns | **不可行**：负裕量约 142 ps | **证据不足**：可能值得做隔离的 P&R 探针，但必须先回收至少 142 ps，且要留额外余量 |
| 110 MHz | −0.575 ns | **不可行**：负裕量约 575 ps | **证据不足**：没有新策略的布线结果；现有数据不支持稳定承诺 |
| 125 MHz | −1.666 ns | **不可行**：负裕量约 1.666 ns | **证据不足，且不建议按约束/实现策略单独追**：需要大幅改善，现有路径含显著逻辑延迟 |

因此，对“现在能否稳到 105/110/125 MHz”的发布判断是：**都不能据现有证据判为可行**。这不等于证明 RTL/器件组合在数学上永远达不到这些频率；替代实现策略没有跑过，故其能力属于证据不足。产品构建入口目前还明确拒绝非 100 MHz 配置。

**收益有限**：以 110 MHz（频率提高 10%）估算，全量档 `t_result` 最理想可省约 0.54–0.55 s；考虑文档推导的 PL 占比 87.8% 后，估计约省 0.47–0.48 s，整轮约 7.5%。这不足以抵消重建全套制品、时序复核和板端逐 SHA 验收的成本与误码风险，现阶段不推荐仅为此提高时钟。

## 1. 证据范围和基线

主证据是现有已布线报告：

`hw/build/bkb220-p16-k2-ldpc-20261014T102111Z-board-migrate/reports/timing.rpt`

报告头标明 Vivado 2022.2、器件 `7z020-clg400`、速度等级 `-2`，运行命令为 `report_timing_summary -max_paths 10`（L3–L9）。利用率取同目录 `reports/util.rpt`，其设计状态为 Physopt postRoute，顶层共 36,600 LUT、37,606 FF、89 RAMB36、6 DSP。

基线时钟周期 10 ns / 100 MHz（`timing.rpt` L155–L159）。汇总 WNS +0.334 ns、WHS +0.036 ns、setup/hold 失败端点均为 0；时序报告称所有用户约束均满足（L142–L147，时钟路径分项见 L231–L233）。

这里的余量是**单一实现**上的 STA 结果。按本任务指定的口径，它是在常温、标称电压下的裕量；它不覆盖板上温度/电压边界，也不代表多次布局布线的分布。路径报告将 worst setup path 标为 Slow Process Corner（L245），但本任务没有上板，也没有进行温压扫描。

## 2. 当前最差路径的真实构成

当前最差 setup 路径不是 Stage1，而是片上 LDPC decoder：从 `llr_mem_reg_0_4/CLKBWRCLK`（RAMB36E1）到 `state_reg[3]/D`（FDRE）。报告给出的数据路径延迟为 **9.402 ns**，其中：

- 逻辑延迟 **4.495 ns（47.809%）**；
- 布线延迟 **4.907 ns（52.191%）**；
- **9 个 Logic Levels**：2 个 CARRY4、3 个 LUT4、1 个 LUT5、2 个 LUT6、1 个 RAMB36E1。

出处：`timing.rpt` L239–L248。路径明细显示 BRAM 级联读出后，信号经过状态/迭代相关 LUT、CARRY4 计数链，再到状态寄存器（L273–L310）。因此这是“BRAM 读出 + LDPC 迭代/控制逻辑”的路径族；不能把它概括为只有布线问题。

报告的十条最长 setup 路径也支持这是一个路径族：9 条从 LLR BRAM 出发，终点分布在 state、emit-slot 和 scan-index 控制寄存器；另一条从 sum BRAM 到 LLR BRAM 写数据。前者为 8–10 个 Logic Levels，后者为 8 个 Logic Levels（例：L321–L330、L403–L411、L567–L576、L650–L659）。

文档中“最差路径 84.5% 是布线”的说法（`bkb220-p16-full-flow-compression.md` §2D；`bkb220-p16-time-budget.md` §5 第 10 项）**不能由这份指定的当前报告复现**：当前 worst setup path 是 52.191% 布线；十条最长 setup 路径的布线占比约 44.3%–52.2%。时间预算表中的 WNS +0.617 ns 也与当前报告 +0.334 ns 不同。除非另有对应 build 的报告，不应把 84.5% 或 +0.617 ns 当作本次 K=2 + LDPC 布线结果。

## 3. 105/110/125 MHz 的时序推算

线性估算以“保持当前网表、布局布线、时钟插入延迟、时钟不确定度和端点 setup 值不变，只缩短周期”为前提。最差路径报告给出：数据路径 9.402 ns、setup 0.059 ns、时钟不确定度 0.081 ns、有效不利 skew 0.124 ns（`timing.rpt` L247、L249、L253、L314）。所以当前路径的周期需求约为：

```text
Tmin ≈ 9.402 + 0.059 + 0.081 + 0.124 = 9.666 ns
Fmax ≈ 1000 / 9.666 = 103.46 MHz
```

用 WNS 表示同一个一阶近似：

```text
WNS(f) ≈ 0.334 ns − (10 ns − 1000/f)
```

因此用户给出的 `100/(1−0.0334) ≈ 103.5 MHz` 粗算是**正确的一阶换算**。它把 0.334 ns 当作 10 ns 周期的 3.34% 裕量。它只给出当前实现的静态上限估值；新频率会改变 Clock Wizard 的实际配置、时钟偏斜/抖动以及布局布线结果，不能把估值称为新频率实测。

| 频率 | 周期 | 相对 100 MHz 少掉的周期 | 同一布线估算 WNS |
| ---: | ---: | ---: | ---: |
| 100 MHz | 10.000 ns | 0 | +0.334 ns（报告实测） |
| 105 MHz | 9.524 ns | 0.476 ns | −0.142 ns |
| 110 MHz | 9.091 ns | 0.909 ns | −0.575 ns |
| 125 MHz | 8.000 ns | 2.000 ns | −1.666 ns |

若改善全来自最差路径的布线部分，达到“刚好 WNS=0”至少需要从 4.907 ns route delay 中回收约 2.9%（105）、11.7%（110）、34.0%（125）；这些还没有给温压、实现种子和 release guardband 留空间。只靠给 100 MHz 实际时钟写更紧的 XDC 约束不会提高硬件时钟，只会让 STA 报告更严格。

## 4. 实现手段、门槛与风险

| 手段 | 对本设计的适用性 | 门槛与风险 |
| --- | --- | --- |
| 降逻辑级数 | 当前路径包含 LDPC BRAM 读出、迭代计数/失败检查的 CARRY4 与 LUT 链。可通过重构控制/比较逻辑、分段或预计算来减少组合深度，但这需要 HDL/RTL 变化，超出“只调约束/实现策略”的前提。 | 会影响 LDPC 状态转换、收敛行为及读写时序；必须重跑仿真、完整构建，并以全量板端 SHA 逐位相同为唯一正确性门禁。若 RTL 不动，只能期待工具的重定时/复制有限改善，当前无证据可量化。 |
| 调整 place / physopt 策略 | 可以在隔离构建目录中比较 timing-driven place、physopt/route 选项和不同 seed；当前 route 占约一半数据延迟，物理优化值得作为 105 MHz 探针。 | 单个 seed 不是“稳定”。每个候选都要重新完整 route、确认 WNS/WHS 与拥塞，并做多个独立 seed。现有 WHS 仅 +0.036 ns，改动布线也可能改变 hold 修复和 setup 结果。 |
| 修改 XDC / 时钟配置 | 约束本身不能让板上时钟变快。`top.xdc` 说明时钟由 PS7 与 BD 内 Clock Wizard 自动生成；实际频率由 `hw/scripts/bd.tcl` 的 `CONFIG.CLKOUT1_REQUESTED_OUT_FREQ` 设置。生产入口 `hw/scripts/build.tcl` 当前固定拒绝 `clk_mhz != 100`。 | 真正提频需要独立实验构建配置、生成新的时钟网表并重新实现；不能放宽 uncertainty、加 false path 或错误 multicycle 来“制造”正 WNS。BD 把同一时钟送给 PS GP/HP、AXI DMA、Stage1、voter、decoder 和 LDPC，因此是整条 PL/AXI 域一起提频，不能只针对 Stage1。 |
| 换速度等级 | 当前实现目标是 `xc7z020clg400-2`（报告头 L8–L9）。更快 speed grade 可能提升器件时序模型，但不能通过把约束文件改成 `-3` 来改变现有板上 FPGA 的硅片等级。 | 必须更换并确认实际器件/板卡为对应 speed grade，再按新器件重新构建和验收；物料、功耗/热条件与硬件兼容性均需重新核实。对当前 -2 板不能作为无 RTL 的软件旋钮。 |

### “稳定可用”的建议验收门槛

后续若值得继续探测，应在新 build/report 目录使用真正的 Clock Wizard 目标频率，不覆盖本次报告：

1. 目标频率下完整实现，setup WNS ≥ 0、hold WHS ≥ 0，所有约束端点无失败；应同时检查 max/slow 与 min/fast 条件。
2. 至少多个独立 place/route seed 都收敛，并保留报告、约束和制品 manifest。单次幸运 seed 不能代表稳定。
3. 新 bitstream/XSA/软件整套构建；板测覆盖目标数据档、反复运行和实际温压范围。任何改频后的功能正确性仍只以指定全量 SHA `fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3` 逐位相同为门禁。

本次不运行新的 Vivado implementation：既有 timing summary 已包含十条带单元级延迟/逻辑级数的布线路径，足以判断当前实现的上限估值；非 100 MHz 的生产构建还被入口守卫阻止。没有独立配置和重实现结果时，继续对现有数字过度精算不会提高结论置信度。

## 5. 110 MHz 的端到端收益

基线为全量 103,616 条记录、同小时背靠背板端实测：K=2 无 LDPC `t_result=5.89 s`，K=2 有 LDPC `t_result=6.06 s`；对应整轮约 6.3 s 与 6.4 s（`bkb220-p16-full-flow-compression.md` §0，L10–L17）。

110 MHz 相对 100 MHz 是**频率/吞吐提高 10%**。若把整个 `t_result` 都假设为频率反比缩放，时延是乘 `100/110`，即减少 9.09%：

| 实测基线 | 全部 `t_result` 随频率缩放的乐观值 | 节省 |
| --- | ---: | ---: |
| 5.89 s（无 LDPC） | 5.35 s | 0.54 s |
| 6.06 s（有 LDPC） | 5.51 s | 0.55 s |

但 `t_result` 还包含不随 PL 时钟同比缩短的 PS 管理、cache、lwIP、协议和结算。压缩报告估算 PL 占 87.8%、PS 占 12.2%（`bkb220-p16-full-flow-compression.md` §1，L27–L33；这是推导，不是 110 MHz 实测）。按 Amdahl 模型，`T110/T100 ≈ 0.122 + 0.878×(100/110) = 0.9202`：

| 实测基线 | 87.8% PL 估算下的新 `t_result` | 估算节省 | 对应整轮节省比例（用 6.3/6.4 s 口径） |
| --- | ---: | ---: | ---: |
| 5.89 s（无 LDPC） | 5.42 s | 0.47 s | 约 7.5% |
| 6.06 s（有 LDPC） | 5.58 s | 0.48 s | 约 7.6% |

以上都是模型值，不是新频率实测；上传时间不会因 PL 时钟提高而同比缩短。收益小于“全流程快 10%”的直觉，且必须付出完整重构、多个实现结果、板端温压与 SHA 回归的验证成本。因此建议先保留 100 MHz，优先处理时序路径或其它已列为高收益的候选项；只有独立 P&R 探针拿到可重复余量后，再考虑 105 MHz，而不是直接上 110/125 MHz。
