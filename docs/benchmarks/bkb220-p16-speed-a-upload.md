# A 组（上位机 / 协议侧）时间优化：读段上传段

本文是 `speed` 主线 A 组的工作记录。底稿是
[bkb220-p16-time-budget.md](bkb220-p16-time-budget.md)，它把整轮 13.272 s 拆成
「上传 3.916 s（29.5%，完全串行）／板端处理 8.682 s（65.4%）／LDPC 0.653 s（4.9%）」。

**边界（先写在前面，全文适用）**：本文的板端耗时都是**客户端打印值或固件自报 tick**，
**不是硬件周期计数器**；`hardware_cycles` / `power_w` 仍为 `null`。
所有「前后对照」都是**同一块板、同一份输入、同一天**，并报中位数与离散。

## 2. H-A0 判别实验（**只读，未改任何制品**）

### 2.1 上位机这侧先排除：预处理不是瓶颈

`tools/profile_upload.py`（本轮新增）把「客户端预处理 + 切批」与「网络停等」分开计时，
并在本机回环上跑同一套停等协议做对照。全量档（103616 条记录 / 4,144,640 B 负载 / 104 批）：

| 分段 | 耗时 |
| --- | ---: |
| 客户端预处理（读 FASTQ + 位平面打包 + 正反向 + 切批） | **0.134 s** |
| 本机回环跑同一停等协议（含逐批 ACK） | **0.126 s**（逐批 RTT 中位 0.462 ms） |
| **板端实际** | **3.94 s** |

→ **上位机侧只占 3.4%**，3.8 s 全在等板端。**H-A0 的嫌疑落在板端/协议，不在客户端 CPU。**

### 2.2 板端实测：批次数不是主因

同一份固件、同一输入，只改 `--batch`（`--no-post`，只测上传段，不触发流水线）：

| `--batch` | 批次数 | 上传耗时 | 吞吐 |
| ---: | ---: | ---: | ---: |
| 500 | 208 | **4.25 s** | 7.81 Mbps |
| 1000 | 104 | **4.18 s** | 7.94 Mbps |
| 2000 | 52 | **3.98 s** | 8.32 Mbps |

批次数降到 **1/4**，耗时只降 6%。**H-A0a 判负：停等不是主因。**
→ 吞吐被**每字节**的东西限住，且 ≈ **1 MB/s**。

### 2.3 定位到具体机制

固件用的 BSP 头 `lwipopts.h` 里写着：

```c
#define TCP_MSS 1460
#define TCP_SND_BUF 8192
#define TCP_WND 2048        /* ← 接收窗口只有 2 KB */
```

窗口受限的吞吐就是 `TCP_WND / RTT`。用实测吞吐反推：
`2048 B ÷ 1.036 MB/s ≈ 1.98 ms`，与板端 RTT 同量级（见下），**自洽**。

板端 RTT 复测（`tools/profile_upload.py --rtt-probe`）：ICMP `ping` 平均 **1.20 ms**
（30 包，min 0.801 / max 2.055），而 TCP 小包往返（`PKT_CAPS` 300 次）中位 **8.58 ms**。
两者之差主要来自 `process_caps` 里那行**阻塞式 `xil_printf`**——约 60 字符 @115200 baud
≈ 5 ms 的串口阻塞。**`PKT_BATCH` 的 ACK 路径不打印**，所以它停在 ~2 ms，
正好对上窗口受限的推算。

**H-A0b 成立：`TCP_WND=2048` 是上传段的限速器。**
这也解释了为什么它从未出现在 PS 侧预算里——底稿 §6 的函数级预算统计的是
**流水线阶段**的 `[PIPE]` 计数器，而上传段的时间既不在 `[in-state]` 也不在任何函数计数里。

## 3. H-A1 实现与实测

派生包由 `tools/build_sw_variant.sh` 产出（本轮给它加了两个能力：`--lwip-opt NAME=VALUE`
改 BSP 的 `lwipopts.h` 并重建 BSP 库，`--sync-src` 把权威源 `sw/app/` 同步进派生包）。
**bit / XSA / ps7_init / FSBL 与参考包逐字节相同**（脚本会核验），只有应用 ELF 与 BOOT.bin 不同。

### 3.1 上传段（`--no-post`，全量 103616 条记录 / 4,144,640 B 负载）

同一块板、同一份输入、同一天，逐档改一个变量：

| # | `TCP_WND` | 空闲主循环休眠 | 批大小 | 上传耗时 | 吞吐 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 2048（参考包） | 1000 µs | 1000 | **4.18 s** | 7.94 Mbps |
| 0' | 2048（参考包） | 1000 µs | 2000 | 3.98 s | 8.32 Mbps |
| 1 | **32768** | 1000 µs | 1000 | **3.22 s** | 10.31 Mbps |
| 2 | **32768** | **0** | 1000 | **0.27 s** | **123.4 Mbps** |
| 2' | **32768** | **0** | 2000 | 0.23 s | 141.6 Mbps |

**结论**：`TCP_WND` 单独只带来 1.23×；把空闲主循环的休眠去掉后才是 **15.5×**。
对照 §1.2 预登记的判据（< 1.0 s）——**通过**（0.27 s）。

> 上表是**单次**测量，只用于定方向；**正式口径是 §4 的四档 × 3 次**。

### 3.2 真正的限速器：`NO_SYS=1` 下每圈只收一帧

两处改动里，**空闲休眠才是主项**——这一点在改之前并不明显，值得写清楚：

BSP 是 `NO_SYS=1` 构建（`lwipopts.h` 里 `#define NO_SYS 1`）。而 Xilinx 适配层的
`xemacpsif_input()`（`contrib/ports/xilinx/netif/xemacpsif.c`）那个「一直取到取不出为止」的
`while (1)` 循环，**整个包在 `#if !NO_SYS` 里**——裸机下它每次调用**只取一个以太帧**。

于是：

```text
收包吞吐 ≈ 每帧字节数 ÷ 主循环一圈耗时
```

上传阶段流水线还没起来，`main()` 走的正是「空闲」那一支，而它当时固定 `usleep(1000)`：

```text
1514 B ÷ (1000 µs + 处理开销) ≈ 1.2～1.3 MB/s
```

与实测 **8.4 Mbps ≈ 1.05 MB/s** 同量级（差的那部分是停等与批边界）。
`TCP_WND` 的作用只是让发送方**一直有帧可发**，所以它单独只能小幅改善；
把它放大之后，瓶颈就完全暴露成「一圈一帧」。

**这条同时解释了为什么它从未出现在底稿的 PS 侧预算里**：底稿 §6 的函数级预算统计的是
**流水线阶段**的 `[PIPE]` 计数器，而上传段的时间既不在 `[in_state]` 里，也不落在任何一个被计时的函数上——
它是**主循环的轮询周期**，不是任何一段被调用的代码。

### 3.3 由此作废的旧候选

底稿 §5 第 1 项「**上传与处理重叠**（流式下发，而非先传完再 POST）」：
上传只剩 0.27 s，**重叠能回收的上限也就是这 0.27 s**，
而它要动的是 POST 语义与流水线起始条件（历史上这类改动失败过两次，
见 `docs/05` P3 的「流式阶段批量推进」）。
**性价比已经不成立**：收益从 3.9 s 掉到 0.27 s，风险不变。→ **不做，理由与证据如上。**

## 4. 四档 × 3 次上传扫描（正式口径）

`tools/board/g3_upload_sweep.sh`（已登记进 `tools/README.md`），其中 `first.py` 带 `--no-post`（只跑上传段，不触发流水线）。**两个包各烧一次板、
背靠背测**，同一块板、同一份输入、同一个小时。

| 源读段 | 负载字节 | 参考包（`WND=2048`，眠 1000 µs） | 新包（`WND=32768`，不休眠） | 加速 |
| ---: | ---: | ---: | ---: | ---: |
| 2,048 | 163,840 B | 0.17 / 0.17 / 0.17 s | 0.01 / 0.01 / 0.01 s | **≈ 17×** |
| 8,192 | 655,360 B | 0.67 / 0.67 / 0.67 s | 0.04 / 0.03 / 0.04 s | **≈ 17×** |
| 32,768 | 2,621,440 B | 2.70 / 2.70 / 2.69 s | 0.13 / 0.12 / 0.14 s | **≈ 21×** |
| 全量 51,781 | 4,144,640 B | 4.27 / 4.27 / 4.26 s | 0.19 / 0.19 / 0.26 s | **≈ 22×** |

- **参考包吞吐恒定 ≈ 7.76～7.80 Mbps**，四档几乎不随规模变化 → 与「一圈一帧」的模型一致
  （吞吐由主循环周期定，不由数据量定）。离散极小（全量三次数 4.27/4.27/4.26）。
- **新包吞吐 125～177 Mbps**，随规模上升（小档被连接建立 / CAPS / CONFIG 的固定开销摊薄）。

- 剩余上限：4.14 MB ÷ 0.19 s ≈ 21.8 MB/s ≈ **千兆链路的 17%**。按每帧 69 µs 反推，
  现在限速的是**板端每帧的收包与拷贝开销**（`pbuf_copy_partial` + 攒包后 40 KB `memcpy` 进 DDR），
  不再是轮询周期。再往下要动零拷贝，**收益只有 0.19 s，本轮不做**。

## 5. 全量档端到端前后对照（**同板、同输入、同小时**）

**⚠️ 先说一个必须说清的坑：跨小时对照会把结论做反。**

底稿 §2 记的全量 `t_result` 是 **8.682 s**（今晨的六档矩阵，3 次中位）。
本轮把参考包**重新烧回板子、在同一个小时里重测**，得到的是 **9.33 / 9.34 / 9.34 s**——
比今晨慢 0.65 s（+7.5%）。如果拿"新包的 9.33 s"去比"今晨的 8.68 s"，
就会得出「**优化让处理段变慢了 7.5%**」这个**假结论**。
板端 `t_result` 在同一天内会漂移，**任何 A/B 都必须同小时重测参考包**，不能引用几小时前的数字。

### 5.1 A/B（`run_g3.sh --full --runs 3 --strict-artifacts`，判据轮 SHA 逐位相同）

| 段 | 参考包（同日同小时重测） | 新包（`TCP_WND=32768` + 空闲不休眠） | 变化 |
| --- | ---: | ---: | ---: |
| 水印下发 | 0.01 s | 0.01 s | — |
| **读段上传** | **3.94 s** | **0.27 s** | **−3.67 s（−93%）** |
| 板端处理（`t_result`） | 9.33 / 9.34 / 9.34 s | 9.33 / 9.33 / 9.34 s | 噪声内相同 |
| 上位机 LDPC | 0.65 s | 0.65 s | — |
| **整轮墙钟（含 LDPC）** | **≈ 13.95 s** | **≈ 10.27 s** | **−3.68 s（−26.4%）** |

- 唯一判据（全量 103616 条记录，LDPC 译码后载荷 SHA-256）：
  **两包各 3 轮全部 = `fcd0cf90bd680e7bbdc203e3398119504da0897acac9e2117008b4efb6b1f2c3`，逐位不变。**
- ✅ `run_g3.sh --strict-artifacts` 两包都 **G3 PASS**；新包 bit/XSA/ps7_init/FSBL 与参考包逐字节相同。
- **边界**：`t_result` 是客户端打印值（POST 发出 → 8100 B 结果收齐），**不是硬件周期计数**；
  上传段来自 `first.py` 的 `stats.t_batches`，同样是墙钟。`hardware_cycles` / `power_w` 仍为 `null`。

### 5.2 对 CPU 的倍率（两种口径都写清楚）

底稿 §2.4 的公平 CPU 基线（同机 i5-13500H，C -O3+popcount，全量 103616 记录）：

| 实现 | 每记录 | 全量折算 |
| --- | ---: | ---: |
| 单核 C | 0.219 ms | 22.69 s |
| 4 线程 C | 0.079 ms | 8.19 s |
| 8 线程 C | 0.051 ms | 5.28 s |
| 16 线程 C | 0.038 ms | 3.94 s |

板端新包，**两种口径分别算**：

| 板端口径 | 全量 | 每记录 | 对单核 | 对 4 线程 | 对 16 线程 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **仅板端处理**（`t_result`，同小时） | 9.33 s | 0.0900 ms | 快 **2.43×** | 慢 **1.14×**（基本打平） | 慢 **2.37×** |
| **端到端**（上传+处理+LDPC） | 10.27 s | 0.0991 ms | 快 **2.21×** | 慢 **1.25×** | 慢 **2.61×** |

⚠️ **两边口径不同，必须一起读**：CPU 数**只算比对内核**；板端 `t_result` 是端到端里的一段，
**端到端**那行还含上传、水印、DMA、Voter、协议与固定开销。所以这个对照**偏向 CPU**——
板端一旦打平，实际是赢的。

**本轮没有改变这个倍率**，要如实说：
同小时参考包 `t_result` = 9.34 s（0.0901 ms/记录）、新包 9.33 s（0.0900 ms/记录），
**处理段本身没变**——本次改动只动了上传段。所以「对 CPU 的倍率」与底稿 §2.4 相比**基本没动**，
只是端到端每记录从 0.1346 ms（同小时参考包 13.95 s ÷ 103616）降到 0.0991 ms，
**对 16 线程的距离从 3.54× 缩到 2.61×**。真正的差距要靠 PL 才能抹平（见 §7）。

## 6. C 组（PL）：唯一能改变「对 CPU 倍率」的方向（**设计已审，未实施**）

§5.2 已经说明本轮的改动**没有改变对 CPU 的倍率**——它把端到端从 13.95 s 压到 10.27 s，
但 `t_result` 一动没动。要真正缩短与 16 线程 CPU 的距离，只能动 PL：板端 9.33 s 里
**PL 约 8.2 s（87.8%）**，PS 侧约 1.1 s。

本轮派了一个**只读**子 Agent（`stage1-multibase`）做 `S_RUN` 多碱基并行的设计审查与探针方案，
产出（**均为静态推导/外推，不是综合也不是实测**）：

| 项 | 结论 |
| --- | --- |
| 现状 | `srpe_batch_pway.v` 的 `S_RUN` 每拍取**一个**碱基索引，并行比较 **16 起点 × 64 记录 = 1024** 个匹配位；`score` 是寄存器数组（16×64×10 位）不是 BRAM；Stage1 OOC 基线 26,867 LUT / 8 RAMB36 |
| K=2 / K=4 改动点 | 新增 1,024 / 3,072 个符号比较单元；读段 BRAM 需按奇偶 bank 拆（K=4 每拍要 j…j+3）；水印 BRAM 需 4 个模 4 bank 或双读口；`S_RUN` 150 拍 → 75 / 38 拍 |
| 资源外推 | K=2 整机约 36k～40k LUT；**K=4 约 40k～48k LUT**（XC7Z020 上限 53,200）。**K=4 高端估算只剩约 5.2k 余量** |
| 时序风险 | 现 WNS 仅 **+0.617 ns**，最差路径 84.5% 是布线。K=4 的多读口与高扇出可能压穿——**必须走 OOC 探针，不能只看 LUT 预算** |
| 预充/排空重叠 | 现 `S_PREFILL 18` + `S_UPD1 5` + `S_UPD2 1` + `S_NEXT 1` 串行；可重叠的**上限是 7 拍**。K 路预充可把 18 拍压到 ≈11（K=2）/ ≈7（K=4）拍 |
| 周期模型 | 每块 176 拍 → K=2 **101** 拍 / K=4 **64** 拍；若再省 7 拍则 87 / 57 拍 |
| 全量估算 | 按 PL 7.77 s 外推：K=4 保留 64 拍 ≈ **3.91 s**；省 7 拍 ≈ **3.60 s**（目标 3.70 s） |

**未做（写清理由，留给接手者）**：本轮**没有**实现 K=2/K=4 的 RTL，也没有跑 OOC 探针。
理由是这是一次**结构性 RTL 改动**（参数化 `srpe_batch_pway` → 接入顶层 / `component.xml` /
`PACKAGED_VARIANTS.txt` → OOC 探针 → 整机 route → 全量功能回归），
在本轮剩余时间内无法既改完又验完，而**改了不验的 RTL 不能进主线**。
探针命令模板、可失败判据（OOC：WNS/WHS≥0、失败端点 0、Stage1 LUT≤40,000；
整机：LUT≤48,000、全量三轮 SHA 逐位不变）已写在子 Agent 的只读交付里，
归集在 `docs/05` 的 P3 条目下。

**块级开销（18+7 拍，占 176 拍的 14%）**：静态看当前 FSM 是串行的，不能自然重叠；
改并行控制后最多省 7 拍。

## 7. 复现与边界

### 7.1 复现命令

```bash
# 上传段的三段拆分（客户端预处理 / 本机回环 / 板端 RTT 探针）——不触板也能跑前两段
python3 tools/profile_upload.py --loopback --json /tmp/up.json
python3 tools/profile_upload.py --rtt-probe 192.168.1.10:7 --rtt-samples 300

# 造派生包（bit/XSA/ps7_init/FSBL 与参考包逐字节相同）
bash tools/build_sw_variant.sh \
  --ref hw/build/bkb220-p16-enet0-software-20261012T144141Z-board-migrate \
  --out hw/build/bkb220-p16-swwnd32k-idle0-<TS>-board-migrate \
  --lwip-opt TCP_WND=32768 --define PIPE_IDLE_SLEEP_US=0 --sync-src \
  --label "H-A1b"

# 烧录 + 全量判据 x3
bash tools/run_g3.sh --artifact-dir <新包> \
  --xsdb D:/xilinx/2026.1/Vitis/bin/xsdb.bat --device xc7z020 --strict-artifacts \
  --uart-port COM10 --ip 192.168.1.10 --port 7 --win-root D:/bkb220_board_speed \
  --full --runs 3

# 四档 x 3 次上传扫描（两包各烧一次，背靠背）
```

### 7.2 边界（引用本文任何数字都要一起说）

1. 所有板端耗时都是**客户端打印值或固件自报 tick**，**不是硬件周期计数器**；
   `hardware_cycles` / `power_w` 仍为 `null`（无外部周期采集、无功率计）。
2. §4 的加速比是**上传段**（`--no-post`，只跑上传不触发流水线）的墙钟，不是整机加速比；
   整机口径见 §5.1 的 13.95 → 10.27 s。
3. **板端 `t_result` 同一天内会漂移**（今晨 8.68 s vs 同小时重测 9.34 s，+7.5%）。
   本文所有 A/B 都用**同小时重测的参考包**；引用底稿 §2 的 8.682 s 时必须注明它是今晨值。
4. §6 的周期、资源与加速比**全部是静态推导/外推**，没有 OOC、没有综合、没有板测。
5. `PIPE_IDLE_SLEEP_US=0` 让主循环在**空闲时也满速自旋**（原来眠 1 ms）。这不影响流水线阶段
   （那一支仍按 `PIPE_RUN_SLEEP_US=200`），但**空闲功耗会升高**——本项目无功率计，
   **未测**，如实记录。
