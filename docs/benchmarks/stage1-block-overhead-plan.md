# Stage1 块内固定开销：分解与压缩方案（2026-10-14）

**这是「全流程压缩」的首选项 A**（[压缩研究 §2A](bkb220-p16-full-flow-compression.md)）。
本文是 **RTL 级分析 + 方案 + 验证计划**；**下列节省量是估算，尚未实测**。

---

## 1. 固定开销在哪（读 RTL 得出，不是公式抄写）

每块拍数 = `1 + 18 + ceil(150/K) + 5 + 1 + 1`。把每一项对到状态机上
（`hw/ip/Dna_accelerator_core_1_0/hdl/srpe_batch_pway.v`）：

| 拍 | 状态 | 在做什么 |
| ---: | --- | --- |
| **1** | `S_LAUNCH` | 置 `pos_base`、清 `score[p][t]`、清 `wm_win`、置 `wm_rd_offset` |
| **18** | `S_PREFILL` | 组装 17 深的参考滑窗，**末三拍**预取 RUN 前两组 |
| 75 | `S_RUN` | `RUN_GROUPS = ceil(150/2) = 75`，真正的相关计算 |
| **5** | `S_UPD1` | 选优树流水排空（`PIPE_TREE=1` ⇒ 等 `P_LOG=4` 级） |
| **1** | `S_UPD2` | 与全局历史最优比较并更新 |
| **1** | `S_NEXT` | `pos_cnt += P_WAYS`，决定下一块还是换 LC |

⇒ **固定开销 = 26 拍 / 101 拍 = 25.7%**（K=1 时是 26/176 = 14.8%——**K=2 把分母砍掉 43%，
把这块的相对权重放大了一倍**，这就是它现在值得做的原因）。

折算整轮（推导，见压缩研究 §2A）：`2550 块/记录 × 26 拍 ÷ 64 记录 = 1,036 拍/记录`，
K=2 实测全量档 ≈5,847 拍/记录 ⇒ **占 ≈17.7%**。

## 2. 两块浪费，各自的成因

### 2.1 `S_PREFILL` 的 18 拍里有 ~6 拍是白等的

`S_PREFILL` 的注释自己写着：「**预充填固定 18 拍**。先按 K 符号组装初始窗口，末三拍预取 RUN 前两组」。

拆开看：**15 拍组装窗口 + 3 拍预取**。
而窗口是 `WM_WINDOW_SIZE = P_WAYS + K - 1 = 17` 深、**每拍能进 K=2 个** ⇒
组装只需要 `ceil(17/2) = 9` 拍。

**15 − 9 = 6 拍是等 ROM 返回**：`pre_cnt` 每拍把 `wm_rd_offset` 推 2 个，
但写窗口的时机由 `wm_tag_lc_qq == lc_idx` 的**标签匹配**决定——也就是说，
这段写成了一个「发一个、等它回来、再发下一个」的变长延迟循环，
拍数按最坏情况定死在 15。

⇒ **把它改成定长流水的读-取结构**（水印 ROM 是 BRAM，延迟是确定的），
组装应能收到 ~9~10 拍。**这是本项最干净的一刀，且不改算法、不改数据通路。**

### 2.2 `S_UPD1/UPD2/NEXT` 的 7 拍里，有 8 拍宽度可以和下一块的预充填重叠

选优树排空（`S_UPD1` 5 拍）读的是 `score[p][t]`，`S_UPD2` 读的是树的输出；
这两者**都不碰 `wm_win` / `wm_rd_offset`**。而下一块的 `S_PREFILL` 只碰后者。

⇒ 只要给 `wm_win` 加**双缓冲**（多一份 17×2 bit 的寄存器，很便宜），
**下一块的预充填就能在 `S_UPD1/UPD2/NEXT` 这 7 拍里并行跑**。

⚠️ 但 `S_LAUNCH` 会清 `score`，而树还在读它 —— 所以 `S_LAUNCH` 的**清 score 必须让位**
（`PIPE_TREE=1` 时树的第一级在 1 拍后已锁存，之后 `score` 即可释放；要按流水级数确认）。
**这是本方案最容易写错的一处，必须以逐周期仿真等价性为门禁。**

## 3. 方案与估算（**估算，未实测**）

| 步骤 | 每块拍 | 相对现状 |
| --- | ---: | ---: |
| 现状（K=2） | **101** | 1.000× |
| ① 预充填改定长流水：18 → 11 | 94 | 1.074× |
| ② `+ wm_win` 双缓冲，预充填与排空重叠 7 拍 | **≈87** | **≈1.16×** |
| ③ 若预充填能进一步压到 9 并全部被吸收 | ≈84 | ≈1.20× |

**折算整轮**：Stage1 约占板端 ≈87.8%（推导），整轮 6.06 s ⇒ **上限约 1.15~1.18×**，
即 **6.06 → 约 5.2 s**。**这是上限估算，不是实测。**

**资源代价**：极低。① 只改控制；② 加一份 `wm_win`（17 × 2 bit = 34 个寄存器）。
**不需要更多 LUT 也不碰 BRAM**——这是它相对 K=3/提时钟的核心优势。

## 4. 验证计划（顺序不能颠倒）

1. **RTL 改动**：只动 `srpe_batch_pway.v` 的 `S_LAUNCH/S_PREFILL/S_RUN/S_UPD1` 附近；
   **不改** `wm_win` 的语义、不改 `score` 的累加、不改选优树。
2. **逐周期仿真等价**：与**改动前**的 RTL 跑同一激励，**逐周期比对**
   `stage1_score/stage1_pos/stage1_lc_idx/stage1_res_valid` 与最终码字输出。
   ⚠️ 拍数会变，所以**不能比"第 N 拍等于第 N 拍"**，要比**每个块的结果序列**。
   项目已有先例判据：`docs/03` 记过「三重逐位比对 + 写死前后周期数逐位相同」的用法。
3. **OOC 布线后天时序**：`SYNTH_IMPL=1`，确认 100 MHz 仍收敛且**只报布线后数字**。
   现状参考：Stage1 K=2 OOC 28,708 LUT / WNS +0.300 ns。
4. **整机 route**：OOC 余量 ≠ 整机余量（本项目实测案例：同模块 OOC +0.444 → 整机 +0.31~0.33）。
5. **上板**：`run_g3.sh`，**唯一判据 SHA `fcd0cf90…b1f2c3` 逐位相同**；
   并做同小时背靠背 A/B（本包 vs `k2freeze`）报板端 `t_result` 与 `[PIPE] total`。

**任何一步没做，就写"没做"。**

---

## 5. ⚠️ 边界（引用本页时必须一起说）

1. **本文全部数字是 RTL 阅读 + 静态推导，没有一行是实测的。**
   26 拍的分解是**从状态机数出来的**（`S_PREFILL` 的注释也自证 18 拍）；§3 的节省量是**估算**。
2. **17.7% 这个占比是推导**：分子 26 拍/块来自公式，分母 5,847 拍/记录由实测 `t_result` 派生。
3. **"15 拍里有 6 拍是等 ROM"是解释，不是测量**——先从注释与代码结构得出，
   **必须用逐周期仿真确认**再当作结论。若实测发现那 6 拍另有用处，方案① 作废。
4. **双缓冲那一步有功能风险**：`S_LAUNCH` 清 `score` 与选优树读 `score` 的先后，
   依赖 `PIPE_TREE` 的具体流水级数，**改错会让结果静默偏移一位而不报错**。
5. 判据永远是那条 SHA。**任何提速只要让这一个字变了，就是错的。**
