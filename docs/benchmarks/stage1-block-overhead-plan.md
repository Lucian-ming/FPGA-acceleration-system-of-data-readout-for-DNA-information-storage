# Stage1 块内固定开销：分解与压缩方案（2026-10-14）

**这是「全流程压缩」的首选项 A**（[压缩研究 §2A](bkb220-p16-full-flow-compression.md)）。
本文是 **RTL 级分析 + 方案 + 验证计划**；**下列节省量是估算，尚未实测**。

---

## 1. 固定开销在哪（读 RTL 得出，不是公式抄写）

每块拍数 = `1 + 18 + ceil(150/K) + 5 + 1 + 1`。把每一项对到状态机上
（`hw/ip/Dna_accelerator_core_1_0/hdl/srpe_batch_pway.v`）：

| 拍 | 状态 | 在做什么 |
| ---: | --- | --- |
| **1** | `S_LAUNCH` | 置 `pos_base`、清 `score[p][t]`、清 `wm_win`、置 `wm_rd_offset` |
| **18** | `S_PREFILL` | 组装 17 深的参考滑窗，**末三拍**预取 RUN 前两组 |
| 75 | `S_RUN` | `RUN_GROUPS = ceil(150/2) = 75`，真正的相关计算 |
| **5** | `S_UPD1` | 选优树流水排空（`PIPE_TREE=1` ⇒ 等 `P_LOG=4` 级） |
| **1** | `S_UPD2` | 与全局历史最优比较并更新 |
| **1** | `S_NEXT` | `pos_cnt += P_WAYS`，决定下一块还是换 LC |

⇒ **固定开销 = 26 拍 / 101 拍 = 25.7%**（K=1 时是 26/176 = 14.8%——**K=2 把分母砍掉 43%，
把这块的相对权重放大了一倍**，这就是它现在值得做的原因）。

折算整轮（推导，见压缩研究 §2A）：`2550 块/记录 × 26 拍 ÷ 64 记录 = 1,036 拍/记录`，
K=2 实测全量档 ≈5,847 拍/记录 ⇒ **占 ≈17.7%**。

## 2. 两块浪费，各自的成因

### 2.1 `S_PREFILL` 的 18 拍里，**只有 9 拍真正写进了窗口**（已实测）

`S_PREFILL` 的注释自己写着：「**预充填固定 18 拍**。先按 K 符号组装初始窗口，末三拍预取 RUN 前两组」。

**实测**（只读探针，复制 TB 加计数器，未改任何 RTL；`P_WAYS=16 / PIPE_TREE=1 / NUM_LC=2`）：

| 量 | 值 |
| --- | ---: |
| `S_PREFILL` 总拍数 | 1,836（102 块 ⇒ **18 拍/块**） |
| 其中**真正落进窗口的写**（tag 匹配 **且** 位置守卫成立） | **920 ⇒ 9.02 拍/块** |
| **不写窗口的拍** | **≈9 拍/块** |

窗口是 `WM_WINDOW_SIZE = P_WAYS + K - 1 = 17` 深、每拍进 K=2 个 ⇒ 装填本就需要
`ceil(17/2) = 9` 拍。**实测正好 9.02** ⇒ **另外 ~9 拍没有产生窗口写**，
它们在做「发 ROM 读地址 / 等数据回来」——也就是这段写成了**非流水的读-取结构**
（发一个、等它回来、再发下一个），拍数按最坏情况定死在 15 拍组装 + 3 拍预取。

⇒ **把它改成定长流水的读-取结构**（水印 ROM 是 BRAM，延迟是确定的），
组装应能收到 ~9~10 拍，**每块省约 8 拍**。这是本项最干净的一刀，
**不改算法、不改数据通路语义**。

> **⚠️ 一条被否掉的中间判断（留证）**：本文初版写「**15 − 9 = 6 拍是等 ROM**」，
> 依据是 RTL 阅读。随后第一个探针去数「写条件 `wm_tag_lc_qq == lc_idx` 成立的拍」，
> 得到 **17.99/18**——**看起来把这条否掉了**。但那个探针数错了信号：
> tag 匹配是**外层**条件，真正决定「这一拍有没有贡献」的是**内层的位置守卫**
> （`wm_tag_qq ∈ [pos_base, pos_base+17)`）。改成数守卫之后得到 **9.02 拍**，
> 原判断**方向成立**（数值从 6 修正为 ~9）。
> **教训：RTL 里的"条件成立"往往有多层，数错一层就会把结论翻过来。**

### 2.2 `S_UPD1/UPD2/NEXT` 的 7 拍里，有 8 拍宽度可以和下一块的预充填重叠

选优树排空（`S_UPD1` 5 拍）读的是 `score[p][t]`，`S_UPD2` 读的是树的输出；
这两者**都不碰 `wm_win` / `wm_rd_offset`**。而下一块的 `S_PREFILL` 只碰后者。

⇒ 只要给 `wm_win` 加**双缓冲**（多一份 17×2 bit 的寄存器，很便宜），
**下一块的预充填就能在 `S_UPD1/UPD2/NEXT` 这 7 拍里并行跑**。

⚠️ 但 `S_LAUNCH` 会清 `score`，而树还在读它 —— 所以 `S_LAUNCH` 的**清 score 必须让位**
（`PIPE_TREE=1` 时树的第一级在 1 拍后已锁存，之后 `score` 即可释放；要按流水级数确认）。
**这是本方案最容易写错的一处，必须以逐周期仿真等价性为门禁。**

## 2b. ✅ 方案① 已实现并验证（2026-10-14）

**改动**（`hw/ip/Dna_accelerator_core_1_0/hdl/srpe_batch_pway.v`，仅 `S_PREFILL` 的地址段）：

```verilog
localparam integer PREFILL_BODY =
    (WM_WINDOW_SIZE - BASES_PER_CYCLE + BASES_PER_CYCLE - 1) / BASES_PER_CYCLE;  // K=2 时 = 8
```

原写法按 `P_WAYS-1 = 15` 组发地址，其中 7 组返回的 tag 落在窗口外、被位置守卫丢弃。
改成只发那 8 组；**末 3 组（给 `S_RUN` 预热）的地址序列原样保留**。
`S_PREFILL` 由 18 拍降到 **11 拍**。

### 逐位等价（硬门禁，先过这个才敢动生产文件）

| 证据 | 结果 |
| --- | --- |
| **差分仿真**：旧 RTL 与 新 RTL 同一激励并跑，比 `score`/`pos`/`cw` | **各 0/64 不符**；周期 88,915 → **86,773**，即 **每块省 7.0 拍**（2,142 ÷ 306 块） |
| **既有回归** `tools/run_sim.sh stage1_pway`（P4 与 P16 两条） | **2/2 PASS**，各 0/64 不符 |

### OOC 布线后时序与资源（**真 A/B，同参数同脚本同一天**）

| | WNS | WHS | Slice LUT | RAMB36 |
| --- | ---: | ---: | ---: | ---: |
| 未改动 RTL | **+0.300 ns** | +0.078 | **28,708** | 12 |
| 改动后 | **+0.755 ns** | +0.084 | **28,428** | 15 |

（未改动那份的 +0.300 / 28,708 与 `stage1-multibase-ooc-probe.md` 的历史记录**逐位吻合**，
说明这就是同口径对照，不是拿不同配置比的。）

⇒ **净赚 +0.455 ns 时序余量，LUT 还少 280。** 预充填变短，关键路径也跟着短了——
这是本项没有预料到的附带收益。

### 折算

每块 101 → 94 拍（−6.9%）。按 Stage1 占板端 ≈87.8%（**推导**）折整轮：
整轮 6.06 s ⇒ **约 5.7 s（≈1.06×）**。

⚠️ **这仍是折算，不是板端实测**——整机与上板验证**尚未做**（见 §4）。

## 3. 方案与估算（②③ 仍是**估算，未实测**）

| 步骤 | 每块拍 | 相对现状 | 依据 |
| --- | ---: | ---: | --- |
| 改前（K=2） | 101 | 1.000× | **实测**（探针） |
| **① 预充填压到能落进窗口的组数** | **94** | **1.074×** | ✅ **已实现、已逐位等价、OOC WNS 反而 +0.455 ns** |
| ② `+ wm_win` 双缓冲，预充填与排空（5 拍）重叠 | ≈89 | ≈1.13× | 估算 |
| ③ 若预充填能进一步与 RUN 前段重叠 | ≈85 | ≈1.19× | 估算 |

**折算整轮**：Stage1 约占板端 ≈87.8%（推导），整轮 6.06 s ⇒ **上限约 1.15~1.18×**，
即 **6.06 → 约 5.2 s**。**这是上限估算，不是实测。**

**资源代价**：极低。① 只改控制；② 加一份 `wm_win`（17 × 2 bit = 34 个寄存器）。
**不需要更多 LUT 也不碰 BRAM**——这是它相对 K=3/提时钟的核心优势。

## 4. 验证计划（顺序不能颠倒）

1. **RTL 改动**：只动 `srpe_batch_pway.v` 的 `S_LAUNCH/S_PREFILL/S_RUN/S_UPD1` 附近；
   **不改** `wm_win` 的语义、不改 `score` 的累加、不改选优树。
2. **逐周期仿真等价**：与**改动前**的 RTL 跑同一激励，**逐周期比对**
   `stage1_score/stage1_pos/stage1_lc_idx/stage1_res_valid` 与最终码字输出。
   ⚠️ 拍数会变，所以**不能比"第 N 拍等于第 N 拍"**，要比**每个块的结果序列**。
   项目已有先例判据：`docs/03` 记过「三重逐位比对 + 写死前后周期数逐位相同」的用法。
3. **OOC 布线后天时序**：`SYNTH_IMPL=1`，确认 100 MHz 仍收敛且**只报布线后数字**。
   现状参考：Stage1 K=2 OOC 28,708 LUT / WNS +0.300 ns。
4. **整机 route**：OOC 余量 ≠ 整机余量（本项目实测案例：同模块 OOC +0.444 → 整机 +0.31~0.33）。
5. **上板**：`run_g3.sh`，**唯一判据 SHA `fcd0cf90…b1f2c3` 逐位相同**；
   并做同小时背靠背 A/B（本包 vs `k2freeze`）报板端 `t_result` 与 `[PIPE] total`。

**任何一步没做，就写"没做"。**

## 5. ⚠️ 边界（引用本页时必须一起说）

1. **本文全部数字是 RTL 阅读 + 静态推导，没有一行是实测的。**
   26 拍的分解是**从状态机数出来的**（`S_PREFILL` 的注释也自证 18 拍）；§3 的节省量是**估算**。
2. **17.7% 这个占比是推导**：分子 26 拍/块来自公式，分母 5,847 拍/记录由实测 `t_result` 派生。
3. **"18 拍里只有 9 拍真正写窗口"是实测**（920/102 = 9.02，位置守卫口径）；
   **但那 9 拍"没在写窗口"的部分具体在等什么，仍是解释不是测量**——
   「等 ROM 固定延迟」是最合理的解释，**没有做隔离实验**（例如把读地址生成提前若干拍再综合）。
   若实测发现那 9 拍另有约束，方案① 的节省量要重估。
4. **双缓冲那一步有功能风险**：`S_LAUNCH` 清 `score` 与选优树读 `score` 的先后，
   依赖 `PIPE_TREE` 的具体流水级数，**改错会让结果静默偏移一位而不报错**。
5. 判据永远是那条 SHA。**任何提速只要让这一个字变了，就是错的。**

### ⚠️ 2026-10-15 分母更正（**引用本页任何百分比前必读**）

`101 拍` / `94 拍` 是**块内 FSM 状态驻留拍数**，作为这个口径它是**实测准确的**：
板端硬件计数器 + 仿真逐状态分解都给出 `S_LAUNCH 1 + S_PREFILL 11 + S_RUN 75 +
S_UPD1 5 + S_UPD2 1 + S_NEXT 1 = 94`（`[HW-CYCLES] Stage1`）。

**但归一化后的每块实际硬件成本是 `116.82 拍`**（板端实测，与仿真逐状态分解差 0.0000；
留证 `logs/board/stage1-hardware-cycles-20261015.md`）。
差额 **22.82 拍/块**来自两项**不按块计**的工作：

| 状态 | 计次单位 | 次数/批 | 折算拍/块 |
| --- | --- | ---: | ---: |
| `S_LOAD_R` | **每记录一次** | 64 | 11.2941 |
| `S_EMIT`+`S_EMIT2`+`S_EMIT_W` | **每碱基位一次** | 9,600 | 11.2941 |

⇒ **凡是用 `101` 或 `94` 当"Stage1 时间"分母的百分比都要重算。** 最受影响的是本页
"每块 101 → 94 拍（**−6.9%**）"：那 7 拍相对 Stage1 硬件时间的真实占比是
`7 ÷ 123.82 ≈ **5.7%**`，不是 `7 ÷ 101 = 6.9%`。

⚠️ 这**不代表**那 22.82 拍可回收——`S_LOAD_R` 与结果发出都是**必要工作**，
能否与 `S_RUN` 重叠是**尚未评估的 RTL 设计任务**。

⚠️ **第 5 步的证据范围（2026-10-14 晚才核清，引用时必须一起说）**：

  ⇒ 它**不能**用来证明**当前**源码。
