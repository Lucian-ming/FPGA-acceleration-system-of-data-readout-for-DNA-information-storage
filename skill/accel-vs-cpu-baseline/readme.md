# 技能包：给加速器找一个「打得过也说得清」的软件基线

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

做了 FPGA 加速，要回答「到底快了多少」。这件事有两个坑：

1. **基线太弱**：拿未优化的 Python 或单线程朴素实现当对照，加速比很好看，但评委一问就塌；
2. **基线不可比**：拿桌面/笔记本 CPU（几十瓦、多核、宽 SIMD）对比嵌入式 FPGA，
   赢了不服人、输了不甘心，而且**回答不了「为什么要用 FPGA」**。

这份技能包给的是一套**分层基线**的做法，以及把「同片 CPU」作为主基线的理由和实现框架。

## 使用方法

### 1. 至少报三条基线，而不是一条

| 基线 | 回答的问题 | 怎么做 |
| --- | --- | --- |
| **同片 CPU（主基线）** | 把这段计算放进 PL，比留在同一颗 SoC 的 ARM 上快多少 | 同一块板、同一份数据，PS 裸机跑优化过的 C |
| 优化过的桌面 CPU 单核 / 多核 | 和通用计算机比处在什么位置 | 同一算法的 `-O3` 实现，多核用 OpenMP |
| 未优化参考实现 | 只用来验证正确性，**不作为加速比分母** | Python / 朴素 C |

**同片 CPU 是最有说服力的那条**：器件相同、供电相同、数据通路相同，
差别只有「算在 PS 还是算在 PL」，正好就是你的设计决策本身。

### 2. 软件基线必须是「认真优化过的」

否则加速比是虚的。至少做到：

- 开 `-O3`，指定目标架构（`-mcpu=cortex-a9 -mfpu=neon`）；
- 数据布局对齐硬件的做法（例如位平面 + 按位运算），而不是逐元素比较；
- **检查编译产物**：ARMv7 上 `__builtin_popcountll` 会退化成库函数调用，
  必须用 NEON 指令自己写，再用 `objdump` 确认真的生成了 `vcnt`。
  没确认过的「优化实现」，很可能慢了好几倍，让你的加速比虚高。

### 3. 板上跑软件基线的框架（不必改生产固件）

参考模板：[`baremetal_baseline.tcl.in`](baremetal_baseline.tcl.in)（**Zynq PS 专用**：
用 XSDB + `ps7_init` + ARM 裸机 ELF；换成其它 SoC 时，方法不变，驱动与工具链换成该平台的）。
流程是：

```text
主机准备数据 ──► XSDB 复位 PS + ps7_init ──► dow -data 把数据写进 DDR
      │                                            │
      │                                     dow 裸机 ELF ──► con（跑）
      │                                            │
      └── 同一份 C 在主机编译出参考答案        轮询 DDR 里的完成标志（mrd -force）
                       │                            │
                       └──────► 逐条比对 ◄──── 读回结果与计时
```

要点：

- **写一个独立的裸机程序**，和生产固件分开：不碰生产代码就不会引入回归；
- 计时用硬件计数器（`XTime`），只计算法本身，准备阶段另计；
- 结果写回 DDR 之前 **`Xil_DCacheFlush()`**：调试器读的是 DDR，不是 CPU 缓存，
  不刷新就会读到旧数据；
- **同一份 C 文件在主机上再编译一次**当参考答案，逐条比对（分数、位置等全部字段），
  全部一致才采信耗时。**只报速度不报正确性的基线没有意义**；
- 轮询完成标志用 `mrd -force`，避免反复 `stop` 打断计时。

附件调用示例、占位符、成功输出和失败判据见下方「附件接口与判读」。这里的 XSDB 流程是 Zynq 裸机模板；其他 SoC/PYNQ 项目保留对照实验与比较协议，替换下载、同步和计时入口。

### 4. 报告口径

- 统一到「每单位工作量」（每条记录、每帧、每样本），而不是总时长；
- 注明重复次数、取中位数还是均值；
- 给出对方的核数、频率、编译选项；
- 未测的项目（比如功耗）**明确写「未测」**，不要用估算填表。

## 失效条件

- 同片 CPU 基线只在 SoC 类器件（Zynq / MPSoC / Versal）上成立；纯 FPGA 板没有这条基线。
- 若加速核与 CPU 跑的**不是同一个算法**（例如硬件做了近似、剪枝），加速比不可比，
  必须先说明算法等价性，或改用「达到同等结果质量所需时间」作为口径。
- 本框架测的是**计算本身**。端到端还包含传输、DMA、后处理，两者不要混用。
- 裸机单核结果不能直接乘以核数当多核结果，多核要实测。

## 已验证效果

本项目旧板 **XC7Z010** 于 2026-09-22 的历史实测（SE150 数据集；不是 BKB220 新板 CPU 基线）：

| 实现 | 每条记录耗时 | 全量任务 |
| --- | ---: | ---: |
| 同片 ARM Cortex-A9 单核（裸机、-O3、NEON popcount） | **12.10 ms** | 约 1,254 s（外推） |
| PL 加速核（4 路 @100 MHz） | **0.2451 ms** | **25.69 s（实测）** |
| 项目 48 核服务器参考实现（Xeon Gold 5220R ×48 @2.20 GHz） | — | 675 条 / 41.07 s（滑动相关 **16.6 条/s**） |

- **同片对比：PL 快约 49 倍**，这是最能说明「为什么要做这个加速器」的一条；
- **CPU 基线已按 2026-10-20 要求统一为项目 48 核服务器**；旧的笔记本 16 线程数据已删除。该基线与板端 `t_result` 的输入规模、计时边界不同，**不相除、不写成严格加速比**；
- 正确性：1,024 条读段的结果与主机参考**逐条完全相同**，之后才采信耗时；
- 稳定性：16 / 256 / 1,024 三档测出的每条记录耗时分别是 12.086 / 12.101 / 12.103 ms。

### BKB220 P4 / P16 的边界

2026-10-12 新板阶段样本给出同板 P4/P16 的 `t_result` 对照：全量 P4 为 26.51 s，P16 为 8.61 / 8.71 / 8.61 s。随后正式六档矩阵已完成，见 `report/design-report-2026.pdf` §4 的同板 P4/P16 对照表；该早期样本保留为历史测量，不作当前绝对值。上传转正记录的最新同小时参考 `t_result` 为 9.33 s。以上均比较 PL 配置且不含上传与 LDPC，**不能替代同片 ARM 基线**。上表 12.10 ms/记录的 ARM 数字来自旧板；没有同一输入、同一口径的新板 ARM 重测前，不得把它与 BKB220 P16 时间拼成严格公平加速比。

模板 `baremetal_baseline.tcl.in` 只负责驱动板端程序、轮询状态和导出结果。它不会自行证明结果正确；主机端逐字段比较器必须在任一字段不一致时返回非零，超时或板端错误状态也必须判失败，速度只有在这些检查通过后才能进入基线表。

### 附件接口与判读

模板中的 `@@OUT@@`、`@@N@@`、`@@TIMEOUT@@` 分别是 XSDB 主机可访问的目录、记录数和超时秒数。目录内需有 `ps7_init.tcl`、`ref.bin`、`input.bin` 和 `baseline.elf`。`@@OUT@@` 使用 Tcl 可读的路径，建议不含大括号。`header_addr`、数据区地址、状态/结果地址以及 `init_magic` / `done_magic` / `error_magic` 都是示例值，必须与 ELF 的共享内存协议一致；模板假设每条输出占 4 字节。

从提交包根目录生成并运行一份实例（把路径和数量换成真实值；XSDB 主机必须能访问该目录）：

```bash
python3 - <<'PY'
import re
from pathlib import Path

src = Path("skill/accel-vs-cpu-baseline/baremetal_baseline.tcl.in")
dst = Path("baseline_run.tcl")
values = {"@@OUT@@": "D:/fpga_baseline/run1", "@@N@@": "1024", "@@TIMEOUT@@": "60"}
text = src.read_text(encoding="utf-8")
for key, value in values.items():
    text = text.replace(key, value)
# 只查「真正会被执行的占位符」：模板头部用 @@...@@ 描述占位符本身，
# 用子串 `"@@" in text` 判断会被那行注释永久误判为未替换。
left = [
    (no, m.group(0))
    for no, line in enumerate(text.splitlines(), 1)
    if not line.lstrip().startswith("#")
    for m in re.finditer(r"@@[A-Za-z_][A-Za-z0-9_]*@@", line)
]
if left:
    raise SystemExit("未替换完模板占位符: " + ", ".join(f"第{n}行 {p}" for n, p in left))
dst.write_text(text, encoding="utf-8")
print("占位符检查通过，已生成", dst)
PY
xsdb baseline_run.tcl
```

这段检查只看非注释行里的 `@@名字@@` 形式，所以模板注释里那句「把 @@...@@ 占位符替换成实际值」不会触发误报（`@@...@@` 里的 `...` 不匹配占位符名，且在注释行内）。如果你的模板把某个占位符写在注释里当真实参数用，请先把该行改成非注释，检查才会覆盖它。

完成时应看到 `BASELINE> status 0x... after ... s` 和 `BASELINE> dumped`，并生成 `sum.bin`、`result.bin`。`exit 0` 只说明板端报告完成且 XSDB 导出了数据；主机端必须读取摘要和结果，与同一输入的软件参考逐字段比较，任何差异都要返回非零。

失败时，板端写入 `error_magic` 会打印 `BASELINE> FAIL board reported error ...` 并以状态 2 退出；未在 `@@TIMEOUT@@` 秒内看到完成标志会打印 `FAIL timeout` 并退出 2；反复 `mrd err` 后也会超时。文件不存在、XSDB 连接/下载错误或占位符未替换会显示 Tcl/XSDB 错误。轮询用 `clock seconds` 且每次等待 2 秒，只用于超时控制；性能数字应读取 ELF 写入的硬件计数器，不用 XSDB 轮询时长代替。

### 换到其他题目怎么用

以本项目为例，裸机 C 文件既在板上运行，也在主机编译成参考程序。换题时先固定相同输入、输出字段和算法质量，再选择目标 SoC 的最佳可用 CPU 实现；把主机/板端比较器做成硬门槛后才记录性能。纯 FPGA 没有同片 CPU 时，保留优化桌面 CPU 和参考实现两条，并明确它们回答的问题不同；不要硬造“同片”基线。

## 来源

来自一次「基线不可比」的教训：项目早期的对外材料写过「相较传统 CPU 方案约三个数量级的加速」，
而后来按同一口径实测，发现连优化过的桌面 CPU 多核都打不过。
返工之后确立了两条规矩：**基线必须是优化过的**，**对照必须同口径**；
再往后才想清楚，嵌入式加速器真正该打的那条基线是**同一颗芯片上的 CPU**。
