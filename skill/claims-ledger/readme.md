# 技能包：证据台账——把「可以说的话」和「不能说的话」钉在一起

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

项目做久了，文档里会沉淀出一堆结论。麻烦的是：

- 早期的估算被后来的实测推翻，但**旧数字还留在别的文档里**，还在被引用；
- 「大约」「预计」写着写着就变成了「实现了」；
- 答辩前临时汇总材料，没人记得清某个数字是实测的、外推的，还是当初拍的。

**最危险的不是没有数据，而是分不清哪些是数据。** 台账就是治这个的。

## 使用方法

维护**一份**文件（本项目叫「证据台账」），只放两张表，其他文档一律引用它。

### 表一：可以说的话

| 列 | 内容 |
| --- | --- |
| 主张 | 一句可以直接写进报告 / 答辩的话 |
| 数据 | 具体数字，带单位与口径 |
| 证据 | 留证目录 / 日志 / 报告的路径 |
| 复现 | 一条能重跑的命令 |
| 边界 | 在什么范围内成立（规模、参数、器件） |

### 表二：不能说的话（**这张表才是关键**）

| 列 | 内容 |
| --- | --- |
| 说法 | 一句听起来很想说、但**目前不成立**的话 |
| 为什么不能说 | 用实测数据说明它为假，或说明缺哪一步证据 |

例（本项目真实条目，已脱题）：

- 「比 CPU 快 N 倍」（不加限定）→ 现行基线是项目 **48 核服务器参考实现**；板端 `t_result` 与该基线的输入规模和边界不同，**不相除写加速比**；
- 「低功耗 / 能效优势」→ **一个功耗数字都没测过**，没有功率计；
- 「纯硬件三级流水线」→ 其中一级实际跑在 CPU 上，架构图必须如实标注；
- 「某某优化提升了吞吐」→ 只对小规模成立，全量任务反而略差。

### 四条配套纪律

1. **数据分级**：每个数字标注是 实测 / 历史实测（旧配置）/ 外推 / 估算，
   四类不得混用，外推必须写明拟合区间与外推倍数；
2. **改结论必须同时改台账**：新实测推翻旧结论时，旧条目划掉并注明被哪次实测推翻，
   **不要直接删**——删掉就没人知道它曾经被相信过；
3. **对外表述前先查台账**：写报告、做 PPT、答辩前过一遍两张表。
4. **区分证据是否随提交交付**：台账的路径列要标出版本管理的摘要、忽略的本机日志或仓库外原始记录。被 `.gitignore` 排除的 `logs/` 和外部路径可以作为审计线索，不能写成“已随代码入库”。

## 失效条件

- 台账只保证「说法有据」，不保证「设计好」。
- 一份台账只能覆盖一个口径体系。若同时支持多个配置（不同器件、不同数据集），
  每条主张都要带配置标签，否则会串。
- 需要有人真的维护它。台账过期比没有台账更危险，因为它看起来权威。

## 已验证效果

本项目台账里「不能说的话」共 9 条，每条都有实测支撑其为假。三次实际拦截：

1. 仓库简介与早期材料里写着「一到两个数量级的加速」，而实测是「只快于单核」。
   台账让这个矛盾在对外材料成型前就暴露了出来；
2. 一条「某阈值是最优值」的说法，查台账发现那个值是设计时按比例拍的、从未测过，
   随即改口为「设计取值，敏感性见 XX 实验」；
3. 一条「误接受率低说明系统鲁棒」被台账挡下：该指标衡量的是中间状态的污染程度，
   和任务成败不是一回事——实测中它高达 21.76% 时，任务仍然 3/3 逐位恢复。

反面证据同样有价值：台账里记着**四次失败的优化尝试**（含每次的失败数字和放弃理由），
它们防止了后来者重复投入。

### BKB220 P16 可说与不可说的例子

- **可以说**：BKB220 / `xc7z020clg400-2` 的 P16（16/1）已完成 smoke、全量三轮与连续脏轮/干净轮；2026-10-12 阶段全量 `t_result` 样本为 8.61 / 8.71 / 8.61 s，图片 SHA-256 一致、四级取证通过。后续六档矩阵、故障探针、v1/v2 数据集对照及 2 h 长稳已有记录，详见 `report/design-report-2026.pdf`。
- **不能说**：8 个 v2 challenge 例已恢复（它们仍 LDPC 不收敛）；功耗、F9、QSPI 冷启动已完成。**已完成、可以说的是**：v2 `score_min=67` 已板测（26 通过 / 16 安全失败 / 0 例静默错误字节）、5 个新载荷均完成板端四级取证（5/5 场次 4/4 级通过）、8 h 长稳已通过（2026-10-18：1736 轮 / 173 探针 / 8 h 0 m 10.3 s）。8.61 s 是阶段样本的 `t_result`，不是整轮耗时或 CPU 加速比；最新同小时参考 `t_result` 为 9.33 s。
- **证据交付状态**：（原始日志未随包提交） 下的原始运行材料在仓库外。若材料包只包含仓库文件，只能称 `report/design-report-2026.pdf` 中的阶段摘要已提交，不能称原始日志已提交。

### 换到其他题目怎么用

以本项目为例，台账同时登记了可说的性能数字、不能说的加速/功耗结论和证据是否随包交付。新队伍可在 `docs/claims-ledger.md` 复制上面两张表：每项先写一句带配置和边界的主张，再补单位、测量端点、输入规模、证据路径、重跑命令和交付状态；反面表记录“当前不能说什么”及缺失判据。更换 FPGA、数据集或计时定义时创建新配置标签并重新测量，不把本项目的测量值当成可迁移基线。

## 来源

一次返工：早期材料声称了一个数量级级别的加速，后来按同一口径实测，
发现连优化过的桌面 CPU 都打不过。返工时最费劲的不是重测，而是
**把散落在十几份文档里的旧数字一个个找出来改掉**——有些还在被别的结论引用。

从那以后规定：**结论只在一处定义，其他地方引用**；
并且专门留一张「不能说的话」，因为经验表明，
**人（和模型）会不自觉地把估算写成结论，除非有一张表在旁边盯着。**
