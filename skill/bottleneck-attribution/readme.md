# 技能包：PS + PL 系统里「到底谁在拖慢」——先证伪，再优化

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

软硬件协同系统跑得比预期慢，而你手上有好几个嫌疑人：PL 计算、DMA 搬运、
PS 固件轮询、Cache 维护、网络传输。**在动手优化之前**，用几个便宜的对照实验把它们逐个证伪。

这份技能包给的是**判据**，不是猜测清单。核心是一条：

> **能被「改掉它、看总时长变不变」证伪的猜测，就不要靠相关性去相信。**

## 使用方法

### 步骤 1：先量出「每单位工作量的成本」，而不是总时长

跑至少 3 个规模档（比如 N、4N、16N），每档重复 3 次取中位数，拟合

```text
T = 固定开销 + 每单位成本 × N
```

- 固定开销大 → 去查初始化、握手、预载；
- 每单位成本大 → 去查主计算与数据通路。
两者的优化方向完全不同，**不先分开就会优化错对象**（本项目吃过这个亏：
把固定开销压了 3.5 倍，全量任务耗时基本没变，因为全量里它只占 9%）。

### 步骤 2：给每一级装上独立计数器，优先用硬件计数

- PL 侧：在每个加速核里加 `CYCLES_TOTAL` 之类的周期计数寄存器（几十行 RTL，代价极小）；
- PS 侧：用 `XTime` 这类硬件计数器给每个状态累计耗时，**分开统计「在这个状态里执行」和「在等待」**。

**留证通道断了等于没有留证**：本项目的固件里早就有打印插桩，但串口线没接，
那些数字从来没被人看到，同一个问题被绕着重查了一遍。串口不通时改用调试器
（XSDB `mrd`）直接读内存里的计数器。

### 步骤 3：用「去掉它」做对照实验，而不是用「它看起来相关」下结论

最有效的一招：**把嫌疑对象直接去掉或改成极端值，重跑同一规模，看总时长变不变。**

- 时长大幅下降 → 它是瓶颈；
- 时长**逐毫秒不变** → 它只是在等别人，真正的瓶颈在别处。

注意判据要选对：**循环次数、轮询次数、CPU 占用这类指标会随实现变化，总时长不会。**

### 步骤 4：用理论值交叉验证

把实测的每单位成本和「纯硬件理论周期」对比。两者接近（差百分之几），
说明这一级已经贴着硬件极限跑，剩下的优化只能靠更多并行度或更高频率，
再抠软件是白费力气。

## 失效条件

- 步骤 3 的前提是**能安全地去掉它**。有些延时同时承担限流作用，去掉会破坏正确性——
  本项目就发生过：把逐步推进改成批量推进，直接撑爆了 DMA 描述符环。
  对照实验必须带上正确性判据（本项目是最终产物的哈希），**只看速度不看结果的实验不算数**。
- 多档拟合要求各档的行为一致。若某一档触发了不同的代码路径（例如小规模走另一分支），
  拟合出来的模型会骗人。
- 外推有范围限制：本项目曾用 128～2,048 的数据外推到 51,781，差了 25 倍量程，
  结论必须回到实测才能确认。

## 已验证效果

本项目旧板 XC7Z010 于 2026-09-22 的一轮历史实测，两个方向都用上了：

**推翻了自己的第一猜测。** 观察到：固件运行期的「等待」时间 ≈ 主循环次数 × 200 µs，
三个规模档都吻合到 1% 以内（4,096 条记录时 1,064 对 1,066 ms；65,536 条时 17,205 对 17,252 ms）。
看上去就是这个 200 µs 的休眠在定速。于是编译了一版**去掉休眠**的固件做对照：

| | 保留 200 µs 休眠 | 去掉休眠 |
| --- | ---: | ---: |
| 主循环次数（全量） | 135,981 | **13,889,938** |
| 流水线总时长 | 28,144 ms | **28,147 ms** |
| 全量板端耗时 | 25.69 s | 25.60 s |

循环次数涨了 100 倍，总时长逐毫秒不变 → **休眠不是瓶颈，ARM 一直在等硬件**。
如果没做这个实验，接下来一整轮都会花在「优化固件节拍」上。

**同时推翻了一条写在文档里很久的结论。** 之前用两版硬件的斜率反推，得出
「主计算只占每单位成本的 37%」，并据此判断换更大的芯片收益有限。
重新实测后，每单位成本 0.2451 ms 与主计算的纯硬件理论周期 0.2436 ms **只差 0.6%**，
即几乎全部成本都在主计算上。那个 37% 是在旧固件（充满轮询空等）下测的，早已过期。
这条修正直接改变了换器件的决策方向。

**副产品：找到一个真的缺陷。** 加计数器的过程中发现固件的超时判定是按「轮询次数」计的
（上限 10 万次）。上一轮优化删掉了轮询间的延时，使每次轮询从毫秒级变成 4.4 µs，
这个上限实际只剩约 440 ms，而满负载任务需要 645 ms——**全量任务必然误报超时**。
改成按真实时间计（30 秒墙钟）后修复。

### BKB220 P4 / P16 当前测量边界

2026-10-12 同一块 BKB220、同一输入和判据下，全量 `t_result`（POST 到收齐 8100B）为：P4 **26.51 s**；P16 **8.61 / 8.71 / 8.61 s**，约 **3.05 倍**。这是新板 PL 配置之间的结果时间比较，不是 CPU 基线，也不含上传与 LDPC，不能称为整轮时间或泛化加速比。

P4/P16 六档矩阵已完成，各档至少 3 次并报告中位数、离散程度、斜率和截距，见 `report/design-report-2026.pdf`。2026-10-12 的 8.61/8.71/8.61 s 是早期全量 `t_result` 样本；最新同小时参考值为 9.33 s，二者按各自时段标注。后续瓶颈归因须保留测量端点与推导边界；仓库外的板端日志不是提交物。

### 换到其他题目怎么用

以本项目为例，被测量的是 PS + PL 协同链路，单位工作量是记录数，正确性护栏是最终结果哈希。换题时把“工作量”定义为稳定的业务单位（帧、包、矩阵块等），为每段写清计时起止点，再照此记录：

| 规模 | 固件/位流标识 | 端到端中位数 | 阶段计数器 | 正确性判据 | 嫌疑项 A/B 改动 |
| --- | --- | ---: | --- | --- | --- |
| N / 4N / 16N | commit 或制品哈希 | 每档至少 3 次 | 周期或时间 | 哈希/逐字段比较 | 只改一个变量 |

没有可导出硬件计数器时，可先用主机高精度计时器量端点；结论只覆盖该端点。不同规模触发不同代码路径、A/B 同时改多个因素，或没有独立正确性护栏时，不把拟合和速度差解释为瓶颈证据。

### 第四次教训（2026-10-16）：**算得出收益，不等于拿得到收益**

这一次的错不在"判据选错"，而在**只检查了一道闸门**。

背景：周期级分析指出，主扫描引擎每批里有 `S_LOAD_R`（装载本批输入）与 `S_EMIT*`（发出结果）
两块串行工作，合起来占全量端到端约 **17%**。给位平面加第二块 bank、让这两件事藏进扫描窗口，
理论上能把它们省掉。

**第一道闸门（收益）—— 通过了，而且是实测通过的**：写了一个非生产的周期级双缓冲原型，
与单缓冲参考核逐条比对 `cw/pos/score` **全部一致**，连续 3 批、并施加了真实的背压。
周期数：参考核 3 批合计 **922,193 拍**，原型 **786,675 拍**，省 **135,518 拍**
⇒ 折算 **0.452 ms/批 × 1,619 批 ≈ 731 ms**，即理论上限 932.5 ms 的 **78.4%**。
收益是真的，不是估算。

**第二道闸门（面积）—— 直接撞死**：把这份原型并入生产 IP 源位、参数与发布件完全相同，
跑整机布局布线：

```text
ERROR: [Vivado_Tcl 4-23] Error(s) found during DRC. Placer not run.
  UTLZ-1#1  LUT as Logic   需要 62,588  可用 53,200
  UTLZ-1#2  Slice LUTs     需要 63,352  可用 53,200
```

**连布局都没进去，时序根本轮不到谈。** 对照：发布件整机只用 **36,282 LUT**（53,200 的 68%）。

再看模块级（单模块 OOC 综合，同器件同参数，只差 RTL）：

| | 生产核 | 双缓冲原型 |
| --- | ---: | ---: |
| Slice LUTs | 28,461（53.5%） | **54,413（102.28%）** |
| Slice Registers | 26,516 | **68,741** |
| F7 / F8 Muxes | 288 / 142 | **9,830 / 4,156** |
| RAMB36 | 12 | 4 |

**原型单独一个模块就超过满器件。** 而且读数字能看出代价**不在存储器**——
双 bank 位平面本身只值大约 **1 个 RAMB36**，真正爆掉的是**控制/地址/元数据状态**
（寄存器 +159%）与**宽组合选择**（F7/F8 涨了 36×/29×）。
"加一块 buffer 很便宜"这个直觉在这里是**反的**。

### 从这次要带走的两条

1. **在容量受限的器件上，优化的第一道闸门是面积，不是收益。**
   周期级仿真能可靠回答"能省多少拍"，但它**完全不能回答"装不装得下"**——
   两者是独立的闸门，**必须都过**，而且要**先过便宜的那个**。
   本项目在同一个器件上已经撞过两次同一堵墙（另一次是"每拍多处理一个碱基"的并行度方案，
   需要 63,246 LUT，同样 `place_design` 硬失败）。**两次都不是时序问题、也不是配置问题，是面积。**

2. **"判死"要判准对象。** 上面被否掉的是**那个原型实现**——它是照"语义正确"写的、
   从未按面积写。**不能**据此宣布"双缓冲这个想法不可能"。
   要在这颗器件上走通，得把核从 54,413 砍到约 42,000 以下（相对生产核的增量从 +91% 压到约 +45%），
   **没有任何证据表明做得到**，所以这条线停了；但**留下了一条未验证的猜想**而不是一句"不可能"：
   装载与发放本来就要抢同一个 BRAM 端口、必须互串，真正需要的也许只是
   "第二块位平面 + bank 选择 + 一个小仲裁"，而不是复制两套寻址引擎。

## 来源

三件事凑到一起才有了这份清单：

1. 一次把固定开销压了 3.5 倍、却发现全量任务没变快的优化——**没先分开固定开销与单位成本**；
2. 一条被相关性说服、却被对照实验推翻的猜测（上面的 200 µs）；
3. 一条因为「上一版验收只测了小规模」而漏网的回归（超时判据）。

**共同点：三次都是判据选错了，而不是代码写错了。**

第 4 条（双缓冲）是**另一类**错：判据没选错，收益也确实测出来了，
**但从头到尾只检查了「能省多少」这一道闸门，没在投入实现之前先检查「装不装得下」**。
前三条教的是"怎么把瓶颈找对"，这一条教的是**别在没确认可行性之前就把优化做完**。
