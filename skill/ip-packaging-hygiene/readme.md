# 技能包：别让「仿真的实现」和「综合的实现」不是同一份

> 参赛提交物，不是本仓库的开发规范（见上级 README）。

## 适用场景

用 Vivado IP 打包（`component.xml`）+ Block Design 的项目，随着微架构迭代，
`hdl/` 目录里往往同时存在同一个模块的多个版本：`foo.v`、`foo_v2.v`、`foo_fast_wip.v`……

于是出现一类**不报错、不影响仿真、只在上板时才体现**的缺陷：

- 仿真跑的是 A 版，`component.xml` 打包进比特流的是 B 版；
- 改 `component.xml` 里的一行文件名，就能悄悄换掉整个微架构，**综合不会有任何提示**；
- 打包目录里混着 testbench，综合工具按目录扫源文件时可能把它一起拉进去。

**这类缺陷不产生错误答案，所以所有仿真判据对它失明。**

## 使用方法

四条规则，都能写成脚本检查（建议接进每次回归，红了才算数）：

### 1. 打包目录只放会被综合的文件

- testbench 放到独立的 `sim/` 目录；
- 实验变体、半成品、已被证伪的版本放 `experimental/`；
- **零引用文件不得留在打包目录**。

### 2. 同名模块可以共存，但必须明确「现在打包的是哪一个」

维护一份受版本管理的清单（例如 `packaged_variants.txt`），内容是
「IP 名 → 打包的 HDL 文件列表」，并写脚本核对它与 `component.xml` 一致。

**意义**：换微架构必须在 Git 里留下一处显式 diff，不能藏在一行文件名里。

### 3. 被打包的实现必须被回归覆盖

`component.xml` 里列的每个 HDL 文件，都要能在回归脚本里找到至少一个用例引用它。
**测了不会进比特流的那份实现，等于没测。**

### 4. 删除要有出口，但要有依据

死文件长期留着同样有害。可删的判据建议定成三条，删除时在提交说明里写明依据哪一条：

1. 该方向已被实测证伪，且结论已写进文档；
2. 与仓库内另一文件逐字节相同；
3. 其功能已被另一个**受回归覆盖**的文件完全取代。

不满足任何一条就先移到 `experimental/` 而不是直接删——Git 历史即是证据保留。

## 失效条件

- 只适用于「文件级打包」的流程。用 IP Packager GUI 反复重新打包的项目，
  `component.xml` 会被整体重写，清单核对要改成比对文件列表而非 diff。
- 规则 3 依赖回归脚本里能静态搜到文件名；若用通配符引入源文件，需要改成显式列举。
- 脚本只能保证「打包的那份被测过」，不能保证「被测的那份是对的」。

## 已验证效果

本项目 2026-09-11 的一次代码卫生审计发现：

- **五个文件同时定义同一个模块名**，改 `component.xml` 一行就能静默换掉整个微架构；
- **回归跑的是 2 路版本，而打包进比特流的是 4 路版本**——
  也就是说，当时「验证过的实现」与「综合出来的实现」根本不是同一个；
- 打包目录里混着 testbench。

整改后加入 4 条门禁（打包清单一致性、testbench 不得在打包目录、零引用文件、
打包文件必须被回归引用），接进每次仿真回归。后续已记录的微架构切换
（2 路 → 4 路、引入参数化 P 路变体）都在版本管理中留下了显式 diff，未再出现错版问题。

补充实测：2026-09-22 新增一个参数化实验变体时，门禁立刻要求它登记到
`experimental/` 的清单表里，并要求接一个回归用例——这正是规则 1 与 3 在起作用。

### BKB220 P16 当前身份核对

当前生产核有 P4（`P_WAYS=4`、`PIPE_TREE=0`）和 P16（`P_WAYS=16`、`PIPE_TREE=1`）配置。检查时要确认三处是同一变体：`packaged_variants.txt` / `component.xml` 的文件集合、回归脚本实际编译的源文件、构建 manifest 中的参数值。P16 的 CAPS/TCP 握手与 P4 相同，不能靠应用层输出分辨 4 路或 16 路；应核对制品 manifest 或 XSA 参数。BKB220 P16 的整机 route 与板测摘要见 `build/reports`、`report/design-report-2026.pdf`。

本项目当前摘要记录：P4/P16 正式源集和 `packaged_variants.txt` 条目一致，打包检查与仓库卫生检查通过。复核时仍应在本机运行当前门禁，并记录退出码；本技能包不把某次历史 PASS 当成未来改动的保证。

### 换到其他构建系统怎么用

以本项目为例，Vivado 用 `component.xml` 选择 IP 文件，而回归曾经编译了另一个同名模块。换到其他 FPGA 工具时，把 `component.xml` 和 `PACKAGED_VARIANTS` 换成该工具实际读入的源文件列表/manifest；保留同一个核心不变量：**被打包、被回归和被制品 manifest 指认的实现必须是同一份源码与参数**。若构建系统由通配符动态收集源文件，先导出最终解析后的文件清单再比较。

## 来源

一次上板结果异常的排查：仿真全绿、综合无错误，板上就是不对。
最后发现比特流里的模块和仿真的模块不是同一份。
根因不是任何一行 RTL 写错了，而是**「哪份文件会被综合」这件事没有判据**。
