## 2. 实测留证

`run-logs/` 存放板端逐轮运行的摘要留证，分两批：

| 文件前缀 | 平台与制品 | 内容 |
| --- | --- | --- |
| `20261020t025814z-g3-full-*` | BKB220（XC7Z020），2026.1 制品，`fw_build_id=bfcd40dd3c435a19` | 一次完整 G3：三层判据、固件身份读回、四级逐级取证 |
| `20261020t071142z-soak-2h-*` | 同上 | 2 h 长稳：262 轮逐轮记录、26 次恢复探针、启动时固件身份读回 |
| `20261018t023907z-soak-8h-v11-*` | BKB220，v1.1 制品，`fw_build_id=db5705fb4d0bc003` | 8 h 长稳汇总（1,736 轮、173 次恢复探针），属另一制品 |
| `202608*`、`202609*`、`run*-uart-*` | 迁移 BKB220 之前的开发板（XC7Z010），早期 4 路版本 | 开发期判据演进记录，仅作历史参考，不对应本包制品 |

2026.1 那两组记录所用 ELF 的 SHA-256 是 `e71554ac…`，与本包 `build/artifact` 里的
`ff5894b5…` 不同：两者 `fw_build_id` 相同，差别只来自 BSP 断言里嵌入的构建绝对路径
（去掉路径字符串与随之移动的地址常量后，代码与只读数据逐字节相同），详见
`build/reports/2026.1-rebuild.md` §5.1。

摘要**保留运行当时的存放路径原样**，用于把同一轮的摘要、留证目录与产物对上号，
故其中会出现当时宿主机上的目录名；判据结论与关键计数不受影响。
**原始逐轮日志与 DDR 导出不入库**：体积大，且摘要已记录全部判据结论与关键计数。

判据是**三层**：

1. **架构判据**——板端 syndrome 全零；
2. **系统判据**——板端从合法码字直接提取的载荷 SHA-256 与期望一致；
3. **诊断层**——主机侧译码，仅记录、不作为通过条件。

加 `--full` 可追加四级逐级取证。三层都必须过，任何一层失败即整轮失败；
诊断层不参与判定，是为了避免「主机译码恰好成功」掩盖板端通路的缺陷。

## 3. 复现时的注意事项

- 先起常驻 `hw_server`（`xsdb` 自带的会随进程退出而结束）。
- PS UART 是板载 FT4232H 的通道 C（序列号尾号 `15051C` 那一路），Windows 下枚举为
  `COM9/COM10/COM11` 之一；设备名随 USB 重枚举漂移，按序列号定位而不是按号。
- `--win-root` 指向的目录必须事先存在，脚本不会替你建。
- 同一制品重跑应得到同一组判据结论；若换制品，先核对 `SHA256SUMS` 与
  `manifest.json` 里的 `fw_build_id`。
